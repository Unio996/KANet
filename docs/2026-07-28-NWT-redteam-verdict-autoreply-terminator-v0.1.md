## 0. MUST-FIX 1 🔴 P1 没有定义**复位规则**,而复位规则决定它到底是不是终止条件

### 现稿
§3 P1:「连续自动回复达到 N 次 ⇒ 停止对该 peer 自动回复,进入冷却 T」,状态 `{ n, firstAt, lastAt }`。
⇒ **「连续」的断裂条件没有定义;`n` 什么时候归零没有定义。**

### 而这一格不是细节,它决定这份设计满不满足它自己 §2 提的要求

§2 原文要求:**「终止条件必须满足:无论对方说什么,有限步内必然触发」**。对着它验两种可能的复位:

```
(甲) 时间间隔复位(常见写法: 距上次超过 X 秒 ⇒ n 归零)
   🔴 攻: 对面把节奏放慢到 X+1 秒一轮 ⇒ n 永远到不了 N ⇒ 【永不触发】
   ⇒ 它连"有限步"都不满足, 只是把烧钱速率降下来

(乙) 只有冷却 T 结束才复位(不按间隔)
   🔴 攻: 冷却结束 ⇒ 计数归零 ⇒ 循环【原样重开】⇒ 每个 T 周期再烧 N 笔
   ⇒ 总轮数仍然【无上界】, 只是被限了速
```
🔴 **⇒ 两种自然写法都交付【限速】,不交付【终止】。** 而 §2 明写要的是后者。

### 🔨 改法(二选一,但必须选并写下来)

```
① 承认它是【限速器】而不是终止条件 —— 那么 §2 那段要求要跟着改, 且验收 §6① 的
   措辞「第 N+1 轮必须不发出」要改成「每 T 窗口内不超过 N 轮」
   🔴 这条我不反对 —— 限速已经足够把"公测上花别人的钱"这个现役风险压住
② 真做终止: 加一个【不靠时间自愈】的终态。例如连续 K 个冷却周期内该 peer 仍在触发
   ⇒ 该 (relay,peer) 进入 do_not_auto_reply, 只有人工/显式动作能解
```
🔵 我倾向 ①(它便宜、够用、不引入新的永久状态),**但必须明说**。
🔴 **不许留在"没写"** —— 因为没写的那一格,落码的人会按 (甲) 写(最自然),而 (甲) 是三种里唯一**完全不成立**的。

## 1. MUST-FIX 2 🔴 P2 的数据源(`relayToName`)用错了两次,而错法是"看起来实现了"

§3 P2 提议用 `nameToRelay / relayToName` 判「对端是不是本机 agent」(§7③ 他自己也在问这张表可不可靠)。**实读结论:这张表做不了这件事。**

```
🔴 错误一 —— 键错了: relayToName 的键是 relay 【id】, 值是 agent 名
   而 peer 是一个【地址】。用地址去查一张 id→name 的表, 结构上查不到
🔴 错误二 —— 集合不全, 且不全的方向恰好是"漏 peer":
   ① 初始化(:120-133)的取数是 INNER JOIN:
      SELECT r.id, r.name FROM relay_nodes r JOIN adapter_nodes a ON a.id=r.adapter_node_id
      WHERE r.address IS NOT NULL
      ⇒ 【没有 adapter 的本机 relay 根本不在表里】
   ② 懒填(:178-185)只在【某 relay 自己要回复时】把它自己加进去
      ⇒ 它永远只加"正在回复的那个", 从不加"对面那个"
```

### ⇒ 回答他 §7③ 那个问题(他问:漏了是退化成宽上限,还是完全不生效)

🔴 **是后者,而且更糟:它会【几乎永不命中】** ⇒ P2 等于没实现 —— 但代码是绿的、不报错、日志里什么都不会说。
⇒ 这正是 vacuous-teeth 的标准形态:**装上了,而它从来没有咬到过任何东西。**

### 🔨 改法:用闸已经算好的那个值,别自己再查一次

`evaluateSenderGate` **已经在按地址正确地做这件事**(`mind-manager.js:296`):
```sql
SELECT id, name FROM relay_nodes WHERE address = ? AND id != ?
```
命中即 `relation='sibling'`,而这个结果已经放在 `gate.meta` 里、随 task 传进队列(`senderMeta`)。
⇒ 🔨 **P2 直接读 `senderMeta.relation === 'sibling'`,零新增查询。**
⇒ 🔵 附带好处:P2 与闸**用同一个值** ⇒ 两者永远不可能对不上(自己再查一次就一定会有对不上的那天)。

🟡 **而这个来源的强度我要标清**:`relay_nodes` 的两条业务写入路由今天**没有鉴权**(我另一份档 `2026-07-28-NWT-redteam-sibling-trust-from-unauthed-relay-create.md`,commit `fc01d048`)。今天靠 Console 绑回环挡着。⇒ P2 的判据是"本机可信表",**不是**"密码学可证的对端身份"。按此强度写,别写成"识别出对方是机器人"。

## 3. note-2 🔨 P1 位置提前到"调 Brain 之前"——我攻了,成立,但计数语义要写准

他 §7② 问:有没有哪个信息只有生成后才有,而计数需要它?
✅ **没有** —— 计数按定义与内容无关,提前判是免费的,我背书这个位置。
🟡 但提前之后,计数的**对象**变了:`:553` 那里数的是【发出去的回复】,提前到 Brain 之前数的是【收到的入站消息】。
⇒ 两者在"每轮都回"时相同,在"有些轮被 Gate 0/Gate 1/相似度闸吃掉"时**不同**。
⇒ 🔨 请在稿里写死数的是哪一个。我建议数【入站触发次数】(那才是"花钱的机会"的上界),并在注释里说明它与发出数不等。
🔵 攻过但不成立的一格:用入站计数会不会被对面用"我们不会回的垃圾消息"刷爆而误伤正常对话 —— **不成立**,计数是 per-(relay,peer) 的,刷爆的人只是让**自己**被静音,伤不到别的对话。

### 🔵 §2 我不但没打穿,还给他加一格(他的论证可以更硬)

他的理由是「触发依赖生成内容的分布,而那是我们不控制、也不可预测的」。
🔨 **更硬的说法**:我们的回复是**对面消息的函数** ⇒ **想让循环继续的那一方,可以通过变换自己的措辞来间接操纵我们回复的相似度**。
⇒ 也就是说,那不只是"我们不控制",是 **"对手控制"**。
⇒ **任何以内容为输入的谓词,都可被对手绕开** ⇒ §2 的结论从"经验上不可靠"升级为**结构上不可用**。建议把这句写进稿里。
