## 一、要答的一个问题

> **一个不是 Telegram bot 的外部程序,怎么进 KANet 当 broker?**

今天答案是**进不来**(`kasia-console/src/api/kanet-broker.js:270-288` 要求 `bot_token` 并打 Telegram `getMe`)。
而问题不是"多一个必填字段":

🔴 **这个入口密码学地验证了 Telegram 身份,对 Kaspa 地址只跑了一个正则(`:267`),然后把信任授给了没被证明的那一个。**
⇒ **被证明的那个身份不是我们要的;我们要的那个身份没被证明。**

## 二、判据不是新立的 —— 是 r277 自己的(而它有一半从没被实现)

r277(2026-05-29,Bettor 签 / Owner 钦定)砍掉了 `/link` 的 nonce+verifyMessage。它的注释给了两半理由:

| | 逐字 | 核实结果 |
|---|---|---|
| ✅ **被实现了的那半** | `PoolSide claim needs the real key` | ✅ 【实读】`PoolSide.sil` claim/refund 硬 `require(checkSig(...))` |
| 🔴 **从没被实现的那半** | `paying FROM an address proves control` | 🔴 【实读】`pool.js:2406-2407` 逐字:**`sender NOT checked — deterministic address binds`** ⇒ 它靠的是**收款地址确定性推导**,**从不检查付款人** |

🔨 **⇒ 提炼出 r277 真正的判据:入口需不需要证明,取决于【下游有没有一个必然要用到那把钥匙的点】。**

| | 下游有钥匙点吗 | 判 |
|---|---|---|
| `/link` | ✅ 有(claim 硬 `checkSig`)⇒ 冒报 = 钱进别人的 P2SH = 自损 | 入口可省 |
| broker onboarding | 🔴 **没有。** 地址从进库 → fork 进程 → 五道门,**没有一步要求那把钥匙** | 🔴 **不达标** |

✅ **⇒ 这不是"给 r277 开例外",是【执行 r277】。**
🔴 **而 broker 比 `/link` 更糟一层**:`/link` 冒报自损;**broker 冒报净赚** —— 拿到的不是钱,是五道门。

第二条判据:`docs/KANet-Positioning.md:78`「不审核参与者」。**今天这个入口既审核(必须有 Telegram 认的 bot),又审错了(审的不是它声称的那个身份)。**

## 四、v1 方案:挑战-签名(A)

### 4.1 三条必须成立

1. **`broker_address` 必须签一段自描述字节证明控制权**
2. **`bot_token` 降为可选** —— 它是投递通道,**不是身份**
3. **`recommended` 只发给证明过的地址**

### 4.2 机制

| | |
|---|---|
| 挑战 | 服务端发 nonce,内存 Map 绑 `(address, 用途, bot_username, expires)`,TTL 5 分钟(中间有人工去签,再短会逼人重来) |
| 提交 | ✅ **只交 `address + signature`** —— 公钥从地址推【NWT 实测,带对照臂】 |
| 防重放 | 验成功即 delete + TTL 到期清 + 🔴 **真正的防重放在签的字节里** |

**签的字节 —— 自描述 + 域分离:**

```
KANet broker onboarding
network: testnet-12
address: kaspatest:xxxx
bot: @xxxx
nonce: <hex>
expires: <ISO8601>
```

🔴 旧版签的是**不透明字符串** ⇒ 受害者看到乱码,**无从判断自己在授权什么**,可在任何"帮我签个字符串"的场合被诱签。
✅ 现在这个形状:**攻击者拿到的签名只对这一个用途、这一个部署、这一个 bot、这一段时间有效。**
🔴 **`network` 那行不可省** —— 域分离要覆盖"这个用途 **+ 这个部署**",否则一份 testnet 的授权可以被拿到别的部署上重放。

🔴🔴 **待签字节必须【存下来逐字用】,验签时读存档那一份,绝不在验签时重新拼一遍。**
⇒ 重拼时字段顺序 / 空白 / 时区格式任一处不同 ⇒ **签名完全正确而验签失败** ⇒ 报错又一次指向别处。
🔵 而它顺带让 §4.4 免费:**我们存的就是第三方拿去复验的那一份,天然是同一个东西**;而"重新拼"会让存档与实际验的那份可能不一样。

### 4.3 🔴 P2SH 硬闸(实测结论,不是建议)

> **【NWT 实测,带先验臂 + 对照臂】`XOnlyPublicKey.fromAddress(<P2SH 地址>)` 不抛错 —— 它把【脚本哈希】当公钥返回,根本不校验地址版本。**

⇒ 后面 `verifyMessage` 拿这把**假公钥**去验 ⇒ 验不过 ⇒ **外部集成者看到的是"签名验证失败",不是"你的地址类型不支持"** ⇒ 他会去查一个不存在的签名 bug,而真正的问题在地址的第一个字节。

✅ **硬要求:入口必须显式判 `address.version === 'PubKey'`,不是就直接拒,并说明【是地址类型不被支持】。**
🔴 **不许依赖 `fromAddress` 抛错来挡 —— 实测它不抛。** 这不是加固,是**否则错误信息是错的**。

🔵 **而这不是库的缺陷,是我们问了一个对 P2SH 无意义的问题**:
- **P2PK**:控制权 = 持有私钥 ⇒ **A 是它的原生证明**
- **P2SH**:控制权 = 能满足那个脚本 ⇒ **只能通过花一笔钱来表达** ⇒ **B 才是它的原生证明,A 对它原理上不适用**

⇒ **v1 只做 A + 显式拒 P2SH。B 留给 P2SH,等确实有人来要再做(§6 的四条留给那个人)。**

### 4.4 🔵 拱心石:公开证明与自描述【互锁】

> **落库保存【签名 + 被签字节原文】,并公布字节格式规范(哪几行、字段顺序、换行怎么算)⇒ 任何第三方离线可自验。**

🔴 **而这两条不是各自的好主意,是互锁的**:
- 若签的是**裸 nonce** 而我们又把签名公开 ⇒ 那是一张**不写用途的空白授权**,任何采用相同格式的系统都可能被它通过。
- 若**自描述而不公开** ⇒ 存档只有我们看得懂,「任何人都能自己验」是空话。

🔨 **⇒ 写成一句,不许拆到两个小节** —— 拆开后改稿的人会以为可以只留一条。
🔵 **⇒ 它解掉 A 的固有短板:A 的证明本来是"我们验完就丢、我们是唯一见证人";存档+公布之后,我们只是【第一个】见证人。**

🔴 **而规范里必须写死 `expires` 的语义:它只约束【什么时候可以提交这个签名】,不约束这份控制权证明的有效期。**
⇒ 存档是永久的,而字节里嵌着一个短期字段 ⇒ **一年后第三方复核会看到"已过期",判不出这份绑定是仍然有效还是作废了。**
🔵 一份永久存档里嵌一个短期字段,而复核者无从知道该按哪个读 —— 这个形状很少有人想到,所以必须明写。

### 4.5 🔴 provenance:同一个验签结果,在两类 broker 上含义完全不同

> **若某个 broker 的私钥在我们手上(托管),那"签这段挑战"是【任何能够到那个 relay/托管的人】都能让它做的动作。**
> ⇒ 对托管型 broker,这个签名证明的是**谁够得到我们的托管**,不是**谁拥有这个地址**。而验签这一步分不出来。

✅ **存档必须记 provenance,而只有两档:**

| 标签 | 含义 |
|---|---|
| `produced-by-us` | 这一份是我们自己的 relay/托管签出来的 —— **我们确知** |
| `provenance-unknown` | 外部提交上来的,**来源我们不知道** |

🔴 **不许写"外部自签"** —— 外部交上来的只有 `address + signature`,他可能自己签、可能托管在别人那里、也可能是另一个 relay。**写"自签"是在替对方作证,而我们没有那个证据。**
🔵 **断言的范围不能超过取证工具的物理触及范围。**

🔴 **`produced-by-us` 的那份不算证明**:那是"我们向自己证明我们控制自己的钥匙",循环,对第三方零信息。
✅ ⇒ 它不与外部提交的那种共用标签,也不产生同一种 trust ⇒ **托管型 broker 记成【KANet 为其背书】,不是【他证明了自己】。**
🔵 **两者出事时责任归属相反(前者是我们的责任,后者是他的)** ⇒ 不该共用一个字段。
✅ **公布的规范里必须写清:`produced-by-us` 的那份不是对外可复核的所有权证据。** 否则第三方验签通过,会以为验到了所有权。

### 4.6 其余四处(不改则修一半)

1. 🔴🔴 **对 `broker_onboarding` 那一行的【任何一次写入】(建 / 改 token / 改 username)都必须带一个当次有效的签名。**
   🔴 只守"主键"不够 —— 攻击正好从"`bot_token` 可选"进来:甲带签名建行(不带 token,合法)⇒ 乙带 token 走 UPDATE 分支 ⇒ 覆盖 ⇒ **接管照旧,只是绕过了新加的那道证明。**
   🔵 **⇒ "守住 upsert 主键"听起来像守住了整张表,实际只守住了插入那一下。** 必须改写成**每次写都要重新证明**,否则 UPDATE 就是一条没有闸的旁路。
   ⬇️ 而下面这段是原始漏洞的记录,保留作为设计输入:
   `identities` 那一写**有守卫**(`:311-317` 不降 owner、不解封 blocked、只升 normal);**`broker_onboarding` 那一写没有** ⇒ 乙拿自己的 token + 甲的地址 POST 一次,UPDATE 覆盖成乙的 ⇒ **console 用乙的 token 绑着甲的地址 fork 进程**,甲无通知,无日志说"这地址换人了"。
   🔵 **性质是【我们替乙冒充甲】。** ⚠️ 读码判定,未实跑(实跑=往 live 身份表写)。
2. **`status` 列**:`:304` INSERT `'pending'`,`:300` UPDATE 不碰,`:320` 返回**硬写的 `'approved'`** ⇒ 那一列**永远停在 pending**,两个 API 面都盖住了它。⇒ **要么确实推进,要么删掉。**
3. **地址格式校验必须在调 wasm 之前**,说清哪一位不对。今天手抄错一位拿到 `RuntimeError: unreachable`(与 J1 撞的 networkId 同形状)。
4. **错误码三分**:`401` 验签失败 / `410` nonce 过期或未知 / `400` 地址格式。合成一个 400 会让集成者去查不存在的 bug。

⚠️ 旧版两端点挂 `verifyIngestRequest` preHandler ⇒ 只有我们自己的 bot 能调。**新入口给外面用 ⇒ 那道闸不能留 ⇒ 签名成为唯一认证**,门槛比旧版高,**不能照抄旧版**。

### 4.7 两档的实际含义 —— 别把一句字面为实的话当成对外承诺

🔴 **v1 并没有"去掉 Telegram 这个身份权威",它把它【关进了托管那一档】:**

| | 身份权威 | 覆盖谁 |
|---|---|---|
| 自证档 | ✅ **链上密钥** | 新增的外部非托管程序 |
| 背书档 | 🔴 **仍然是 Telegram**(唯一可用的授权就是"他是那个 `tg_user_id`") | 🔴 **我们现有的全部用户** |

🔴 **⇒ 所以「我们不再靠 Telegram 认身份」对新来的外部程序成立,对我们现有的每一个用户不成立。**
🔵 **⇒ 这是一句字面为实、省掉对自己不利那半的话,而引用的人只会带走那一句。对外文案不许这么写。**

✅ **两档不该拿到同一组门。** 尤其**第五道(进 LLM 提示词)必须要求自证档** ——
背书档的权威只是一个 Telegram 账号,**若它也能拿到说服通道,等于把最弱的证明接到了最不可观测的那道门上**。
⏳ 前四道如何在两档间分配 = **产品尺度,列给 Owner 定**,不是技术判断。

**已在库的行怎么办(读法乙,写死):**

> **保留那一行,而对它的【任何一次写入】一律要签名,不因为"它是老行"就放行。**
> - 能签 ⇒ 无感,且证明自动补齐,那一行自动转成已证明
> - 不能签 ⇒ **改不了,但也没坏** —— 一个不能证明自己是主人的人,本来就不该能改那一行

🔵 **⇒ 不必现在为一个"可能不存在的问题"设计迁移流程。让它在确实发生时才浮出来。**

🔴 **而实情已经查了(【实查 live DB · 只读】):这样的行只有 1 个,且它是我们的托管钱包。**
- `broker_onboarding` 行数 = **1**(`@younio2024`,2026-07-05,`status` 停在 `pending`)
- 它的 `identity.trust_level = recommended` ⇒ `approvedBrokers()` 捞得到 ⇒ **有一个活的 fork 进程**
- 🔴 它命中 `tg_custodial_wallets.kaspa_address`,`mnemonic_encrypted` **非空**(`tg_user_id 1437320734`)⇒ **助记词在我们库里**

⇒ 所以:**它停在"KANet 背书"档 · fork 照跑 · 标签说实话 · 不会坏。**
🔵 **而它「无法被证明」与「无法被夺走」是同一个原因** —— 谁都签不出来 ⇒ **接管路径对它是关死的**。冻结在这里恰好是它最安全的状态,**而这不是为它设计的,是那条统一规则自己长出来的。**

🔵 **⇒ 一条 08:58 基于理论加的区分(provenance),在落地之前就撞上了唯一的现存实例。** 若没加,这唯一的迁移案例会被静默标成"已证明" —— **而那是假的,且没有任何东西会喊。**

**B 的实际代价(若将来为 P2SH 做,按这个记):**
1. 🔴 需要一件本仓没有的原语:**判定"这笔钱是从那个地址来的"**。唯一近似是 `rpc-listener.mjs:383-395 extractSender()`,**启发式且回落 outputs = fail-open**。⇒ 选 B = **先重写一个钱路相邻的共享函数**。
2. ⚠️ `check_utxo_landed` **答的是收款侧**(某地址收到没有),参数里没有"发送方"概念 ⇒ **不能当作"验证路径已存在"**。
3. ✅ 防重放两条缺一不可:**收款地址必须本次申请专属·当场派生** + **txid 一次性消费 UNIQUE**。
   🔵 **确定性推导是用来防重放的,不是用来替代身份的 —— r277 的误读正在这里。**
4. 🔴 **B 把准入押在我们的水龙头上**(TN12 的币要从我们这里领)⇒ **审核者从 Telegram 换成我们自己**。
   ⚠️ 不足以否掉 B,**但必须写下来,否则我们会带着"已经解决了审核参与者"这个错觉上线**。
5. ⚠️ 「任何人都能自己复核」**只在我们公布派生规则之后才成立** —— 否则外人只看到"有人付了一笔钱",复核不了绑定。
