## v1.1-rc 增量审(`f803496e`)—— N8 proof-of-possession 层,PASS

**背景**:我在设计中期发现 N1/N2 的派生证明是纯公钥算术(非硬化派生只需根的 xpub,不需要私钥),而 N6 要求根对验证方可读且各域互相核对同源本来就得读别人的根 ⇒ 根与派生 pubkey 都可抄,没有持有证明时登记表每行只是声称。Bettor 裁采纳我的方向(签名式 proof-of-possession),J2 落成 N8。

**核实(现读代码,不采信 commit message 转述)**:
- **验签公钥 = 申报的 identity pubkey 本身,不是提交者任意钥、不是 `relay_nodes` 地址**——这是整层的承重点,条款第 2 条把它写死,不是含糊过去。这条直接堵住我发现的攻击:域 X 抄 Y 的根、算出正确派生 pubkey、但签不出能被那个 pubkey 验过的签名(X 从未持有 Y 名下任何身份的私钥)。
- **引用的现有原语,现读确认真实存在、行为与引用一致**:`kaspa-wasm verifyMessage({message,signature,publicKey})` 在 `coord-status-sign.mjs:91-93` 确实这样用;`kaspa-wasm signMessage({message,privateKey})` 在 `relay.mjs:642(import)/647(调用)` 确实这样用——两条引用逐行核对精确,不是编的坐标。**没有新造密码学,复用的是仓库里已经在跑的原语**,这条比"我们会另起一套签名机制"要可信得多。
- **fail-closed 覆盖面**:缺签/形状不合法/挑战非服务端签发/已用过/已过期,五种失败模式全部拒、全部不落库,没有"大部分情况拒,某个分支放行"的缺口。
- **重放分析成立**:整份合法提交重放没有收益(payload 绑了提交方自己的 relay_id,重放只会去执行提交者自己那条注册;一次性挑战会让它直接失败)。**我另外推演了一步 N8 文本没写但同样成立的点**:Y 的签名能力从不会被 X 触发或获取(Y 只会为自己的合法注册签名,不存在"Y 被诱导替 X 的 relay_id 签名"这条路径),所以不存在跨域签名代签的攻击面——这条不是缺口,是确认设计没有留后门。
- **V14/V15/V16**:V15 精确对应 Bettor 那句"签名有效≠控制成立"的验收要求(验签公钥取申报 pubkey,不是提交者任意钥),V14/V16 覆盖了缺签和挑战三种失效形态。三格没有互相重叠或漏测某个 fail-closed 分支。
- **作用域诚实**:N8 明写"关掉的是抄根冒充,不关掉一个域确实控制同一 seed 派生的两个硬化账户"——没有把这层的修复范围说大到覆盖 §1 的 C 边界(仪式域)问题,那条本来就不是密码学能解的。

**总裁定(v1.1-rc)**:**PASS。N8 层设计正确、复用真实存在的原语、fail-closed 覆盖完整、作用域诚实。A2 规范可继续落码。**
