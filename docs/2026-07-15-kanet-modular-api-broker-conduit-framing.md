## 零、对抗轮① 收敛结论(2026-07-15 08:4xZ·Bettor 记)

### §五 v0.1 框架稿三处错误前提(三方抓出, Bettor 认账修正)
1. **"trustless 已解决只差推广"是错的**(NWT): 已证=分配环节 trustless(给定正确输入, 分对且偷不走, fw9kk 实证); **未证=输入可信**(feeSplit 吃的 poolSompi/winners 是调用方自报, 无独立链上复算层)。把 trustless 开放给任意第三方 app = 全新攻击面(规则注入 99% 自肥/自成交马甲刷佣零 sybil 抵抗/触发环节敞开)。
2. **"permissionless vs 审核闸"是已决陈饭**(J2): 7/4 Owner 钦定+落码, 测试网已 permissionless。真问题=**broker 身份与 TG-bot 焊死耦合**(必须交 bot_token, broker_onboarding 0 条真实记录=空转骨架), 电商类 app 要 HTTP API 不要养 bot; 且**身份注册与费率声明是两条不相交路径**(fee_rules=建市场方 write-once 嵌入, app 无"注册后声明费率"标准通道)。
3. **"introducer 自动归属=标准化既有机制"是错的**(KANet-UI): 现状=create-v07 手动传参(且 6 月 uw8rd 100KAS 事故在此路径), 自动归属**不存在, 是新建**; custodial/自持地址是**信任模型差异**(谁持钥谁签名)非 UI 选项, 双轨标准化禁做成"一个参数切换"。

### §六 共识(零分歧, 直接进设计)
- **信任边界总切法**(J2 提出/KANet-UI 附议/与 NWT 攻击面同图): 拆出的 API 进程只做**协议翻译+速率限制+转发**(镜像"relay=唯一链上出口"既有边界); 分润计算/链锚校验/verify-value-source 全留受信任核心侧。应用打崩 API 进程 = 最多 DoS, 永远拿不到伪造分润的能力。
- **顺序铁律**(KANet-UI): 内部 API 收敛(register×6/create×3 裂变, 7/5"调用方不选版本"整顿未完成)**先于**对外标准 API——否则技术债焊进对外承诺改不动。
- **执行面硬验收**(KANet-UI 批0 教训): ①拆分前先完成"数据访问分类"(哪些必须核心侧/哪些可跨进程 IPC, 防重演 seeder 连坐 MUST-FIX); ②新 API 进程 restart-safety(端口检测/幂等/守卫)= 第一天硬验收项非留白。
- **identity trust ≠ 数据可信**(J2/NWT 同点): 两层信任设计上物理分开, 不许用"onboarding 已放开"模糊数据校验缺失。

## 二、目标形态(一图)

```
  应用A(电商)   应用B(预测)   应用C(任意行业)     ← 每应用 = 一个 broker 端
      │             │             │
  ────┴─────────────┴─────────────┴────  标准 API 接口层(版本化·调用方不选版本)
      │   KANet 基础层(三原语)                │
      │   身份/发现 · 安全通信 · 价值结算       │
      │   +分润组件(命门④链锚·trustless)      │
  ────┬─────────────┬─────────────┬────
      │             │             │
   钱包用户(custodial TG / 自持地址 / 任意接入端)
```
佣金管道 = 应用(broker 角色)促成的每笔价值流动, 按链锚规则自动分给 应用/引荐人/验证方/基础设施, 谁也偷不走 → 应用接入动机自洽。
