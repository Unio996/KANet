## 二、目标形态(一图)

```
  应用A(电商)   应用B(预测)   应用C(任意行业)     ← 每应用 = 一个 broker 端
      │             │             │
  ────┴─────────────┴─────────────┴────  标准 API 接口层(版本化·调用方不选版本)
      │   KANet 基础层(三原语)                │
      │   身份/发现 · 安全通信 · 价值结算       │
      │   +分润组件(命门④链锚·trustless)      │
  ────┬─────────────┬─────────────┬────
      │             │             │
   钱包用户(custodial TG / 自持地址 / 任意接入端)
```
佣金管道 = 应用(broker 角色)促成的每笔价值流动, 按链锚规则自动分给 应用/引荐人/验证方/基础设施, 谁也偷不走 → 应用接入动机自洽。

## 三、对抗讨论议题清单(六项·各 owner 认领互挑)

1. **API 标准面**(KANet-UI 主答): 暴露哪些原语(身份注册/发现/建单/押注·下单/结算状态/分润查询/通知订阅)? 版本化策略? 认证=地址签名制? 与现有 8 register/3 create endpoint 的收敛关系(7/5 整顿账)?
2. **broker 端模型**(J2 主答): 现有 broker_onboarding/trust-elevation 如何泛化为"任意应用注册即 broker"? permissionless vs 审核闸? 费率结构谁定(机制 vs 部署方决策边界, KB §5)?
3. **佣金管道 trustless 保持**(NWT 主答): 任意应用可配分润规则时, 命门④链锚+verify-value-source 如何不被应用端污染? 恶意应用攻击面(假用户/自成交刷佣/规则注入)?
4. **钱包用户端**(KANet-UI): custodial TG(已 live)与自持地址双轨的标准化; 应用带用户进来时 introducer 角色的自动归属(引荐链)。
5. **边界铁律**(全员): 什么焊死在 KANet 核心(结算/信任/身份), 什么归应用(UX/业务逻辑)——"只建地基不造房子"如何在 API 面落成硬边界而非文档约定?
6. **与进程分离手术的合并**(J2+KANet-UI): 批1+ 的进程拆分切面(API 层独立进程)与本议题的"标准接口层"是**同一个架构动作**——两线合并设计, 一次手术两个交付?
