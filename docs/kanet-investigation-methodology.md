# KANet 系统调查方法论

> 遇到系统行为异常，必须按以下六层顺序调查。不允许跳步。
> 跳步的代价：结论正确但论证软，下次同类问题无法复用结论。

---

## 第一层：场景

**目标：锚定"什么是正确行为"。**

没有这个锚点，后面所有的"问题"都可能是伪问题——你在修一个其实不该存在的功能。

必须回答的问题：
- 这个功能的设计意图是什么？
- 正常场景下，用户/Agent/外部节点的预期体验是什么？
- 异常是必现还是偶发？在什么条件下触发？
- 旧版本是否工作正常？从什么时间点开始异常？

**输出：** 一句话描述"期望行为 vs 实际行为"。

---

## 第二层：真实数据

**目标：用 DB 里的实际数据说话，不用日志猜测，不用代码推断。**

这一步最容易被跳过，也是最容易产生错误结论的地方。

必须执行的操作：
- 直接查询相关表，看实际值
- 记录关键字段的时间戳（创建时间、更新时间、状态变更时间）
- 对比"应该有的数据"和"实际有的数据"的差异
- 统计异常数据的规模（影响了多少条记录、多少个 peer）

**禁止：** 凭日志或代码阅读推断数据状态，必须实际查询验证。

**输出：** 真实数据快照，标注异常值。

---

## 第三层：协议

**目标：区分"协议设计错了"还是"实现偏离了协议"。**

这两个问题的修复方向完全不同。

必须回答的问题：
- 协议消息的格式和字段定义是什么？
- 协议规定的状态机是什么？哪些状态转移是合法的？
- 当前异常行为，是协议本身的设计缺陷，还是代码没有按协议执行？
- 协议是否有版本变更？旧版和新版的差异在哪里？

**输出：** 标注出"协议规定"和"实际执行"之间的偏差点。

---

## 第四层：执行逻辑

**目标：追踪代码执行路径，找到偏离点。**

必须执行的操作：
- 从入口到出口，完整列出执行步骤（不跳过任何中间节点）
- 标注每一步的 await/fire-and-forget 属性（这决定了执行顺序）
- 找出竞态窗口：哪些步骤之间存在时序依赖？依赖是否被代码保证？
- 对比旧版代码和新版代码的差异（git diff）

**重点警惕：**
- fire-and-forget + 后续 await 的组合 → 竞态温床
- 新增 DEDUP/去重逻辑时，写入位置是否同步调整？
- 时序假设是概率性的还是确定性的？必须明确区分

**输出：** 完整执行步骤图，标注竞态点和假设条件。

---

## 第五层：数据流向（逻辑链）

**目标：验证数据从产生到存储的完整路径，找到链断裂的位置。**

这是把协议和存储连起来的中间层，最容易藏竞态和边界条件。

必须追踪的路径：
```
外部事件
  → 哪个模块接收？
  → 经过哪些处理步骤？
  → 写入哪张表的哪个字段？
  → 其他模块如何读取这个数据？
  → 读取时机和写入时机是否存在窗口？
```

必须回答的问题：
- 数据是否存在双写（同一数据写入多张表）？两张表是否保持一致？
- 统计查询的 SQL 是否有过滤条件？是否把系统消息计入了业务消息？
- 状态字段是否区分了"协议状态"和"本地观测状态"？

**输出：** 数据流向图，标注每个节点的写入/读取时机。

---

## 第六层：存储表

**目标：DB 是最终事实，用表结构和实际值验证前五层的推断。**

必须检查的内容：
- 相关表的 schema（字段类型、索引、约束）
- 是否有 UNIQUE 约束保护关键字段（如 payment_txhash）？
- 时间戳字段是否齐全（created_at / updated_at / 状态变更时间）？
- 统计不一致的两张表，各自的行数和关键字段值是否吻合？

**补充：UI 呈现验证**

UI 是验证终点。用户看到的是否和 DB 一致？
- 如果不一致 → 问题在渲染层或 API 层
- 如果一致但错误 → 问题在数据层

**输出：** 确认 DB 实际状态与前五层分析一致，或标注新发现的矛盾点。

---

## 结论输出格式

完整走完六层后，输出必须包含：

```
【场景】期望行为 vs 实际行为（一句话）

【根因】精确到文件名 + 行号 + 是什么引发了什么

【时序/竞态说明】
  - 是概率性竞态还是确定性失败？
  - 在什么条件下必现？在什么条件下偶发？

【影响范围】
  - 影响的数据规模（条数、用户数、时间范围）
  - 哪些场景不受影响（重要！避免过度修复）

【修复方案】
  - 改哪个文件的哪一行，改成什么
  - 修复后是否引入新的窗口或边界条件？必须明确说明

【验证方式】
  - 修复后如何验证（具体的命令或查询）
  - 期望输出是什么
```

---

## 常见跳步错误

| 跳过的层 | 典型后果 |
|---------|---------|
| 跳过第二层（真实数据） | 结论依赖代码推断，timing 假设未被验证，论证软 |
| 跳过第三层（协议） | 修了实现，没发现是协议设计本身的问题 |
| 跳过第四层的时序分析 | 找到了"问题代码"但没找到为什么这里会有问题 |
| 跳过第五层（数据流） | 修了写入端，没发现读取端的统计 SQL 也需要改 |
| 跳过第六层验证 | 修复方案在代码层面正确，但 DB 约束缺失，竞态从别处回来 |

---

> 这个方法论适用于所有 KANet 子系统的异常调查：Relay、Mind、Scout、Console、交易状态机。
> 编程智能体在开始任何修复之前，必须先完成前三层的输出，得到架构师确认后再进入第四层。
