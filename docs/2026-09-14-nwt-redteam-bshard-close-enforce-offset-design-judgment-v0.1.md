# NWT 判断 · `bshard-close-enforce.mjs`委员签名校验偏移设计——硬编码常量 vs 运行时派生

> **Status**: FINAL v0.1（2026-09-14 · NWT · docs only）
> Bettor 1224：J2跑既有测试曝出`_PREDICATE_COMMIT_REDEEM_OFFSET_V2`/`_PMR_COMMITTEE_CHECK_OFFSETS_V2`在
> 新pin+30参数ctor下万级漂移。请先判设计：(a)硬编码+tripwire vs (b)运行时从编译产物派生偏移（是否引入
> "产物被换则偏移跟着被换"新攻击面，是否需绑D-019 pin）；predicate_commit 4处命中该选哪处。

## 结论：**(b)运行时派生更安全，前提是绑定D-019既有pin+固定git-tracked源码路径（不是caller可传路径）+
缓存（避免每次签名请求都开子进程）——这样做不引入实质性新攻击面，因为它复用的正是T3/T4已经在用的同一套
信任锚点，不是发明一个新的信任来源。当前(a)的两组常量本身防护强度不对等：`_PMR_COMMITTEE_CHECK_OFFSETS`
系列有PUSH32前缀哨兵+5份互证（部分tripwire），`_PREDICATE_COMMIT_REDEEM_OFFSET`系列完全没有任何结构
哨兵（纯裸切片）——这个不对等本身独立于这次漂移，是一个更早就存在、这次才被看见的真实缺口。"predicate_
commit 4处选哪个"这个问题本身答案是"不重要"：4处是同一个值的字节级重复拷贝，选哪个不影响正确性，只影响
"下次ctor再变时，这个具体偏移数字要不要跟着手动重算"——如果采纳(b)，这个问题自动消失（程序化搜索，不
需要人工挑）。**

## 一、现状机制——独立读源码确认

`onChainCommit = psRedeemHex.slice(offset*2, (offset+32)*2)`——从委员**独立收到**的PS redeem十六进制
字符串里，按一个硬编码的字节偏移**裸切片**出32字节，跟委员自己独立算出的`expectedCommit`比对——这是
Track B"命门①"（W2/J2设计文档语言）的核心：委员不信任调用方喂的predicate，只信从链上redeem字节里**自己
切出来**的那份，跟自己重算的比对，两者不等就拒签。**这个机制的安全性完全建立在"切的位置真的对"这一件事
上**——如果offset是错的，切出来的是**redeem里某处跟predicate_commit毫无关系的字节**，比对结果分两种：
- **偏移错→切出乱码→跟expectedCommit不等→拒签**：这是活性问题（合法close_attest签不出去，结算卡住），
  不是安全问题，是当前实测到的"红"这条。
- **理论上更坏的方向（本次未观测到，但设计上必须承认存在）**：如果偏移错误恰好切到的字节段，在某笔被
  精心构造/或恰好巧合的redeem里等于`expectedCommit`，committee会**误签一个跟真实predicate不符的verdict**
  ——这正是Track B整套设计要防的那类攻击，被一个错误的offset常量绕过了。**这条理论风险目前无法用"看起来
  概率很低"打消**：一旦offset是错的，这条防线的实际有效性就完全未知（不是"打折"而是"失效，靠运气"）。

## 二、现有两组常量的防护强度——独立核对，不对等

- **`_PMR_COMMITTEE_CHECK_OFFSETS`/`_V2`（poolMerkleRoot，5副本）**：`extractOnChainPoolMerkleRoot`独立
  读代码确认——每个offset读取前先检查`redeem[o-1] === 0x20`（PUSH32前缀哨兵，offset错了大概率不是`0x20`，
  会loud throw）+ 5份读数互相cross-check必须全等——**这是一个真实存在、虽不完美但确实在生效的部分tripwire**
  （能挡住"offset随便错到某个不巧合是PUSH32前一字节"的drift，挡不住"错的offset刚好前一字节也是0x20"这种
  更巧合的drift，但比"完全没有"强得多）。
- **`_PREDICATE_COMMIT_REDEEM_OFFSET`/`_V2`（predicate_commit）**：独立核对确认这一组**完全没有任何结构
  哨兵**——用法就是一次裸`slice`，连"redeem长度够不够"这种最基本的边界检查都没有（`_PMR`那组至少检查了
  `redeem.length < o + 32`）。**这个不对等本身是一个独立于本次漂移的真实缺口**——即便这次没有被漂移问题
  带出来，它本来就应该补一条至少同等级别的哨兵（比如同款`redeem[o-1]===0x20`的PUSH32前缀检查——独立读了
  `.sil`里`predicate_commit`ctor声明的类型是`byte[32]`，跟`poolMerkleRoot`同类型，理应也是PUSH32编码，
  这条哨兵原则上可以直接照抄过去）。

## 三、(a) vs (b)——设计判断

### 3.1 (b)运行时派生是否引入"产物被换则偏移跟着被换"这条新攻击面——独立推理，结论：不会，前提写清楚

这条顾虑的实质是："如果offset不再是写死的数字，而是每次动态算出来的，攻击者是不是能通过换掉'用来算offset
的那份东西'来操纵offset本身，达成跟直接改offset常量同等的效果？"——**答案取决于"用来算offset的那份东西"
是什么、来自哪里，不是"动态计算"这个动作本身天然危险**：

- **危险的实现方式（不该这么做）**：如果offset是从**调用方/signRequest传入的编译产物**动态派生的——那
  确实是新攻击面，攻击者只要在请求里夹带一份自己构造的"编译产物"，就能让offset指向任意位置，等价于直接
  绕过命门①。**这条本稿不建议，也不认为J2/Bettor原本设想的是这种做法**。
- **安全的实现方式（本稿建议）**：offset从**固定的、git-tracked的`.sil`源码路径**（跟部署时用的那份
  `PayoutShardV2.sil`是同一个文件，不是caller可以指定路径）+ **D-019已经建立的pin二进制**（sha256核对+
  黄金样本deep-equal，跟T4工具、跟这次刚审过的`compileSilV100`同一套信任锚点）重新编译一次，从编译产物的
  `state_span`/模板前后缀结构里程序化搜索`predicate_commit`字节的位置——**这条路径复用的信任锚点跟T3/T4
  全程依赖的信任锚点完全同源**（"这份.sil是真的部署了的那份"+"这个编译器是D-019认过的那个"），不是发明
  一个新的、独立的信任来源。**结论：只要绑定D-019 pin+固定源码路径（这正是Bettor问题里已经预设的前提，
  "是否需绑D-019 pin"——答案是需要，而且这个绑定本身就是让它不引入新攻击面的关键条件，不是可选项）。**

### 3.2 (b)相对(a)的真实优势——不是"更优雅"，是消除了这次真实发生的那一类bug

(a)的失效模式已经真实发生了两次（V1→V2一次，这次T3代币化又一次）——**根因是"offset是对某个特定.sil结构
的手工快照，源码结构一变就需要有人记得去重算，没有任何机制强制这件事发生"**。(b)从设计上消除了这个"需要
有人记得"的环节：offset变成源码结构的**函数**，源码变了，下次重新编译时offset自动跟着对，不需要人去猜
"这次改动会不会影响offset"。这正好对应T4整个"创世前硬门"的设计哲学（"给定源码+ctor，重新算一遍权威产物，
不信任何写死的快照"）——把同一套哲学用在committee daemon的offset推导上，是同一个模式的自然延伸，不是
另外发明一套新东西。

### 3.3 (b)引入的真实、需要正面处理的新增维度（不是攻击面，是运维/可用性维度）

- **子进程编译的延迟/失败模式**：committee daemon是Byzantine-defense的**热路径**（每次close_attest/
  cancel_attest签名请求前都要跑），如果每次都真的spawn一次`silverc`子进程，会给这条本该快速响应的路径
  引入秒级延迟+"编译器这一刻恰好不可用"这个新的失败模式。**建议**：offset派生结果按`(pinned编译器sha256,
  .sil源码文件的sha256)`做key缓存（跟`_runSilverc`既有的cache key构造方式同款，不是新发明），daemon启动
  时或第一次用到时算一次，之后重复用缓存——只要.sil源码或pin没变，缓存永远有效，不会拖慢正常签名路径。
- **编译失败时的行为应该是"拒绝签名"而不是"用旧offset硬撑"**：这次的经历恰好证明了"hardcode一个可能已经
  过期的数字，静默继续用"是更危险的失败模式（活性问题掩盖了理论上的安全问题）；如果换成(b)，编译失败
  应该让整条签名路径fail-closed（daemon拒绝对这个市场签任何东西，直到有人修好编译环境）——这是行为上的
  升级，不是退步：宁可committee暂时罢工，不要committee在不知道offset对不对的情况下继续签。
- **建议同时保留一份"上次已知良好值"的checked-in参考（同黄金样本的精神）**：不是为了在运行时替代动态
  计算，是为了给人一个"这次算出来的offset跟上次记录的不一样"的**可见信号**——(b)本身会自动纠正，但纠正
  发生的事实应该被记下来、被人看到，不应该完全无声无息地发生（同T4 tripwire"命中即须NWT复核"的既有纪律，
  这里可以是"派生结果跟checked-in参考不同→WARN级日志+记一条ledger，不是ERROR拦签"——因为(b)本身已经是
  正确的，不需要跟(a)一样拦下来等人手工修，只是需要留痕）。

## 四、"predicate_commit 4处命中选哪个"——独立判断，答案是"不重要，且采纳(b)后这个问题自动消失"

4处命中都是**同一个32字节值的字节级重复拷贝**（`require(blake2b(byte[](predicate_commit)) !=
predicate_commit)`这行代码里`predicate_commit`被引用两次，close_attest/cancel_attest各一次这样的
tautology check，两个entry各贡献一对，共4个位置）——**选哪个位置切，切出来的VALUE完全相同**，不存在
"选错了会切出错误值"这个问题。唯一有实质差别的是**位置数字本身要不要写死**——如果继续走(a)，"取每对
第一份、跟V1既有约定一致"这个选择只是为了**书面一致性**（跟历史注释的选取逻辑保持一致，方便以后对照），
不是安全考量。**如果采纳(b)，这整个问题自动消失**：程序化`indexOf`搜索时用同一个确定性规则（比如"某个
entry字节范围内第一次出现"）动态定位，不需要人在4个位置里手动选一个记下来。

## 五、给Bettor的处置建议

- **设计判断：建议采纳(b)，绑定D-019 pin+固定源码路径，前提条件见§3.1**——这不是引入新攻击面，是复用
  T3/T4已经建立的同一套信任锚点，解决的是一个已经真实发生两次的drift类bug。
- **落码时补三件事**：①offset派生结果按`(编译器sha256,源码sha256)`缓存，避免拖慢签名热路径；②编译/派生
  失败时整条路径fail-closed（拒签，不用旧值硬撑）；③保留一份checked-in参考值，派生结果跟参考不一致时
  WARN级留痕（不拦，只记），供人事后审计"这次为什么变了"。
- **顺手指出一个独立于本次漂移、需要单独处理的既有缺口**：`_PREDICATE_COMMIT_REDEEM_OFFSET`系列完全没
  有`_PMR_COMMITTEE_CHECK_OFFSETS`那种PUSH32前缀哨兵——即便这次选择走(b)，过渡期/回退路径如果还保留(a)
  的裸切片作为fallback，也应该补上同款哨兵，不能比另一半的既有防护还弱。
- **"4处选哪个"这个问题本身不影响安全性，答案是"不重要"**，采纳(b)后不需要人继续操心这件事。
- 本稿只判断设计方向，不涉及任何代码改动；`bshard-close-enforce.mjs`是委员签名的钱路/covenant类改动，
  落码仍须走铁律0的报备→审核→批准→测试全流程。
