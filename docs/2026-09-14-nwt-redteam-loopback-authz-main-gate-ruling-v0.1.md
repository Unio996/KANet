# NWT 判断 · T-LOOPBACK-AUTHZ第一档主闸裁定（`checkConsoleOrigin`是否可被本机进程绕过）

> **Status**: FINAL v0.1（2026-09-14 · NWT · docs only）
> Bettor 1308/1314：①`checkConsoleOrigin`能否被本机进程伪造Origin/Host绕过、是否仍需再叠一层；
> ②确认或推翻Bettor的分析——"本机进程可先GET页面取token"与"本机进程读不到浏览器会话存储"两条。

## 结论：**确认。`checkConsoleOrigin`对"本机任意进程直发HTTP请求"这个本次整条T-LOOPBACK-AUTHZ
调查的原始威胁模型零防护——不是"防护较弱"，是逻辑上无法防护，因为它比对的两个值（Origin、从Host推导
的expected）都是攻击者在构造裸HTTP请求时百分百自己控制的。它对一个不同但也真实的威胁（恶意网页CSRF）
有效，该保留，但不能当作Tier1.1/1.4的唯一/主闸。Bettor 1314的分析（页面注入token同样无效+sessionStorage
方案有效）两条均确认成立，J2可以据此出v0.2。**

## 一、独立分析`checkConsoleOrigin`——逻辑证明，不需要跑代码

`checkConsoleOrigin`的核心比对：
```js
const origin = request.headers['origin'];
const expected = 'http://' + request.headers['host'];  // 从请求自己的Host header推导
return origin === expected;
```

**攻击者视角**：一个直接拼裸HTTP请求的本机进程（不经过浏览器），**同时控制`Host`和`Origin`两个
header的值**——它只需要让这两个值互相一致（比如都设成`http://127.0.0.1:3202`），`expected`和
`origin`就会字面相等，检查通过。**这不需要猜任何秘密、不需要读任何文件、不需要知道任何只有合法
调用方才知道的信息**——只需要知道目标端口号（`kanet.env`里的`PORT`，或者对`127.0.0.1`扫一遍常见
端口）。

**这跟真实浏览器场景的本质区别**：一个恶意网页的JS**不能**自己设置fetch()请求的Origin header
——浏览器引擎在发出跨源请求时会**自己**根据"这段JS运行在哪个源加载的页面里"来设置Origin，页面JS
读不到、改不了这个值。同源策略保护的是"Origin的值不受页面JS控制、只受浏览器根据真实加载源计算"
这条不变量——**这条不变量只在真实浏览器环境里成立，对一个直接拼HTTP请求的本机进程完全不成立**，
因为它没有"浏览器"这层强制执行者，它自己就是请求的构造者，Origin对它来说只是一个可以随便填的
字符串字段，跟`Host`字段没有本质区别。

**判断：`checkConsoleOrigin`对本次triage文档（`docs/2026-09-14-nwt-redteam-loopback-authz-
triage-v0.1.md`）分析Tier 1.1/1.4时所针对的原始威胁模型（"本机任意进程凭一次HTTP POST即可真实
转走资金"）**零防护**——不是弱，是这个机制的安全性质根本不建立在"攻击者是否知道秘密"上，而是建立
在"攻击者是不是被一个强制执行Origin真实性的浏览器约束着"这个前提上，本机进程攻击者天然不受这个
约束。**

**但它对一个不同的、同样真实存在的威胁——恶意网页在另一个tab里对`localhost:<port>`发起跨源CSRF——
是真实有效的**（设计文档§0举的例子本身成立：今天任何用户访问过的恶意网页确实能静默转走这台机器上
relay的钱，`checkConsoleOrigin`合入后这条路会被真实堵住）。**这条价值是真实的，建议保留作为AND的
一道副闸（Bettor 1314方案），但不能继续当作Tier1.1/1.4唯一/主闸**——继续这样用等于用"堵住了CSRF"
这个真结果去掩盖"没堵住直接HTTP攻击"这个假结论，是两个不同威胁模型被合并成了一个判断。

## 二、确认Bettor 1314的分析——两条均成立

### 2.1 "本机进程可先GET页面取token" —— 确认成立

J2提出的替代方案（页面渲染时注入一个per-session token，前端JS读出来自动带在后续请求header里）——
**独立确认这条方案在本威胁模型下同样无效**：console本身**没有登录态**（独立读代码确认——本session
全程审查过的所有路由，没有一条`GET /relays`或类似页面路由要求任何form of认证才能渲染），这意味着
**"渲染页面"这个动作本身对任何调用方（浏览器或本机进程）都是无差别开放的**——本机进程可以自己先发
一个`GET /relays`，从响应HTML里把注入的token字符串抠出来，再拿着这个token去调后续的资金API，跟一个
真实浏览器走的路径**完全相同、没有任何本机进程做不到的步骤**。**这条方案唯一能生效的前提是"拿到页面
本身这件事需要凭据"——而这正是console目前没有、这条方案本身也没有引入的东西**，所以它不能单独成立，
只是把"要不要秘密"这个问题往前挪了一步，没有真正解决。**确认成立，J2的自我否定是对的。**

### 2.2 "本机进程读不到浏览器会话存储" —— 确认成立，且给出理由

**这是Bettor方案（admin-secret-tier + sessionStorage缓存header）真正生效的关键，独立确认成立**：
`sessionStorage`跟"页面HTML里嵌的静态内容"是两类完全不同的东西——

- 页面HTML（含任何嵌入的token）是**服务端渲染的响应体**，"拿到它"只需要发一个HTTP GET，跟发起方
  是谁无关，console没有登录态意味着这一步对任何人一视同仁。
- `sessionStorage`的值**不来自服务端渲染**，它是**操作员这个人手动输入一次**（比如在一个"请输入
  操作密钥"的提示框里敲进去），由浏览器的JS运行时写进这个tab/窗口专属的、只有同源页面JS通过
  `window.sessionStorage` API才能读到的一块浏览器进程内存/存储区域——**这个值从来没有作为任何HTTP
  响应的一部分被发送过**，一个只会发HTTP请求、不是浏览器本身、也没有拿到操作员手动输入的那次交互
  的本机进程，**没有标准的网络层手段能拿到这个值**。

**这不是"更难拿到"，是"拿到的方式完全不同类"**——前者(页面HTML)是网络可达性问题(发个GET就有)，
后者(sessionStorage)是"有没有人手动告诉过你这个秘密"的问题，本机进程作为一个独立于浏览器之外的
进程，天然不在"操作员手动交互过的对象"这个集合里，除非它能读浏览器进程自己的内存/磁盘上的会话
存储文件——**那需要额外的、明显更高的权限（进程内存读取、或浏览器profile目录文件读取），跟本
session已经承认并单独立规则处理的Rule 84边界（"能读到解密后私钥驻留的进程内存"这个攻击者层级）
是同一档，不是本次T-LOOPBACK-AUTHZ设计新引入或需要新解决的缺口——这个边界本身早就被本session认定
为"到了那个权限层级，问题已经不是这一批路由的鉴权能单独兜住的范围"（分档文档§一原文已有这句）。
确认成立。**

## 三、给Bettor/J2的处置建议

- **裁定：admin-secret-tier + 浏览器一次性输入存sessionStorage自动带header（每浏览器会话一次） +
  Origin作AND副闸 + 服务端到服务端走独立ingest_secret通道——这个方案确认是本威胁模型下唯一站得住
  的主闸设计，J2可以据此出v0.2。**
- `checkConsoleOrigin`降级为AND的一道副闸保留（真实价值：堵CSRF），不再是Tier1.1/1.4的主防线。
- 一条本session独立追查后新增的观察，供v0.2设计参考，不阻断裁定本身：即便有了sessionStorage方案，
  一个跟浏览器**同一个Windows用户账号**运行的本机进程理论上仍可能通过读取浏览器进程内存（同本
  session Rule 84用过的PEB读取同款技术，只是目标换成浏览器进程而不是console进程）拿到sessionStorage
  里的值——**这跟Rule 84的既有边界是同一档残留风险，不是这次设计的新缺口，摩擦本身（要不要为了防
  这一档攻击者再加码）已经超出本次裁定范围，如实记录供Owner一并权衡，不代为拍板**。
- 摩擦本身（引入一次解锁步骤改变现有零门槛UX）是产品决定，本裁定只确认机制的安全性质，不代为决定
  是否接受这个UX代价——按Bettor提议报Owner。
