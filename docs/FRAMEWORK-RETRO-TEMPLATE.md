> **Status**: CURRENT

> **用途**: 定期（默认每次重大里程碑，如 go/no-go 节点）跑一轮框架自检，判断 ANTI-PATTERNS.md / CLAUDE.md 这套规则体系本身有没有在起作用，而不是只看某一次具体 bug 修没修。
> **核心认识论(Bettor 2026-07-06 裁定)**: 框架对 LLM **永不完备**——总有新的低阻力路径（今天绕过"精准修复"变成"整页重写"就是一例）。所以不追求"零缺陷"，追求的是**同坑复发率趋近于零**，且**规则档案本身不膨胀成新的碎片化源**（Owner 2026-07-06 早上诊断：老文档/老决策不作废，隔一段时间被当成当前状态重新翻出来，本身就是一种"坑"）。
> **首次运行锚点**: 2026-07-08 世界杯软启动 go/no-go，用这一周（7/1~7/8）真实发生的事件跑第一圈。
> **责任人**: qzdh7nar(J1) 出模板与首轮数据整理，Bettor 审+落地裁决。

## 一、复盘议程（每轮固定跑这五步，不跳步）

1. **读上一轮 LOG**（如果是首轮则跳过）——上一轮识别的问题，这一轮有没有真的处理，还是又不了了之。
2. **填三张计数表**（见下文）——用本轮周期内的真实事件填，不是印象。
3. **逐条过 ANTI-PATTERNS.md 规则**，标记：`本轮触发过 / 本轮没触发 / 已经 N 轮没触发建议降载出必读清单`。
4. **升级/合并/降载判定**（按下文 L1-L4 阶梯 + 判定规则出结论）。
5. **写本轮 LOG + 下一轮待办**，追加到本文件末尾的"复盘记录"区（只追加，不改历史条目——这本身就是在示范"不删除、只标注"的文档纪律）。

## 三、执法阶梯 L1–L4（给"优化"一个可执行定义）

规则从被发现到被"讲过一次就完事"，中间必须有阶梯，复发就自动升级，不是靠自觉：

- **L1 · 文档记录**：写进 ANTI-PATTERNS.md，Wrong/Right/Why 三段式。首次发现默认到这一级。
- **L2 · Lint WARN**：`scripts/lint-kanet.mjs` 加静态扫描规则，命中时 WARN 不 block。适用于"高置信度信号但存在少量合理例外"的模式（参考规则 49/50 的 R_NULLIFIER_I64/R-SHARD-BLIND 设计）。
- **L3 · Lint BLOCK / 强制审核门**：命中直接拦截 commit，或纳入"铁律 0"式的强制报备-审核-批准流程。适用于 L2 上线后仍然复发 ≥1 次的规则——说明 WARN 级别的提醒不够，必须硬拦。
- **L4 · 物理不可能**：机制上直接让错误路径执行不通（例如：修复类任务禁止对既有文件用 Write 整体覆盖，只放行 Edit/str_replace 式最小补丁）。

**L4 的范围细化（Bettor 2026-07-06 裁定）**：L4 只对**修复类(fix)任务**生效——已经过批准的**重构类(refactor)任务**需要走 D-编号（DECISIONS.md 决策编号）显式解锁，否则真正需要的大范围重构会被 L4 卡死，这本身又会变成新的阻力点逼人绕开机制。

**升级触发条件**：某条规则在"同坑复发计数表"（表 1）里连续 2 轮复发 ≥1 次 → 自动升级一级，不需要另开会讨论要不要升级。

## 四、降载/合并判定（防止只增不减）

- 某规则连续 **3 轮**复发次数 = 0，且对应的代码模式已经被 L3/L4 机制锁死（不依赖人记得） → 从 CLAUDE.md"必读"清单移除，转入 ANTI-PATTERNS.md 内部索引（文件不删，只是不再要求每次接位都通读）。
- 两条规则如果本质是同一类问题的不同表现（例如"DB 记录滞后于链上真实状态"这个母题下，phantom-leaf/consolidate DB-lag/claim 假阴性其实是同一族）→ 合并成一条，附各自的具体案例作为子条目，避免规则数量虚高稀释信号。
- 发现"已经作废但未标注"的历史文档（Owner 2026-07-06 早上指出的"炒陈饭"问题）→ 不删除，在文档顶部加：
  ```
  > ⚠️ 已废弃 — 被 [新决定/日期/文档链接] 取代，保留仅供追溯历史脉络，不代表当前状态。
  ```
