## 0. 一句话目标（不变，照抄 v0.1）

商家定一份带渠道预算的佣金计划（报价），邮件/视频/网站等任意渠道用同一种归因链接分发，消费者点开归因链接下单，一笔链上强制分账自动把钱分给商家/broker/引荐渠道，未归因的份额按报价规则并入指定方——任何人拿着开源组件就能快速部署、快速使用。

## ② 报价 JSON（不变，照抄 v0.1；新增字段见下方 §6.1 的 `mass_feasibility_proof`）

在 v0.1 报价 JSON 基础上新增一个字段（`validateQuoteMassFeasibility` 的产出，签名覆盖的字段之一，见 §6.1）：

```json
{
  "...": "...(其余字段同 v0.1)",
  "mass_feasibility_checked": true,
  "mass_feasibility_worst_case": { "no_change_mass": "437753", "with_change_mass": "…", "safety_budget": "400000" }
}
```

`mass_feasibility_checked`/`mass_feasibility_worst_case` 是**签名前必须为真**的前置条件（不是可选审计信息）——签名工具在 `validateQuoteMassFeasibility` 返回失败时**拒绝产生 `signature_hex`**，见 §6.1。这两个字段本身也被签名覆盖（写进 canonical 序列化范围内），任何人验证签名时可以同时确认"这份报价确实过过 mass 校验"不是事后编的。

## ③.3 归因防抹强化（NWT SHOULD，新增）

v0.1 §3.2 的论证（篡改要么改变地址要么改变不了份额）成立，但只到"渠道**主动**核对才有效、每单都要做、没做等于没保护"这个字面要求——NWT 建议加一条低成本主动强化：

**渠道预先公开订单地址声明**：渠道在报价发布后、消费者下单前，用自己的私钥对 `"我基于这份 quote(hash) + 我的渠道地址 ch 算出的订单地址是 X"` 签一条声明，公开发布（自己的页面/社交账号，格式自定，不需要我们的服务器）。SDK 新增两个工具函数：

```
signOrderAddressClaim(channelPrivKey, quoteHash, channelAddr, orderAddr) -> claimSignatureHex
verifyOrderAddressClaim(channelPubkeyHex, quoteHash, channelAddr, orderAddr, claimSignatureHex) -> bool
```

这样任何消费者/审计者**不需要主动怀疑才去核对**——结账页展示的地址跟渠道预先公开的声明**在付款前**就能自动比对，不一致直接是红旗，不必等事后审计。§4.2"建议渠道方优先自托管"是同一条防线的另一半（自己控制自己看到的页面），两者并为一条组合防线：**渠道自己控制的页面 + 渠道自己签发的地址声明，两者任一对得上，消费者付款前就有信号**。

**这不改变本设计的信任模型**（仍然是"可验证性"不是"不可能篡改"），只是把验证的时间点从"事后审计"提前到"付款前"，降低被动性——不是 MUST，是 SHOULD，本版纳入。

## ⑥ 放宽（不破 D-034 §7 三条验收为界）

### 6.1 N 收款方——报价签名时刻强制 worst-case mass 校验（MUST-1 修复）

**根因（NWT 独立复测坐实）**：`fold_to` 折算逻辑（§6.4）只会**减少**参与结算的角色数（未归因的角色被折进目标角色，从不增加）——这意味着一份报价"最坏情况"（`canonical_rules.roles` 里全部角色都被同时归因、没有任何折算）的输出集合，在报价**刚签发**的那一刻就已经完全确定，不需要等到某个具体订单才能算出来。v0.1 §6.1 把"真实 mass 估算"放在"SDK 构造具体订单时"（`buildSplitTx` 调用时）做，这时消费者可能**已经**照着这份报价推算出的订单地址付了钱——如果这次实际归因凑巧命中一个 mass 超限的组合，`split()` 从此**永久**构造不出来（不是"暂时"，这个具体 ctor 的这个具体输出组合，mass 永远是这个数），唯一出口是等 `deadline_ms` 后全额退款——分账这件事本身没有发生，且退款是全额退给付款人，如果消费者此刻已经收到商品/服务，退款反而制造一笔协议管不了的经济纠纷。

**真实实测数字**（NWT 独立复测 + J2 用同一个 `tx-mass-ub.mjs`、同一份 `n_recipient_mass.mjs`/新增变体脚本逐字复现，两次独立测量结果完全一致，非估算非猜测）：

| 场景 | mass | 结论 |
|---|---|---|
| 4-at-floor（纯 4 个卡在 0.1 KAS 运营下限） | 377,778 | 安全（对 500,000 硬上限留 24.4% 余量） |
| 4-at-floor + 4×1KAS（N=8，MAX 上限的典型混合场景） | **437,753**（余量 **12.4%**，不是 v0.1 误写的 24%——那个 24% 只是纯 4-at-floor 场景自己的余量，混合更大规模场景后余量薄得多） | 仍安全，但余量比想象的薄 |
| 4-at-floor + 4×5KAS（N=8） | 407,512（余量 18.5%） | 安全 |
| **5-at-floor + 3×5KAS（N=8，只比"≤4-at-floor"这条运营准则多 1 个）** | **505,357——超过 500,000 硬上限，共识层直接拒绝** | **一步之差从"安全"到"秒拒"，是悬崖不是渐变带** |
| 4-at-floor 基线 + 追加 1 个 1KAS 输出的边际存储质量贡献 | **+25,326**（不是 v0.1 文字暗示的"C/amount≈2000 可忽略"） | **v0.1 §6.1 的"明显高于下限的角色贡献可忽略"这句话是错的**，见下方"为什么边际贡献比想象的大" |

**为什么边际贡献比想象的大（如实更正 v0.1 的错误直觉）**：storage mass 公式里输入侧那一项 `C·p_in²/amount_in` 是一个**折扣项**（从输出侧的和里减掉）——它的大小反比于总输入金额 `amount_in`。往一份报价里加一个新输出（哪怕金额很大）会让 `amount_in`（= 全部输出之和 + 手续费）**变大**，这个折扣项因此**变小**，抵消了新输出自己那个理论上很小的直接贡献（`C/amount≈2000`）——净效应是净贡献比"直接项"单独看起来的数字大得多（实测 +25,326，是"直接项"估算的十倍以上）。**结论：不存在任何可以安全略过真实模拟的"经验法则"或"数量级估算"——任何新增输出、任何金额变化，都必须重新跑一次真实 mass 估算，没有近似公式可以替代。**

**MAX=8 与"≤4-at-floor"运营准则的关系（NWT 确认不矛盾，但也不够）**：`MAX=8` 是合约 `for` 循环的**编译期结构上限**（决定合约能不能表达 8 个输出），"≤4-at-floor"是**运营层对当次实际参与结算角色集合的经验准则**，两者管的是不同的事——但"5-at-floor + 3×5KAS"这个真实反例证明**光有这条经验准则本身不够**，一旦运营配置疏忽多算错 1 个，就从安全变成共识层秒拒且资金卡死。**真正的防线必须是代码里的强制检查，不能是一条给人看的经验准则**。

**修复：`validateQuoteMassFeasibility(quote)`**

```js
function validateQuoteMassFeasibility(quote, opts = {}) {
  const safetyBudget = opts.safetyBudget ?? 400_000n;   // 与即时分账设计稿同一套 24%~ 安全余量哲学
  const worstCaseRoles = fullyUnfoldRoles(quote.canonical_rules.roles);  // 见下方"为什么检查未折算最坏情形就足够"
  const amounts = worstCaseRoles.map(r => BigInt(quote.price_sompi) * BigInt(r.bps) / 10000n);  // 与 feeSplit 同一套 floor 除法, 不能自创另一套舍入

  // 分支 A: hasChange=false, 精确充值
  const massA = realMassEstimate(amounts, /*inputAmt=*/ sum(amounts) + BigInt(quote.max_split_fee_sompi));
  // 分支 B: hasChange=true, 找零卡在运营下限(§4.4 MIN_RECIPIENT_SOMPI, 最坏找零情形)
  const massB = realMassEstimate([...amounts, MIN_RECIPIENT_SOMPI], /*inputAmt=*/ sum(amounts) + BigInt(quote.max_split_fee_sompi) + MIN_RECIPIENT_SOMPI + 1n);

  if (massA > safetyBudget || massB > safetyBudget) {
    return { ok: false, massA, massB, reason: 'worst-case mass 超出安全预算, 拒绝签名; 需要减少角色数或提高份额低于运营下限的角色的份额' };
  }
  return { ok: true, massA, massB };
}
```

- `fullyUnfoldRoles`：把 `roles` 数组里所有带 `fold_to` 的角色**当作已经全部归因**（不折算，`address` 用一个占位值——占位值本身不影响 mass，因为 mass 只依赖 `value`/`spk` 的**字节长度**，不依赖具体内容；本设计的收款地址统一是标准地址反解出的 scriptPubKey，长度固定 36 或 39 字节，占位值用任意同长度字节即可，不影响真实性）。
- **两个分支都要测**（`hasChange=false`/`true`）——`hasChange=true` 分支多一个找零输出，找零金额未知（取决于实际充值多少），本函数用 `MIN_RECIPIENT_SOMPI`（即时分账设计稿 §4.4 的运营下限）作为找零的**最坏情形**（找零恰好卡在下限，贡献最大的单项 mass）；如果连这个最坏找零情形都过不了安全预算，报价本身就不该允许多付路径成立（消费者一旦不小心多付，`split(hasChange=true)` 会永久构造不出来，同 MUST-1 的问题，必须同一次堵死）。
- **签名工具（不管本版有没有完整配置页 UI，§2 的报价生成流程本身）在 `validateQuoteMassFeasibility(quote).ok !== true` 时拒绝产生 `signature_hex`**——这样"报价一旦签发，`split()` 就一定构造得出来"这个不变量在源头锁死，不依赖任何人在事后记得测。

**为什么检查"未折算最坏情形"就足以保证一切折算后的子集都安全（数学证明，不是直觉）**：设两个正数金额 `a, b > 0`，折算（合并）成 `a+b` 后存储质量的直接贡献项从 `C/a + C/b` 变成 `C/(a+b)`。由调和不等式 `1/(a+b) < min(1/a, 1/b) < 1/a + 1/b`（对任意正数 a,b 恒成立），合并后单项贡献**严格小于**合并前两项之和——即"折算"这个操作对 storage mass 的直接影响**永远是单调改善**（变小），不会变差。同时折算后总输出数少 1 个，输入侧的折扣项 `C·p_in²/amount_in` 不变（`amount_in` = `price_sompi` 不因折算而变，折算只影响钱怎么分配给谁，不影响总额）。**结论：任何折算操作后的 mass 一定 ≤ 折算前的 mass**——因此检查"完全不折算"这一个最坏情形，足以保证运行时任何实际归因组合（必然是某种程度的折算）都在安全预算内，不需要枚举所有可能的归因组合。

### 6.2 收款地址不限 P2PK——但必须能反解成标准地址类型（MUST-2 修复）

**v0.1 的疏漏（NWT 独立复测坐实）**：v0.1 §6.2 只验证了"格式细节"（36 字节含版本前缀会被共识接受，34 字节裸 script 被拒）——但这只证明"字节格式合法"，**不证明这段字节代表的脚本将来能被谁花掉**。UTXO 模型里，一个输出的 `scriptPubKey` 在**创建**这笔交易时，节点只检查字节格式是否合法（长度、版本号能识别），**不会去验证这段脚本未来能不能被谁花掉**。如果报价里的某个角色 `address` 字段是一段格式合法但实际上算不出真实解锁条件的垃圾字节（UI 传参 bug、恶意报价故意塞的垃圾、或纯粹打错），`split()` 一旦真的执行，这份钱就**永久烧掉**——`InstantSplit` 本身在 split 输出层面没有任何后续退款/纠正机制（`refund()` 只对**分账前**的那个 UTXO 有效，钱一旦分出去，各个输出各自独立，没有"分错了收回来重分"这回事）。

**修复**：SDK 接受报价里任何角色的 `address` 字段时，必须先用 `addressFromScriptPublicKey(spk, network)`（kaspa-wasm 标准 API，`spk` = 报价里 `address` 字段解出的 `version++script` 字节）尝试反解——**返回 `undefined` 就拒绝**（真实验证：一段任意拼的垃圾字节反解结果确实是 `undefined`，不是抛异常也不是静默接受，SDK 判空即可）；只接受能反解出以下三种标准地址类型之一的：

| 反解出的 `Address.version` | 地址类型 | 能否收款 | 能否绑定押金（见 §7.3） |
|---|---|---|---|
| `PubKey` | 标准 Schnorr P2PK | ✅ | ✅（能取出 32 字节 pubkey） |
| `PubKeyECDSA` | ECDSA 变体 P2PK | ✅ | ✅（能取出 pubkey） |
| `ScriptHash` | P2SH（任意合约地址，包括另一个 covenant） | ✅ | ❌（见 §7.3，没有单一 pubkey 可绑） |
| （反解为 `undefined`） | 不是已知模板的裸字节 | ❌ 拒绝，不接受进报价 | — |

这条校验**在报价签名前**（同 §6.1 的时机原则——能在源头堵住的问题不要留到运行时）与**在结账页渲染前**都要跑一遍（双重防线：商家自己的报价生成工具挡一次，任何独立结账页实现挡第二次，不依赖只有一方做对）。

### 6.4b 未归因份额并入指定方——方案 (b)：一单多渠道同时参与（草图，待 Owner 选定后再定型）

如果 Owner"一笔交易，多个渠道共同参与"的原意是**同一笔订单的收益真的由多个不同渠道同时瓜分**（比如同一个订单，邮件渠道 A 促成了首次点击、网站渠道 B 促成了最终转化，两者都该拿到各自的份额），需要一套全新的**多跳/多来源归因**机制，本设计**不预先选定**，只给出草图供 Owner 参考选择的影响面：

- **报价层**：`canonical_rules.roles` 需要支持**多个**具名渠道角色（比如 `channel_1`/`channel_2`……，或改成一个 `channels: [{slot, bps}]` 数组，每个坑位有自己的预算上限），而不是 v0.1 的单一 `"channel"` 名字。
- **归因链接层**：链接参数需要能表达"这次点击归因到哪个坑位"（比如 `ch1=<地址A>&ch2=<地址B>`，或每个渠道分发的链接天生带一个坑位标识），且需要一套规则解决"消费者可能经过不止一个归因链接才最终下单"时，各个坑位分别由哪次点击的哪个地址填入——这本身是一个不小的产品逻辑决定（先到先得？最后一次点击？多次点击的渠道分摊同一个坑位？），**不是加个字段能补的，是另一层设计**，需要 Owner 明确产品意图后才能定具体规则。
- **mass 影响**：**直接放大 §6.1 MUST-1 的风险**——如果一单可以同时归因给 N 个渠道（不是折算成 1 个或 0 个），"全部渠道坑位都被同时归因"这个最坏情形出现的**真实概率**从"运营配置疏忽才会撞上"变成"这就是设计出来要发生的正常业务场景"，`validateQuoteMassFeasibility` 的强制校验因此变得**更加不可或缺**（而不是可选的加固）——§6.1 的机制不需要改，但会更频繁地在正常报价配置阶段就拒绝签名，倒逼商家一开始就把渠道坑位数和份额配置在 mass 安全的组合内。
- **实现复杂度**：远高于方案 (a)，`resolveRulesForOrder` 需要整个重写，归因链接格式（§3）需要扩展，静态结账页（§4）需要能处理"当前 URL 携带了几个渠道参数"而不是假设恰好 0 或 1 个。

**Owner 需要回答的问题（供 Bettor 转达）**：① 是"多种渠道类型、每单仍只认一个来源"（方案 a，现在就能定型），还是"一单真的可以被多个渠道同时瓜分"（方案 b，需要另一轮产品设计）？② 如果是方案 (b)，多次点击归因到同一坑位时用什么规则决定谁生效（先到先得/最后一次/其他）？

## ⑦ 渠道押金 covenant

### 7.1-7.2（不变，照抄 v0.1）

### 7.3 报价里的押金核验（重写，补 MUST-2 的边界说明）

`require_channel_deposit: true` 时，结账页/SDK 在把某个渠道地址代入 `channel` 角色之前，先核对该角色的 `address` 反解出的类型（§6.2）是 `PubKey`/`PubKeyECDSA` 之一（能取出 32 字节 pubkey）——**如果不是（比如渠道的收款地址是 `ScriptHash`，即渠道想让佣金直接进自己的另一个 covenant），本版明确不支持"押金要求"与"任意脚本收款地址"同时对同一个角色生效**：商家必须二选一——要么这个角色的收款地址限定 P2PK/P2PK-ECDSA（可以同时要求押金），要么放弃对这个角色要求押金（收款地址可以是任意标准地址类型）。这是**本版的明确限制**，不是遗漏——押金身份的本质是"证明这是一个有沉没成本的具体身份"，而"身份"在押金机制里就是一个 pubkey，一个 `ScriptHash` 收款地址背后可能是任意合约逻辑，没有单一可验证的"谁能取回押金"的对应关系，勉强绑定只会制造一个新的未定义状态（同 NWT 指出的那个"两条设计各自都对但没讲清楚同时打开时怎么办"的问题）。

满足条件时，核验逻辑同 v0.1：查询 `f(channel_pubkey)` 这个押金地址是否有 ≥`min_deposit_sompi` 的余额；没有则视为"无有效归因"，走 §6.4 的折算路径，不报错卡单。
