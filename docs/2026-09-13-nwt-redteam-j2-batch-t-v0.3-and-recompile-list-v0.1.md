## ① H5 负向证明——`OpCovInputCount(token_cov)==0` 这句写法有具体技术缺口

**我核的依据**（只读，隔离 clone `scratch/_j2_silverc_v100`@v1.0.0，J2 自己那份检出，未新建/未碰 live 树）：

`docs/DECL.md:416` 与 `docs/kcc20-book/src/kcc20-minter-contract.md:81/324` 里 `OpCovInputCount(cov_id)` 的**唯一**用法都是传一个**具体的、单一的 covenant-id**（官方 `KCC20Minter` 范例里，那个 `kcc20Covid` 是这个控制器 ctor 里烤死的**一个**特定 KCC20 covenant 实例的 id，`require(OpCovInputCount(kcc20Covid) == 1)` 意思是"这笔交易里恰好有一个输入花的是**这一个特定** covenant-id"）。

**问题**：市场合约 M 的某条不共花分支要证明"没有任何代币输入在场"，前提是它知道要查哪个 `token_cov`。如果 KANet 的代币是**单一持有者模型**（全局只有一个持续演进的 covenant-id，所有 mint/transfer 都排他地经过同一个 UTXO），`OpCovInputCount(token_cov)==0` 写法没问题——但这个模型本身就有问题：**它会把所有下注/领取序列化到一个 UTXO 上，不同市场、不同投注人之间没有并发**，这与批 T §3 T2 描述的"多个领取 covenant 各自持有 amount、余额=名下求和"的设计**直接矛盾**（那个设计明确暗示了**多个**代币持有型 covenant 实例同时存在，各自不同的 covenant-id，共享同一份合约字节码/模板）。

**如果是多实例模型**（这才是与 T2 一致、且是任何实用的多用户 fungible token 该有的形态），"没有任何代币输入在场"这句话的真实含义是"没有任何一个**字节码匹配代币模板**的输入在场"——这不是"某个特定 covenant-id 是否在场"，是"**任意一个**跑代币模板字节码的 covenant-id 是否在场"。`OpCovInputCount` 按官方范例的用法只吃一个具体 id，不吃模板/字节码哈希；要表达"没有任何模板匹配的输入"，需要的是**遍历 `tx.inputs`、对每一个用类似 `readInputStateWithTemplate` 的模板哈希匹配逐个核对、断言没有一个匹配**——这与 H1 模板前缀锁用的思路是同一类原语（模板匹配），跟 `OpCovInputCount` 的"具体 id 计数"是**两种不同的原语**。

**这不是我猜的**——J2 自己在 T0①的答案里已经区分了这两种原语：`readInputState(int)`（同模板，具体 index）vs `readInputStateWithTemplate(idx, prefixLen, suffixLen, expectedTemplateHash)`（**跨模板**，靠哈希匹配）。H5 那句"`require(OpCovInputCount(token_cov)==0)`"用错了原语类——它抄的是官方范例里"单实例控制器"那个模式，但批 T 自己的设计（T2 多领取 covenant）需要的是模板匹配模式。

**MUST-FIX**：H5 的负向证明重写为——遍历本次交易的输入，对每个输入用 H1 已经在用的模板匹配原语（前缀切片或 `readInputStateWithTemplate` 式哈希核对）逐一检查是否命中代币模板字节码，断言全部不命中。这比一行 `OpCovInputCount` 调用**贵得多**（一个循环 + 每次迭代一次模板匹配，不是一次常数时间调用），直接影响④的估算（见下）。

**范围声明**：这不否定 H5"在场≠同意"这条核心判断本身（那条仍然对、仍然是 MUST）——只是**具体怎么写"没有代币在场"这句证明**用错了原语，需要在 T1/T3 落码前先把这条订正，否则写出来的 `.sil` 编不过或者编过但没起到断言作用（如果 `token_cov` 被随手填成某个占位常量，编译器不会报错，但那句 `require` 实际上什么都没验证到——这正是我域内"vacuous teeth"要抓的那类坑）。

## ② C1（allow 注解 vs 改 cov-bound 声明）——攻击面判断

**我核的依据**（同一份 DECL.md，`entry`/leader 契约段）：`allow` 注解**不是**"告诉编译器别管"的空白通行证——DECL.md 原文明确写了三选一模式（① `require(OpCovInputCount(cov_id)==1)` 拒绝共享执行 ② 拒绝 covenant input zero 扮演 delegate ③ 要求 covenant input zero 并校验完整输入/输出组扮演 leader），**作者必须先手写实现了三选一里的一种，才能加 `allow` 去"确认"这条**——`allow` 后编译器不再校验这段手写逻辑是否正确，但它假定的前提是"这段逻辑本来就该由人工正确实现"，不是"随便写就能过审"。

**我的攻击面判断**：
- **`allow` 路线风险**：三处手写 entry（FoldNode `seal_to_root`、PoolLeaf `register_append`、PoolShard_fold `register_append`）是在**旧编译器不做这项检查的年代**写的——它们大概率已经实现了三选一里的某一种（因为它们在 TN12 生产跑了这么久没出过 covenant-group 层面的事故），但**"大概率"不是"已验证"**。风险面是：如果其中某一处**恰好没有**完整实现三选一任何一种（比如漏了某个边界条件），旧编译器从不检查、新编译器加了检查但被 `allow` 关掉，这个洞会**从"编译器本该抓但没抓"变成"编译器主动放弃抓"**——比现状风险更高的不是"选 allow"这个动作本身，是"选了 allow 却没有人去读那段手写逻辑核对它到底实现了哪一种"。
- **改 cov-bound 声明路线风险**：这是**行为改写**，不是标注——改声明会让编译器重新生成 group-validation 逻辑，字节码/dispatch tag 大概率变化，等于给这三个合约重新过一遍完整验收（同 D-016 那套字节等价证明的规模），且这三个合约都在主网集（★），一次不必要的重写等于给批 T 增加了三份合约的完整回归成本。
- **判断**：**`allow` 是更低风险的选项**，前提是把"读那段手写逻辑、确认它实现了三选一的哪一种、记录下来"作为**明确的 MUST 验证步骤**，不能因为"选了低风险路线"就跳过验证——这个验证工作量不大（三个文件、每个几十行），但必须做，且**天然应该跟 H5 的输出校验审查合并在同一次人工评审里**（J2 §0.5 H5 行末尾已经提了这个建议，我认可这个安排）。

## ③ 批 A 九条——哪几条会改语义

批 A 现有九条按"是否可能改变实际字节/数值内容"分三档：

| 档 | 项 | 判断 |
|---|---|---|
| **需单独核字节等价（真正有语义风险）** | **A2**（`byte[34]→byte[36]`）、**A8**（`byte[N](int)→(x as byte[N])`） | A2 是**类型宽度变化**——如果只是重新声明宽度而底层值的字节布局本该随 v1.0.0 的编码变化而变（如 pubkey/scriptPubKey 表示法本身就变宽了 2 字节），那这条改动的"正确"取决于**值的来源是否也跟着变了**，不是纯语法替换；A8 是**整数到定长字节数组的转换**——旧内建函数与新 `as` 转换在**端序/符号处理/填充方向**上是否完全一致，这类转换历史上最容易在"编得过但值不对"这条线上出问题（尤指本条命中的 `PayoutShardV2`，**在主网集**，且很可能用于往 hash/scriptPubKey 承诺里塞金额或索引——一旦端序不对，是那种"编译通过、部署上去、构造特定输入才会露出"的坑，不是"一试就炸"的坑） |
| 低风险，J2 已用探针验证是"包一层不变值" | A6（`byte[N]+byte[M]` 拼接结果包 `byte[](…)`）、A7（哈希函数参数包 `byte[](…)`）、A9（scriptPubKey 比较右侧包 `byte[](…)`） | 三条都是"给一个已经算好的 `byte[]` 值加一层类型注解包装"，J2 自己的探针（P5/P6）已经验证了"包一层对已是 `byte[]` 的值是 no-op"——这个验证方法论正确，但只覆盖了"包装本身不变值"这一层，**没有**覆盖"包装前的那个值本身在 v1.0.0 下是否还是原来的字节"（比如 A7 包的哈希函数参数，如果哈希函数本身的实现在 v1.0.0 有变化，包装层不背这个锅，但也不能证明没问题） |
| 纯语法，零语义 | A1（关键字重命名）、A3（`byte[](x,n)`→`(x as byte[n])`，byte到byte的转型）、A4（已知 API 重命名，D-016 系列长期跟踪过）、A5（结构体字面量加类型名前缀） | 这四条只改**怎么写**，不改**算出什么**——A5 是纯语法要求（加个标识符），A1/A4 是重命名，A3 虽然也是转换但对象是 byte[]→byte[]（不像 A8 是 int→byte[]，没有端序/符号这类语义分歧点） |

**结论**：**A2、A8 是本清单里唯二需要单独逐字节等价验证、不能只看"编得过"就采信的项**——尤其 A8 命中的 `PayoutShardV2` 在主网集，这条验证应该排进批 T 落码前的 MUST 清单，不能等到"计划 §5 辅证"这个笼统的将来时。清单本身在 §6 已经如实自陈"只证编得过不证语义等价"，态度是对的，只是没有把 A2/A8 单独点名出来标"优先做"。

## ④ T3 估算——低估，且低估的原因与①③直接相关

v0.3 现估："≈32 入口 ×（一段校验 + 一正一反向量），量级 = 批 B + 批 C 之和"。**这个数字建立在"每条入口只需要一段校验"的假设上，而①已经证明"负向证明"那一段实际上不是一段简单 require，是一个循环 + 每次迭代一次模板匹配**——按 H1 同款原语实现，工程量和测试向量数都比 J2 假设的"一段"重（循环意味着要测"0个匹配/1个匹配/多个匹配"这类边界，不是"一正一反"两条就够）。

另外，34 条入口里有 3 条（FoldNode/PoolLeaf/PoolShard_fold 的手写 entry）**同时**背着②的验证任务——这是叠加在 H5 工作之上的**额外**读代码+记录的工作，J2 建议"同一批人审最省"是对的，但"最省"不等于"零增量"，这 3 条入口的实际耗时应该比其余 31 条更长，估算表目前没有单独标出来。

**结论**：T3 至少还要再往上修两次——①的修正会让"负向证明"分支的单条成本上升，③的 A2/A8 验证若发现真有字节不等价（尤其 A8 命中 `PayoutShardV2`，恰好也在主网集、也在 T3 的改动范围内），可能触发这些文件的**返工**（不是"重估"，是"已经按旧假设写的东西要重写"），这是排期风险不是简单加个系数就能吸收的。

## 给 Bettor 的处置建议

- H5 的负向证明写法先按①订正（模板匹配循环替代单一 `OpCovInputCount`），再让 J2 出一版小范围试编验证这个循环能编过、断言真的挡住"任意模板匹配输入"（不是编过就信，按我域内标准要一正一反向量）。
- C1 走 allow，但把"读三处手写 entry、记录它实现的是三选一哪一种"列为 T3 落码前的独立小任务，不能省。
- A2/A8 排进 T0 之后、T1 之前的独立验证项（离线、不花钱），确认字节等价或找出真实差异，别等到"计划 §5"这个笼统阶段。
- T3 的量级估计等①③两项落定后再报一次新数字，现在这个"≈批B+批C之和"暂不作为排期依据。
