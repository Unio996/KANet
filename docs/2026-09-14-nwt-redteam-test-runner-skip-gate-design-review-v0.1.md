## 三、(a) 显式URL指向生产口是否也该拒——独立判断，确认是真实缺口，需要补

**判断：这是当前设计一个真实、需要补的缺口，不是过度谨慎。**

现状设计§2.2第3点："若`KANET_CONSOLE_URL`已被调用方显式设置...沿用（这是调用方明确知道自己要打哪，
不受本条约束，本来就该放行）"——**这个论证的漏洞在于"显式设置"这个动作本身只证明了"有人打了这一行
字"，没有证明"这一行字打对了、这个人真的知道自己在打生产口"**。真实的失败模式（不是假设的）：一个
残留的旧`KANET_CONSOLE_URL`环境变量（比如上一次调试时手动设的、忘了清）、一次复制粘贴错误、或者一个
共享shell session里前一个任务留下的env——这些都会产生一个"显式设置"但**内容是错的**的值，恰好指向
一个真实在跑的生产/共享实例——**当前设计对这种情况完全没有信号，跟"我确认过、我就是要打这里"这种真正
知情的显式设置得到的对待完全一样**。

**这正是Bettor指出的问题本质："显式"这个属性回答的是"这行配置是不是调用方自己填的"，不回答"调用方是
不是真的确认过这个目标是安全的/预期的"这个更本质的问题**——两者不是同一件事，当前设计把第一个当成第
二个的替代品用了。

**建议**（供落码时参考，不代为最终裁定具体阈值/交互方式）：即便`KANET_CONSOLE_URL`已显式设置，仍执行
一次端口监听探测；如果探测到"有人监听"，**不必然拒绝**（显式设置确实应该比"派生值撞见监听端口"更被
信任一些），但至少应该打一条**跟当前设计里"未显式设置+撞见监听"同等LOUD级别**的提示，明确写出"你显式
指向的这个口当前确实有服务在监听，如果这不是你预期的测试专用实例，请立即中止"——**把决定权交还给人，
不是替人静默做"反正是显式的，应该没问题"这个假设**。**Bettor提的"可能还需一道real_chain类旗标"这条
建议本身很精确**：这个提示的严重程度应该跟"即将执行的case集合里有没有`real_chain`标签"联动——如果
这批case里一个`real_chain`都没有，即便撞上生产口，最坏后果多半是往生产DB插了几条测试数据（本session
既有memory里`feedback-m0a-bare-import-gate-runs-only-on-staged-diff-tests-get-a-db-via-db-path-temp-
plus-import-client`一类的既有教训范畴）；如果这批case里**有**`real_chain`，风险等级完全不同——**两种
情况不该共用同一条警告文案/同一个响应动作，应该分级**。

## 四、(b) 探测本身是否安全（只connect不触发路由）——原理层面确认成立，实现留待落码后验收

**协议层面的判断**：设计文档说的"本地`net.connect`探活"是指原始TCP socket连接（不经过HTTP层）——
如果实现真的是"建立TCP连接后立即关闭，不写入任何字节"，这在协议层面**不会触发任何HTTP路由处理**：
Fastify/Node HTTP server的请求分发（路由匹配、handler执行）依赖于HTTP解析器解析出完整的请求行+
headers之后才会派发`request`事件——一个纯TCP connect（三次握手完成后立即断开、不发送任何应用层数据）
从协议角度**没有产生任何HTTP层字节流**，服务端的HTTP解析器不会有任何东西可解析，自然不会派发到任何
路由handler。**这条设计假设本身在协议原理层面是成立的。**

**但这只是"设计意图正确"，不等于"实现会正确"——本次复核不能就此打钩**：
- 本页是"只写方案不落码"，实际探测代码尚未写出来。**落码验收时必须独立确认**：实现真的用的是Node
  `net.connect()`（原始socket，`.end()`/`.destroy()`时不writeAny字节），**不是**任何会发送真实HTTP
  字节的客户端（`fetch`/`http.request`/`axios`哪怕只发`HEAD`/`OPTIONS`——这些**都会**被服务端HTTP层
  解析并派发到路由，即便对应的handler本身"安全"，这仍然是一次真实的应用层请求，跟"纯探测不留痴迹"这个
  设计初衷不符）。
- **一个更细的残留观察点（低风险，非阻断，供实现时留意）**：即便是裸TCP connect，在TCP/OS层面仍然会
  在目标进程留下一次"connection accepted"的踪迹（不是HTTP access log，是更底层的连接层，如果目标
  进程/防火墙/IDS对连接本身做计数或告警，这次探测本身会被看见）——这跟"探测会不会误导目标做出错误
  反应"是两个不同层次的问题：**功能层面（会不会触发业务逻辑）本次判断为不会；观测层面（会不会在目标
  留下痕迹）没有零风险，只是风险极低且通常无害**，如实记录不代为下最终结论。

**结论：设计意图本身经协议原理审查确认合理，但"探测只connect不发请求"这条具体要求必须在实际代码落地
后，我独立读代码/独立跑一次实测确认（比如指向一个真的在监听、且挂了访问日志中间件的测试console，探测
完之后确认访问日志里没有多出一行请求记录）——这次只能给"设计正确"的GREEN，不能替代"实现正确"的GREEN，
两者是分开的验收，落码笔到了我会专门做这条实测。**
