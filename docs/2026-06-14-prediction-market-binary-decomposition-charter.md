# 预测市场统一纲领 — 复杂市场 = binary 分解 + 组合

> **日期**: 2026-06-14
> **来源**: Owner 洞察——"再复杂的游戏都可以拆分成简单的 yes/no，再组合"。Bettor 拆解 Polymarket 真实赛事(荷兰 vs 日本世界杯)实证后成文。
> **性质**: 战略纲领。统一 #25(UMA oracle 能力引擎) + #26(bshard 规模化) 的目标谱系——证明二者正是"复杂市场拆成 binary 后剩下的两个真问题"。
> **守红线**: G5——报机制/范式,非经济闭环。

---

## 0. 一句话

**任意复杂预测市场 = 一组精确的 binary YES/NO 谓词 + 组合层。** 我们的 binary YES/NO 池就是那个普适原语;不需要发明新市场类型。复杂度不消失,它精确地搬到两处:**① 谓词定义 + oracle 判定力(→ #25)** 和 **② 组合 + 多池效率(→ #26)**。

---

## 1. 核心命题:分解是普适的,且是现实

不是理论——**Polymarket 自己就这么做**。它没有任何"原生非二元"市场;一切都是"一个 YES/NO 问题 + 一条判定规则"。实证(2026-06-14 荷兰 vs 日本世界杯整页):

| 表面"复杂"玩法 | 实际 = binary 谓词 |
|---|---|
| 三向赔率(荷/平/日) | 3 个 binary(荷兰赢? / 平? / 日本赢?)耦合,ΣYES≈1 |
| 让分 荷兰 -1.5 | binary "净胜≥2?" |
| 大小球 Over 2.5 | binary "总进球≥3?" |
| 球队进球数 荷 Over 0.5 | binary "荷兰进球≥1?" |
| 双方都进球 BTTS | binary "两队各≥1球?" |
| 谁先进球(荷/日/都不进) | 3 个耦合 binary |
| 角球阶梯 7+/8+/.../14+ | 一排 binary "角球≥N?" |
| 球员进球 Ueda 1+/2+/3+ | binary "Ueda 进球≥N?" |
| 正确比分 / 连续结果 | 拆成一排/分桶 binary(0-0?/1-0?/...) |
| 半场/全场组合 HT/FT | binary,复合谓词(HT=X AND FT=Y) |

**连续结果也普适**:任意标量(总进球数、比分、百分比)拆成阶梯/分桶 binary。代价仅是"很多 binary"(效率,非不可能)。

---

## 2. 玩法归 5 结构类(全部 → binary)

1. **多结果联动**(moneyline / 下半场 / 谁先进) = ΣYES≈1 的耦合 binary 组
2. **线 line-based**(让分 / 大小球 / 球队进球) = binary,谓词带 **线值 + 比较运算**(净胜球 vs 线、总和 vs 线)
3. **阶梯 ladder**(角球 7+…14+、正确比分) = 一排线市场
4. **props 细粒度**(球员进球、BTTS、谁先进) = binary,谓词指向统计级事实
5. **复合 composite**(HT/FT) = binary,多条件谓词

**5 类全部 = binary 池 + 不同的谓词 + 不同的耦合关系。** 市场结构永远是 YES/NO。

---

## 3. 架构推论:binary 池 = 普适原语

- 我们现有的 **binary YES/NO pool(PoolSpine_v07 + PoolSide)就是那个对的原语**。再复杂的赛事 = 已有 binary 池 ×N + 组合。架构方向被 Owner 的分解验证。
- **结算上各 binary 池独立判**——耦合(ΣYES≈1)是显示/定价层,不是结算层。这对池模型反而干净(每个池各自一个谓词、各自 settle)。

---

## 4. 复杂度的去向(诚实的关键)

拆成 binary 后,难的不在"市场结构"(永远 YES/NO),而在两处:

### ① 谓词的精确定义 + oracle 能不能如实回答 → **#25 UMA 引擎**
- "角球≥7?"是傻瓜 binary,但 oracle 要有**角球数据源**才能答。"净胜≥2?"要终场比分+算术。"只算90分钟?"要时间窗。
- **拆成 binary 把所有难度压进了"这个 YES/NO 到底问什么(线值/球员/阈值/时间窗) + 去哪查能如实答"**。
- 这正是 [UMA 规则学习引擎](2026-06-14-NWT-uma-learning-oracle-engine.md)(#25)的活:学"每类谓词去哪个权威源、查什么粒度"。C1(拿真相判分)在这里=每个 binary 谓词必须能被真数据如实判,不能猜。

### ② 组合 + 多池效率 → **#26 bshard 规模化**
- 耦合组(荷/平/日)、阶梯(角球 7+…14+)、连续拆桶(正确比分)= **一个赛事炸出几十上百个 binary 池**。
- 每个池要能扩(押注数无界)+ 几十池并行结算 = 正是 [bshard 滚动分片 + trustless fold](2026-06-14-bshard-fold-trustless-§4-consensus.md)(#26)解的规模问题。
- 组合层(把相关 binary 显示成一个赛事、ΣYES≈1 定价 UX) = 上层封装,不动结算原语。

---

## 5. oracle 能力分层(谓词难度 → 数据粒度)

对应 Owner 钦定"判断能力一档档加":

| 层 | 谓词类型 | 数据需求 | 现状 |
|---|---|---|---|
| **L1** | moneyline / 让分 / 大小球 / 球队进球 | **终场比分 + 算术**(净胜球、总和 vs 线) | **现在就能做**(ESPN extractor 有比分,加算术层) |
| **L2** | BTTS / 谁先进 / 半场胜负 / HT-FT | 半场比分 + 进球明细 | ESPN summary 有,extractor 待扩 |
| **L3** | 角球 / 球员进球 props | 统计级源(角球数、球员进球) | 需专门数据源,UMA 引擎学 |

**洞察**:让分/大小球这类"比分+算术"其实 **L1 就够得着**(都从终场比分推)——是近期高性价比的扩展(一个比分源解锁一大批 binary 谓词)。

## 6. 镜像纪律(Q1 延伸)

拆成 binary 后,镜像(seeder)必须 verbatim 搬**每个 binary 的完整谓词**:类型 + **线值** + 球员/统计目标 + **时间窗** + verbatim 规则 + 源。少搬"线=2.5"或"只算常规时间"= 判错。配 [[project-broker-dm-dual-surface-seeder-supply]] 单源 usable-gate。

## 7. 统一收口

**Owner 的分解把我们两条主线串成一个统一框架**:

```
任意复杂市场
   │ 分解(普适, Polymarket 实证)
   ▼
一堆精确 binary 谓词  +  耦合/阶梯/分桶关系
   │                          │
   ▼ 每个谓词要被如实判        ▼ 几十池要能扩+并行结
 #25 UMA oracle 能力引擎     #26 bshard 规模化
 (谓词→源→判定力分层)        (单池无界 + 多池 fold)
```

再复杂的赛事,对 KANet 都是:**定义一堆精确 binary 谓词 → 各自一个 binary 池(#26 让它无界+并行) → oracle 逐个如实判(#25 让它判得对)**。binary 池是地基,#25 和 #26 是地基之上仅剩的两个真问题。
