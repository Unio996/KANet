# faucet_grants 卡住的 `pending` 行 — operator 处置流程

**适用范围**：`faucet_grants` 表里长期停在 `status='pending'` 的行。
**为什么会有这种行**：发放流程先写一行 `pending` 作为原子预留，再去转账，成功后改 `sent`。
若转账**结果无法确定**（relay 没返回 txid / 抛异常 / 进程在两步之间被重启），那一行**故意**留在 `pending`。

🔴 **它留在 `pending` 是设计,不是残留** —— 它同时承担两件事：
1. 记录"这笔钱**可能**已经出去了"；
2. 挡住同一钱包重复领取（`wallet_address` 上有 UNIQUE）。

---

## 🔴 第一条规矩：不许批量清

**绝不要**"把所有 pending 一次性删掉/改成 failed"。
两类 `pending` 在表上**长得一模一样**，而它们的正确处置相反：

| 类别 | 钱 | 正确处置 |
|---|---|---|
| ① 转账结果不明（relay 说不清） | 🔴 **可能已经付了** | 查链后再定 |
| ② 预留之后、转账之前进程被重启 | ✅ **确定没付** | 查链后释放 |

🔴 **表里没有任何字段能区分这两类** —— `status`、`txid`、`granted_at` 三者在两类上取值相同。
⇒ 所以**不能靠读库判断**，只能**逐行问链**。

---

## ✅ 判据：问链，不问库、不问信号

对每一行 `pending`，问的问题是：

> **这个 `wallet_address` 在链上到底收到没收到？**

🔵 这条判据的好处是它**对两类都成立** —— 它不问"我们发了没有"（那件事我们答不了），
它问"它到了没有"（那件事链上答得了）。

### 🔴 而现成的那条查法**用不了** —— 它按 txid 查,而卡住的行**恰恰没有 txid**

本仓既有的链上验证通道 `check_utxo_landed` 是**按 txid** 查的。
🔴 而一行之所以卡在 `pending`，正是因为**没拿到 txid**。⇒ 这条现成的路在这里**结构上走不通**。

### ✅ 替代判据（三层,一层比一层硬）

| 层 | 问的问题 | 强度 |
|---|---|---|
| ① 地址 | 这个 `wallet_address` 在时间窗内有没有入账？ | 🔴 弱 —— 别人给它打钱也算 |
| ② 地址 + 金额 | 入账金额是否 ≈ 本次发放额？ | 🟡 **必要不充分** —— 同一地址可能有别的入账 |
| ③ **+ 发放方** | 🔵 那笔候选 tx 的**输入**里，有没有属于 **faucet 发放地址**的？ | ✅ **强** |

🔵 **③ 才是判据**：我们知道币是从 faucet 的发放地址出去的。
「**从我们的发放地址进到这个钱包**」比「这个钱包收到了一笔约等于该金额的钱」强一个量级 ——
因为别人给这个地址打钱**不会**带上我们的发放地址作为输入。

🔴 **不要**拿 `kaspa_tx_log` 当判据 —— 本仓已记死：它命中不证明仍在 canonical 链，未命中也不证明不存在。

### 🟡 它能答什么、不能答什么（写死,免得被做成自动的）

- ✅ **能答**：这个地址**有没有**从我们这里收到过一笔 —— 这就是 operator 定 `sent`/`failed` 的依据。
- 🔴 **不能答**：当同一地址在历史上有**多笔**来自我们的入账时，**这一笔对应的是哪一行**。
  ⇒ 历史遗留的 stuck 行仍需**人工确认那一笔的来源**；而本次修复之后**新产生**的 stuck 行没有这个歧义
  （每个钱包最多一行）。
- 🔴 ⇒ **不要把它做成全自动的**。做成自动的那一天，它会在历史行上判错。

---

## 🔴 时间下限：必须等够,否则会把"已广播未确认"读成"没收到"

🔴 **「链上现在没有」≠「永远不会有」**。一笔刚广播、还没被接受的 tx，查出来同样是"没收到"。
⇒ 在该行 `granted_at` 之后**未满足确认窗**之前，**不许**判定为"没付"。

⚠️ 具体等多久，取决于当时的确认深度口径 —— **查当时的实际 DAA 进度，不要用记忆里的数**。
本仓已记死：判 DAA 差值必须每次用新鲜 tip 精确算。

---

## 🔴🔴 判 `failed` 是这里唯一**不可逆**的动作 —— 它的前置单列（NWT 2026-07-29 审出）

其余三种处置都可逆或无副作用；而 `failed` 会**释放配额** ⇒ 那个钱包可以**再领一次** ⇒
🔴 **若原来那笔其实会确认，就是双领。**

### ✅ ③ 层查的是什么：**只查【已确认】,不含 mempool**（定死,不是取舍）

```
🔴 原稿【没定义】这一层 —— 而"已确认 UTXO"与"含 mempool 的待确认"对同一个状态给出相反读数
✅ 定死: 【只查已确认】。两条理由:
   ① 已确认收到 ⇒ 判 'sent' ⇒ 🔵 钱确实到了, 这个判断安全
   ② mempool 里卡着 ⇒ 读成"没有" ⇒ 而"没有"的动作是【什么都不做】(见下), 不是 release
      ⇒ 🔵 于是"mempool 卡单被误判"这条路【不通向任何动作】, 危害为零
🔴 而【含 mempool】反而更坏: 未确认的会被判成 'sent'
   ⇒ 用户被记成【收到了他没收到的钱】, 且从此被挡住 ⇒ 既错记又挡人
```
🔵 **注意这条定死之所以安全，是因为下面那条（不产生 `failed`）先成立。**
两条是一对：单独把 ③ 层定成"只查已确认"而仍保留 `failed`，就会重新打开双领那条路。

### 🔴 ⇒ 结论：**本流程今天不产生 `failed`。** 它只能把 `pending` 变成 `sent`。

要让 `failed` 安全，需要证明**那笔付款永远不会发生** —— 而这是一个**无法证明的否定**。
🔴 而"再等久一点"**不解决它**：时间下限只降低概率，**不改变性质**。

⇒ **所以处置矩阵里没有 `failed` 这一行。**
满足了时间下限而链上仍然没有 ⇒ 🔴 **仍然什么都不做，保持 `pending`。**

🟡 **代价要写清、也要接受**：那个钱包**被永久挡住**。
🔵 而这是**对的取舍** —— 这是测试币的 faucet：**挡住一个钱包的代价，远小于双领**。
🔨 **用户面的出路是【换一个钱包地址】**，不是把闸放开。

### 🔴 而"释放配额"只以 **override** 的形式存在 —— 它**不是矩阵里的一行**

🔴 **允许 release 的条件是【判据】,不是【像不像下面那两个例子】** —— 判据见本节末尾那张表
（**源头证否**才算数；举例只是示例，将来出现没人想到的证据形态，**拿那条判据一量就知道算不算**）。

满足判据时，才允许人工 release，而形态固定为：

```
operator 明确写下【为什么他认为这笔永远不会到】+ 署名 + 时刻 ⇒ 才允许 release
```

🔴 **它之所以不写进矩阵**：矩阵里的行**会被照着执行**，而这一条**必须每次都重新想一遍**。
🔵 二者的区别是：**一条规则会被当成手续走完；而一次 override 会留下一个人的判断。**

### 🔴🔴 而"想的那一遍"要想什么：**只接受【源头证否】,不接受【末端证否】**

| 证法 | 例子 | 会不会翻 |
|---|---|---|
| ✅ **源头证否**（证明**我们没发**） | relay 进程当时根本没起来（日志可证）· 发放地址在那个时间窗内**零出账**（链上可证） | ✅ **不会翻** |
| 🔴 **末端证否**（证明**它没到**） | 「链上现在查不到这个地址收到过」 | 🔴 **会翻** —— mempool 卡单后确认，读数就变了 |

🔴 **override 只接受源头证否。**
🔵 因为要 release 就是在断言"这笔永远不会到"，而**只有源头那一侧能给出不会翻的证据**：
末端的"现在没有"永远只是**此刻**的读数。

🔨 ⇒ 一句话记法：**想的是「我们发没发」，不是「到没到」。**

### 🔵 而这一格的来历值得记（它是本次修复的那个 bug 从恢复流程重新进来）

本次修复堵的正是"**在不确定的情况下发第二笔**"。
🔴 而 `failed + 释放配额` 是**同一件事换了个入口**：它在恢复流程里重新打开了那扇门。
🔴 它特别容易漏，因为**恢复流程看起来是在收拾残局，不像是在动钱**。

🟡 **顺带一格未核**：本仓现有的链上查询通道**能不能读 mempool**，我没核过。
它不影响上面的结论（因为我们本来就不判 `failed`），但它会影响将来若要做 override 自动化时的判据强度。

## ✅ 处置矩阵（逐行,不批处理）

🔴 **三行,没有第四行。**（原稿有一行 `failed + 释放配额` —— 已删，理由见上节）

| 链上查询结果（**只看已确认**） | 处置 |
|---|---|
| **收到了** | `status='sent'`，并补上实际的 `txid` |
| **没收到** | 🔴 **什么都不做**，保持 `pending` —— 🔴 **无论时间下限满没满** |
| 查询本身**失败** | 🔴 **什么都不做** ——「查不到」与「没收到」是两个读数，别合并 |

🔵 **注意"时间下限"这一维从矩阵里消失了**：原稿用它区分"再等等"与"可以判 failed"，
而拿掉 `failed` 之后，那两条分岔**通向同一个动作**（什么都不做）⇒ 这一维不再改变任何处置。
🔴 它仍然写在上面那节里，因为它解释**为什么等下去也不会变成 `failed`** —— 但它**不是**矩阵的输入。

### 🔵 配额:`pending` 计入,而它不会被本流程释放

那三个上限（per-wallet 永久一次 / per-IP 24h / 全局日帽）在计数时**把 `pending` 也算进去** ——
这是对的：`pending` 代表"可能已经花出去的钱"，一个忽略它的上限不是上限。

🔴 而本流程**不释放配额**（因为它不产生 `failed`）。
释放只经上节那条 **override**：写下理由 + 署名 + 时刻。

🔴 具体做法（删行 / 加排除条件 / 改计数口径）**由实现时决定并写进 migration 或查询**——
本文件只规定**它必须被一起处理**，不规定用哪种手段。

## 🟡 已知的残留(诚实标出,不假装闭合)

- 🔴 **本流程是人工的**。没有任何东西会自动发现卡住的 `pending` 行。
  ⇒ 谁来定期看、多久看一次，**尚未指定**。在指定之前，一个卡住的钱包会一直卡着。
- 🟡 **类② 的窗口大小未测**。它取决于"预留写入"到"转账返回"之间的实际耗时，而那个耗时没有埋点。
- 🔵 而根治方向（让 relay 在**可证没提交**的路径上返回一个结构化字段）是**另一个域的改动**，
  需要单独报备审核；在它落地之前，本流程是唯一的出口。
