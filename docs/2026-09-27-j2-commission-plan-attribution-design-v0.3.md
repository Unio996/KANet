## ③.1 归因链接格式——改为"逐级转发追加地址"（重写）

### 链接格式

```
https://<结账页域名>/checkout?q=<quote_id或完整报价>&ch=<addr1>[,<addr2>[,<addr3>[,<addr4>[,<addr5>]]]]
```

`ch` 参数是一个**逗号分隔的地址列表，最多 5 个**——对应 D-034 §8"链接逐级转发时追加渠道地址"：

- **第一个渠道**（比如商家自己发的邮件里的初始归因链接）分发时，`ch=<渠道1地址>`（1 个地址）。
- **第一个渠道的受众如果继续转发**（比如渠道 1 是个博主，读者又转给朋友，且这个转发本身也算一次归因——具体业务场景是否允许"二次转发算数"由商家在报价里用 `channel_2` 槽位的 `bps` 是否 >0 决定，bps=0 等价于"这个槽位不参与分润，纯粹上限占位"），转发时**在末尾追加**自己的地址：`ch=<渠道1地址>,<渠道2地址>`。
- 以此类推，最多追加到 5 个地址：`ch=<渠道1>,<渠道2>,<渠道3>,<渠道4>,<渠道5>`。

### 顺序规则（写死，不含糊）

**链接里地址出现的顺序 = 渠道槽位编号**（第 1 个地址 → `channel_1` 槽位，第 2 个 → `channel_2`，以此类推）。顺序在链接生成的那一刻就已经确定（每次转发只能**追加到末尾**，不能插队、不能改写前面已有的地址）——这与"地址列表 + 顺序"共同构成 ctor 的确定性输入（§6.4），任何人篡改顺序会得到一个**不同的订单地址**，跟即时分账/单渠道版本"篡改归因会改变地址"的论证是同一个机制的直接推广，不是新发明的安全性质。

### 去重规则（写死，防同地址多次占位蹭佣金）

**同一个地址在一条链里出现多次，只按第一次出现的位置生效，后续重复出现的位置视为空槽位**（不会让同一个地址占用两个槽位、拿两份佣金）。例如 `ch=A,B,A,C` → 实际生效 `channel_1=A, channel_2=B, channel_3=(空，第二次出现的 A 被当作没填), channel_4=C`——`channel_3` 走"未填槽位"折算路径（§6.4）。**去重判断在 SDK 解析链接参数时做**（不是等广播到链上才发现），去重后的槽位映射结果就是喂给 ctor 的最终输入，这一步本身也是确定性函数（同样的原始链接，任何人独立解析得到同样的去重结果）。

### 上限规则

第 6 次追加（试图凑出第 6 个不同地址）**结构上不可能被接受**：结账页/SDK 在解析 `ch` 参数时如果发现超过 5 个（去重后）地址，**拒绝构造订单**，明确报错"最多 5 个渠道槽位"——不是静默截断前 5 个（截断会让用户以为归因生效了但实际上第 6 个渠道拿不到钱却不知道），是直接拒绝让调用方知道链接本身已经不合法，需要上游修正（同 §6.1 真实 mass 上限——6 渠道场景真实测量 mass=700,078，远超硬上限，不存在"勉强放行"的空间）。

## ⑥ 放宽

### 6.1 N 收款方——按同时在场渠道数分档的最低额（真实测量，替换 v0.2 单一常量）

**根因（本轮新发现，Owner 定多渠道后才会暴露）**：v0.2 的 `MIN_RECIPIENT_SOMPI = 10,000,000`（0.1 KAS）是在"至多 1 个渠道"的假设下定的运营下限。Owner 定多渠道（最多 5 个）之后，**这个常量不再安全**——真实测量：`商家 + 5 渠道(各 0.1 KAS) + 找零(0.1 KAS)` 这个 7 输出的最坏情形，`mass=600,067`，**超过网络硬上限 500,000**（`kasia-relay/src/lib/tx-mass-ub.mjs` 真实估算，非推算）。用同一个固定常量不管当次有几个渠道在场，在 5 渠道场景下会产出结构上不可能广播的交易。

**修复：最低额按"当次实际可能同时在场的渠道数"分档**，真实二分搜索（目标：`商家 + N 渠道(各等于该档最低额) + 找零(同等于该档最低额)` 这个最坏情形的 mass ≤ 400,000 安全预算）：

| 同时在场渠道数 N | 每渠道最低额（真实二分搜索） | 该档最坏情形 mass |
|---|---|---|
| 1 | 5,000,176 sompi（≈0.050 KAS） | 399,999 |
| 2 | 7,500,469 sompi（≈0.075 KAS） | 400,000 |
| 3 | 10,001,101 sompi（≈0.100 KAS，与 v0.2 旧常量巧合接近） | 399,997 |
| 4 | 12,502,032 sompi（≈0.125 KAS） | 400,000 |
| 5 | 15,003,751 sompi（≈0.150 KAS） | 399,995 |

**数值规律（供实现参考，不是替代真实测量的公式）**：每档最低额 ≈ `2,500,000 × (N+1)` sompi（`N=1`→5,000,176≈2.5M×2；`N=5`→15,003,751≈2.5M×6，五档全部落在此规律的 0.5% 误差内）——这个近似式**只用于 SDK 给用户的即时提示/UI 展示的快速估算**，**真正的准入判据永远是 `validateQuoteMassFeasibility` 对当次报价实际配置跑一遍真实 `tx-mass-ub.mjs`**（同 v0.2 §6.1 的既有纪律："不存在可以安全略过真实模拟的经验法则"，本轮再次验证这条纪律的必要性——如果只按近似公式发运营指导、不做真实校验，5 档的真实数字之间仍有 ±0.5% 的量测噪声，边界情形可能因为这几千 sompi 的误差从"安全"变"超限"）。

**SDK 常量**：`MIN_RECIPIENT_SOMPI` 从单一常量改为函数 `minRecipientSompiForConcurrentCount(n)`（查表或按上述近似式起草，第一步实现时用查表，五档都是真实测过的，不需要在 5 个档位之外做任何推断——超过 5 档的场景本来就结构上不允许，见下方）。

**`validateQuoteMassFeasibility` 更新**：不再按"报价里配置了几个渠道槽位"动态决定测哪个 N，统一按**满编 5 槽位、全部归因、不折算**的最坏情形跑真实校验（即使某份报价的商家只想开放 2 个渠道槽位，也建议按 5 槽位的更严格预算测——如果商家确实只想用 2 个槽位，报价里就不声明 `channel_3`/`channel_4`/`channel_5` 这三个角色，`fullyUnfoldRoles` 自然只展开报价里实际写出来的槽位数，不会凭空多测未声明的槽位；"5 槽位"是**上限**不是"每份报价都必须用满"）。

**6 渠道场景确认结构性不可行**：真实测量 `商家+6渠道(各0.1KAS)+找零` mass=700,078，远超硬上限——这是 D-034 §8"每单最多 5 个"这个 Owner 裁定在数字上的直接印证，不是巧合，是**5 这个数字本身就是从 mass 约束反推出来的合理上限**（第 6 个渠道在任何金额分布下都会显著推高 mass，5 已经是"仍能给出有意义最低额"的上限，第 6 个只会让每档最低额进一步升高到不实用的程度）。

### 6.4 渠道槽位与未归因份额并入指定方——定稿（合并 v0.2 §6.4a/§6.4b，Owner 已选定多渠道方案）

**报价示例**：

```json
"canonical_rules": {
  "schema_v": 1,
  "roles": [
    { "name": "provider",   "bps": 7000, "address": "..." },
    { "name": "broker",     "bps": 500,  "address": "..." },
    { "name": "channel_1",  "bps": 900,  "fold_to": "provider" },
    { "name": "channel_2",  "bps": 700,  "fold_to": "provider" },
    { "name": "channel_3",  "bps": 500,  "fold_to": "provider" },
    { "name": "channel_4",  "bps": 300,  "fold_to": "provider" },
    { "name": "channel_5",  "bps": 100,  "fold_to": "provider" }
  ]
}
```

（示例用递减比例——第一个转发者拿更多，鼓励原始推广而不是链条末端搭便车；这是商家的业务选择，不是协议强制，槽位也可以配等额 `bps`，或者只声明 `channel_1`/`channel_2` 两个槽位——报价里没写的槽位视为该报价不支持这么多层转发，链接构造工具应据此拒绝第 3 次转发追加地址。）

**`resolveRulesForOrder` 重写**：

```js
function resolveRulesForOrder(quote, channelAddrs /* 去重+截断后的有序数组, 长度 0-5 */) {
  const roles = quote.canonical_rules.roles.map(r => ({ ...r }));
  for (let i = 0; i < 5; i++) {
    const slotName = `channel_${i + 1}`;
    const role = roles.find(r => r.name === slotName);
    if (!role) continue; // 报价本身没声明这个槽位, 跳过(报价可以只开放 1-4 个槽位)
    if (channelAddrs[i]) {
      role.address = channelAddrs[i];
      delete role.fold_to;
    } else {
      // 这个槽位报价里声明了, 但这条链没填到这一位(链更短, 或去重后这一位变空)
      const target = roles.find(x => x.name === role.fold_to);
      target.bps += role.bps;
      roles.splice(roles.indexOf(role), 1);
    }
  }
  return { schema_v: quote.canonical_rules.schema_v, roles };
}
```

`channelAddrs` 是 SDK 解析链接 `ch` 参数后，**先去重（同地址只保留第一次出现的位置，后续重复位置置空）、再按声明的槽位数截断**（如果报价只声明了 `channel_1`/`channel_2`，链接即使带了 5 个地址，第 3-5 个地址不产生任何效果，对应份额本来就没有对应的槽位角色存在）的最终结果——这一步本身是确定性函数，任何人拿同一条原始链接 + 同一份报价都能独立算出同一个 `channelAddrs`，进而算出同一个订单地址（§3.2 论证的直接推广）。

**防蹭（D-034 §8 关切，本轮明确写清）**：

链接转发机制本身**无法在协议层验证"这次转发代表了真实的推广行为"**——任何拿到链接的人都可以在转发前把自己的地址追加进去，不管有没有做任何实际的推广工作。这个风险在**两种报价配置下处理方式不同**：

- **`require_channel_deposit: false`（默认）**：**这个风险被直接接受，是商家的知情选择**——报价默认不要求押金，等于商家自己判断"这份佣金预算允许无门槛的自由转发，蹭一点也无所谓"（同 D-034 §8"默认不要求、保持拿来即用"的产品取舍）。协议本身**不承诺**"渠道预算只会流向真实推广者"，只承诺"归因链接确实决定了钱怎么分、不能被结账页悄悄改"——这是两个不同层次的保证，不能混为一谈。
- **`require_channel_deposit: true`**：每个想要拿到某个渠道槽位份额的地址必须有一笔活押金（§7）才算"有效归因"（没有活押金的槽位视为未填，走折算路径）——蹭佣金因此**不再免费**：攻击者可以往链接里塞任意多个自己控制的地址，但每一个要真正拿到钱都得先押 1 KAS（且必须持续押着，见 §7.3），把"蹭"的边际成本从 0 提高到有意义的资金门槛。**这仍然不能防"攻击者自己有钱、愿意押"的情形**（同任何 POW/押金类防女巫机制一样，只筑门槛不做身份验证），但至少不再是零成本攻击。
- **去重规则本身也是一道免费的防线**：同一个地址在链里重复出现只算一次（本节 §3.1 已定），这堵住了"同一个人把自己的地址塞好几次企图拿好几份"这种最粗暴的蹭法——不需要押金也能挡住，因为这是纯粹的**链接解析规则**，不依赖任何链上机制。
