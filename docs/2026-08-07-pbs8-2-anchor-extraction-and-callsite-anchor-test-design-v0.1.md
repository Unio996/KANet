## 1. (a) 锚点判定【首次实装】为单源纯函数

**新文件**: `kasia-console/src/lib/pbs8-2-signreq-anchors.mjs`(镜像 `src/lib/refund-authorization.mjs` 的角色)。

> 🔴 **v0.2**: 本节标题原为「锚点判定**提取**」——**没有可提取的原件**(见顶部变更块)。
> 这是**首次实装 + 一开始就落在单源位置**,好处仍在(可独立调用、不复刻),但**它是新增判定,不是搬运**。

**导出**: `evaluateSignReqAnchors(input) -> { ok: boolean, reason: string|null, code: string|null }`

- **纯函数**: 不读 DB、不发 RPC、不写日志、无副作用 —— 所有外部事实由 `input` 传入。
- `handlePoolOracleTxSignReq` 改为: 组装 `input` → 调本函数 → `if (!res.ok) { console.warn(res.reason); continue; }`。
  🔴 **v0.2 更正**: 本行原写「**判定条件本身一个字节不变,只是从 inline 变成被调用**」——
  **那句话是错的,它假设了一个不存在的原实现**。实况: handler 今天在这个位置**没有任何锚点判定**,
  本改动是**在签名前新增一道拒签闸**。**⇒ 这也正是 D4 那条闸要看的东西(§5.3)。**

### 1.1 🔴 `input` 里"链上值取不到"必须是【值】不是【异常】

```js
// 🔴 落码硬约束(2026-08-07 R9 扫射咬出): chainSpineValue 取不到时传 null, 不许抛。
//   理由: 若建模成抛异常, 用例只能断言"它抛了", 而【抛异常】与【离线环境本来就没有 RPC】
//   在离线下读数完全相同 ⇒ §0 那堵"恒真"墙原样复活, ④ 第一项(RPC 错)白做。
//   ⇒ "取不到"与"没去取"必须在类型层面就是两个不同的东西。
```

⇒ `input.chainSpineValue: bigint | null`,`null` ⇒ `{ok:false, code:'CHAIN_VALUE_UNAVAILABLE'}`
(= @Bettor R2 今日裁定的 `cannot-verify ⇒ 弃权不签、不回落`,**本函数只产出拒绝,永不产出授权**)。

## 2. 必答一 —— 判据(v0.2 重写)

### 🔴 2.0 v0.1 那三条里,两条【整格删除】,不是打折

v0.1 写的是「抽前抽后**行为零变化**」的三条判据。**没有原实现 ⇒ 前两条无对象可核,删除:**

- ~~① 条件逐字相同(比较运算符/边界值/and-or 组合逐字节)~~ ⇒ **删**:没有"抽前"那一份可比。
- ~~② 分支全覆盖(原每条 `return;`/`continue;` 都有对应返回值处理)~~ ⇒ **删**:handler 里根本没有这些分支。
- ✅ ③ **注入实验仍成立且更重要**(见 2.2)。

🔨 **这里不许做的一件事**: 把「行为零变化」**降级**成「行为变化不大」继续留着 ——
**这条判据的价值全在"零"这个字上;失去对象就该删掉,而不是稀释成一句谁都能签的话。**

### 2.1 取而代之: 这是【新 enforce】,判据按新 enforce 的标准写

1. **每条拒签条件必须能指出它拒的是哪一类构造**,且该构造有一条**阴性用例**(六项见 §4)。
2. 🔴 **必须给出"这条新拒签会拒掉多少【真实历史请求】"的实测**——
   拿本机 159 个带 `phase2_tx_obj` 的历史市场**离线重放**这三条判定,**报出会被拒的条数**。
   **这是 D4 那个"弃权率"担心的直接读数,不是估计。**(方法与 2026-08-07 §11.3 下界实测同款。)
   ⇒ **若该数 > 0,必须逐条解释每一条为什么被拒**(是实的坏,还是判定过严)。
3. **fail 方向必须是"拒签"不是"放行"**:任何读不出/解析不了/取不到 ⇒ 拒(fail-closed),
   且与 §1.1「取不到是值不是异常」一致。

### 2.2 注入实验(v0.1 第三条,保留并升为主判据)

把落码后的判定函数里**任意一条边界值改一格**(如 `90n` → `89n`),**对应用例必须变红**。
⇒ 证明用例实的在读这个函数的判定,不是在读别的东西。**还原后逐字节相同**,两次读数都进证据日志。

> ⚠ **本节证的是"这些拒签条件按写的那样生效",不是"这些条件是对的"** —— 条件本身的正确性由 §11.1-11.3 各自的红队负责,不在本稿射程。

## 5. 已知不覆盖 / 弱点(如实,不说满)

1. 🔴 **阳性臂做不成**: 本形态证的是「**该拒的被拒了**」,**证不了「该签的签得出来**」——
   阳性臂要真 relay,离线跑不完。**与 ⑤ 同一格天花板,不是本稿新引入的**(NWT 06:35 认)。
   ⇒ **落码后不许出现"签名闸已验证"这类措辞**,只能说"六类坏输入各自被拒,且拒绝来自本函数"。
2. **三锚点的性质不变**: 按 Codex v4 硬边界,它们**永远只是拒绝信号**,全过 ≠ 可以安全签名。
   本稿只改**可测性**,**不改变**任何一格覆盖范围。
3. 🔴 **D4: 已由 @NWT 06:52Z 重判为【适用】(原判 06:35Z 撤回)——其前提被 v0.2 撤销。**
   NWT 06:35 判 D4 **不适用**,理由逐字是「**纯提取…判定条件本身一个字节不变…弃权率不会因此改变一分**」。
   **而 v0.2 确认这是【首次实装三条新拒签条件】⇒ 弃权率必然上升 ⇒ D4 按其字面适用。**
   ⚠ D4 现状 = **不解除,条件解除**(补 (c) 那条测试 + 冻结积压出清机制之后由 @Bettor 重裁)。
   ⇒ **本稿不自裁,也不假定它会被判为不适用;§2.1 第 2 条那个"会拒掉多少历史请求"的实测,
   正是为了让重判有读数可依,而不是靠各方对"会不会提高弃权率"的印象。**
4. 🔴 **第三层完全不在本稿射程 —— input 组装的正确性(NWT 06:47 独立审补,PASS 的附带要求)**:
   (a) 证的是「**提取出的判定函数正确**」,(b) 证的是「**handler 调了它**」;
   **两条加起来仍【不证明】喂给它的 `input` 是不是从链上正确读出来的。**
   ⚠ 而现状更靠前一格: **这三个锚点本身今天都还没落码**,`chainSpineValue` 这类字段的
   **输入组装代码尚不存在**(NWT 现读 `trade-protocol-filter.js:541` 起确认)。
   ⇒ **本稿是"判定层 + 调用层"的可测性方案,不含"取数层"**;取数层错(读错 outpoint、
   读到陈旧快照、单位搞错)时,**(a)(b) 全绿而结论全错**。
   🔨 **落码时必须同时成立的措辞纪律**: 用例全绿只能说
   「**六类坏输入各自被这个函数拒了,且 handler 实的调了它**」——
   **不许说「锚点检查已验证」,更不许说「签名前的输入已校验」。**
