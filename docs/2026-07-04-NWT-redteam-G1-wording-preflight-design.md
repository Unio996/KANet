# NWT 红队快审 — G1 世界杯措辞 pre-flight 设计（Bettor 2026-07-04 稿）

> 审对象：`docs/2026-07-04-worldcup-G1-market-wording-preflight-design.md`。Owner+Bettor 要求快审，7/8 go/no-go 前必须过。
> 裁决：**CONDITIONAL GO — 2 BLOCKING（决赛/季军赛措辞缺口 + pre-flight gate 定义危险模糊）+ 2 项需澄清**。核心思路（advance vs win 消歧、pre-flight 三项闸、cron 自动开盘）站得住，两条 BLOCKING 都是"漏了一类比赛/一个定义"，不是方向错。

## 🔴 BLOCKING-1：决赛(7/19)和季军赛(7/18)套用"advance"模板在语义上不成立

§1.1 模板问的是「{A} 能晋级下一轮吗」——这句话隐含"存在下一轮"。但 §3 赛程列了 **季军赛(7/18)和决赛(7/19)**，这两场都没有"下一轮"：
- 决赛：赢了就是冠军，不是"晋级"，这场比赛的正确问法本来就该是 §1.2 的"夺冠"句式（且 §1.2 明确说 win 无歧义可用），但 §1.2 只覆盖赛前的"长线冠军盘"（16 队各一个），**没有覆盖决赛当天、决赛两队确定后的单场盘**。如果 §3 的自动开盘 cron 对"决赛"这场比赛也无脑套用 §1.1 模板，会产出「巴西能晋级下一轮吗」这种没有下一轮可晋级的荒谬问题，用户会把它按"能不能夺冠"理解，但模板里写的"点球晋级也算 YES"这套加时/点球语义是为半决赛及以下设计的，跟"夺冠"问题混在一起会产生歧义。
- 季军赛：这场比赛纯粹是名次赛，两队都已被淘汰出冠军争夺，说"晋级"完全说不通（晋级到哪里？没有下一轮）。正确问法应该是「{A} 会赢得季军赛吗」/ "Will {A} win the 3rd place match?"（这场没有"advance vs win"的歧义问题，因为没有下一轮可指代，win 就是唯一终局，跟决赛同理）。

**修法**：§1 需要补第三个模板（决赛/季军赛专用："{A} 会赢得决赛/季军赛吗" win 句式），并且 §3 的自动开盘逻辑必须按 `stage` 字段区分：`stage ∈ {16强,8强,4强}` 用 §1.1 advance 模板，`stage ∈ {决赛,季军赛}` 用新模板，不能让 cron 无差别套用同一个模板函数。这是个"漏了 schedule 里两行数据对应的分支"的具体缺口，不是方向问题。

## 🔴 BLOCKING-2："逐字核对"这个 pre-flight gate 定义模糊到会把自己的每一盘都拦下

§2.1 写"镜像源 resolution criteria 原文与我方 description **逐字核对**"。但我方模板是**故意**用"advance/晋级"而不是镜像源大概率使用的"win/获胜"措辞（§1.1 命门那段自己讲的道理）——如果这个 pre-flight 检查真的按字面文本比对（"逐字"这个词面意思就是字面匹配），我们自己精心设计、故意跟镜像源措辞不同的模板，会在自己设的 gate 上**每一盘都不通过**，因为我方 description 的字面文本本来就跟镜像源不一样。

这不是吹毛求疵——这行字要么：
(a) 实际想说的是"resolution **逻辑**核对"（同一场比赛、同样的赢家判定规则在两边映射一致，包括点球晋级算不算数），字面用词写错了；
(b) 或者真的是字面比对，那这个 gate 从第一天起步就会 100% 拦截所有盘，团队会在 7/8 前的关键窗口里发现"gate 一直红，没人能建盘"，然后手忙脚乱临时改。

**修法**：J2 落码前必须先把这句话改成机器可判的精确定义——具体是比对哪几个字段/属性相等（比如：同一场次 matchId、同一个 resolution 事件源、点球晋级归类是否一致），不能留"逐字"这种自然语言留白让实现者自己猜。这条如果不澄清，是本设计里唯一一条**如果直接照抄字面去实现会当场把整个开盘管线堵死**的条款，必须在 J2 动手前钉死。

## 🟡 需澄清-1：赛程 config"人工录一次"跟淘汰赛靠上轮结果产生新对阵矛盾

§3"赛程配置：一张 schedule config，人工录一次赛程真相"——但 8 强/4 强/决赛/季军赛的**具体参赛队伍**要等上一轮结果出来才能确定（这是淘汰赛赛制的本质，不是我们能控制的变量）。如果这张表真的是"录一次"（一次性静态录入），8 强及以后的行在录入当下根本填不出真实队伍名（只能填"胜者A vs 胜者B"这种占位符，不是 `{matchId,teamA,teamB,...}` 要求的确定队名）。

设计没写清楚：谁、在什么时间点、把占位符换成确定队名？如果没人负责这一步，自动开盘 cron 在 kickoff-24~48h 触发时，8 强场次的队伍字段可能还是占位符，开出来的盘题干里 `{国家A}` 插值会插出乱码或空值。这不是阻塞级问题（可以简单地"上一轮结果出来后由人工/上一轮 close 逻辑联动更新下一轮 config"来解决），但设计文档目前完全没提这一步，落码时如果漏了会在 8 强开盘那天现场炸。

## 🟡 需澄清-2：cap≤900 卡的是"参与人数"还是"payout 叶子数"，两者不等价

§4"每盘创建带参与上限 cap≤900（防 1024 payout 硬顶）"——covenant 层真正的硬顶是 **winner 的 merkle 叶子数**（`merkle_index < 1024`，见 `PayoutShard.sil`），不是"参与人数"。如果一个用户可以对同一场比赛下**多笔**注（多笔 = payout 时是多个独立叶子，每笔押中都要在 merkle 树里占一个 index），那么"900 个不同参与者"完全可能对应远超 900 个 winner-slot（900 人 × 平均每人 2 笔 = 1800，直接击穿 1024）。这条 cap 存在的唯一目的就是防 1024 硬顶，如果它实际卡的维度（人数）跟需要防的维度（叶子数）不是同一个东西，这个 cap 形同虚设——落码时必须先钉死：cap 到底限制"distinct bettor 数"还是"distinct bet(叶子)数"，如果一个用户能下多笔，cap 必须按叶子数算，不能按人数算。

## 我打了但没打穿的部分

- **advance vs win 消歧本身**（§1.1 核心命门）：这条道理站得住，我找不出比"点球晋级但没人赢 90 分钟"更刁钻的反例，语言学上 advance 确实是唯一干净的二元问法。
- **deadline = kickoff+4h 的时间预算**（90+30 加时+点球+判定缓冲）：120 分钟留给点球+判定缓冲，对这项赛事的正常流程够用，没找到会被现实赛程打破的场景（除了下面这条，但那是另一个维度的问题）。
- **kickoff 时间万一延期，deadline 要不要联动**：这条我原本想作为 BLOCKING 提，但世界杯官方赛程极少发生开球时间大幅推迟（不像天气敏感的赛事），且即使发生，deadline 定得比 kickoff 晚 4 小时本身就有一定缓冲空间；真正该管这条的是 G7（judge 延迟/时机扫描）的职责范围，本设计只要在落码时留一个"deadline 校验点读的是最新 schedule config 里的 kickoffUtc 而非开盘那一刻的快照"这种小心思即可，不构成本设计独立的阻塞项，标记为观察点转给 G7/落码者留意即可。

## 结论

方向站得住，两条 BLOCKING 都是具体缺口（漏了两类比赛的措辞分支 + 一个定义模糊到会自锁的 gate 条款），修起来都不大但如果不修会在 7/8 前现场炸。CONDITIONAL GO：BLOCKING-1/2 在 J2 落码前必须先在设计文字里钉死，不需要推翻整体方案重新设计。
