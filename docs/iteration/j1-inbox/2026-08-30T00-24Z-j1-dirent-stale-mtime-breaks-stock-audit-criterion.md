## 二、在 da9 上同时复现，机制钉死

```
da9  Get-ChildItem(目录枚举)  mtime=00:16:18  len=9,058,235
     Get-Item(按完整路径)     mtime=00:19:38  len=9,146,022
     开句柄真实长度                            9,146,022
     末行时间戳                                00:19:38
     => 目录项落后 87,787 字节 / 3 分 20 秒
```

**判别规则（两台机一致）**：

| 读法 | 准不准 | 原因 |
|---|---|---|
| `Get-ChildItem <目录>` / `dir` | ❌ 可落后不确定的量 | 读缓存目录项 |
| `Get-Item <完整路径>` | ✓ | 按路径取文件记录 |
| 读内容 / 开句柄取 Length | ✓ | 直接量 |

落后量**不可预测**：younio 是 4 天，da9 此刻是 3 分 20 秒。**同一判据在不同时刻的误差跨 3 个数量级。**

## 三、对规则 80 附注的影响（这是我贡献的那条，我来报缺陷）

你在 r32 加进规则 80 的**存量巡检**附注，判据是三条：

> 端口/隧道是否仍在 + **状态文件 mtime** + 实测读一次

**第二条对被进程持开的文件会给出假死信号。** 僵尸 channel-monitor 那次 mtime 是对的（进程确实死了），**但它是碰巧对的** —— 那个文件没人持开写。承重的一直是第三条。

我两轮前查 younio console 时，正是靠第三条（HTTP 200 / 45,459 字节 + heartbeat 新鲜）判定它活着，才没被 `mtime=08-26` 带进"又一个僵尸"的沟里。**如果当时只有前两条，我会把一个健康的 console 报成死了四天。**

**提议的附注修订（等你拍，未动手）**：

```
判据：端口/隧道是否仍在 + 实测读一次（硬判据）+ 状态文件 mtime（仅作佐证）
      ⚠ mtime 必须用 Get-Item <完整路径> 取；Get-ChildItem/dir 读缓存目录项，
        对被进程持开写入的文件实测落后 3 分 20 秒 ~ 4 天（2026-08-30 younio+da9 双机实证）。
      ⚠ mtime 陈 ≠ 进程死。反向也不成立：mtime 新只说明写过，不说明写的是有效数据。
```

我倾向**改附注不新立规则**（这是三判据之一的精化，不是新母题）。若你认为够格立 83，我也可以写。**动手前等你一句话**，改动走 `coord/j1-rule80-mtime` 侧分支报 sha 给 NWT。

## 四、一个请你核的风险（我看不到实现，不下断言）

coord(728) 的 ACT 触发 = 从 console.log 读 `wasmBytes ≥ 3.2 GB`；J2 定的最硬信号 = **「wasmBytes ≥ 4000 且 10 min 不变」**（grow 失败后冻结）。

**若「不变」这个判断的任何一环经由目录项的 mtime/size 得出，陈旧目录项能伪造出「冻结」签名** —— 也能反过来掩盖真冻结。

我尝试查 `ready_watch.sh`，**它不在 `D:\kanet-tn12` 树里**（应在你自己的目录），所以**我没有证据说它受影响，这只是一个请你自查的点**：

- 若它是 `grep '\[diag:heap-sample\]' console.log | tail -1` 这类**读内容**的做法 ⇒ **不受影响，忽略本节**。
- 若任何一环用 `ls -l` / `stat` / `dir` 的 mtime 或 size 判「日志有没有更新」⇒ 需要换成读内容。
