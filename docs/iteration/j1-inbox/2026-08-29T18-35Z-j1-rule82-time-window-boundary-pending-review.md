## 二、为什么立这条

**我今天同一个母题犯了两次，第二次已经向你发出了错误断言**（17:10Z 那份更正就是收拾它）。按 CLAUDE.md「撞了未在档案的新坑 → 立即追加一条」，够格立规则。

**规则 82 —— 引用某个时间窗的统计量，必须先核对关心的事件在不在窗内；尤其要问「这个事件发生时，样本还在产生吗」—— 若事件本身会让样本停止产生，窗口就结构性地排除了它。**

**实录一（自己抓到）**：算 younio 有效工作占比时，我用日志 `Processed` 行密度做分母得 74.8%。但块体扫描期间 kaspad 根本不发那种行 —— 1349 条行只覆盖 14.45 小时里的 3.75 小时。那是「有输出的时段里的占比」，不是墙钟占比。

**实录二（没抓到，发出去了）**：我说「本次停滞已计入该速率的长窗基线内」。实查窗口 `08-28 16:12 → 08-29 20:44`，停滞 `08-29 21:18` 才开始 —— 整个在窗外。佐证：窗口内 32 个间隔全在 44.9–74.7 分（均值 53.5），若停滞在窗内必然出现一个约 180 分钟的异常间隔。

## 三、判据的核心是第三问

```
(1) 窗口的起止是哪两个时刻？
(2) 我关心的事件落在窗内还是窗外？
(3) 产生样本的机制，在那个事件期间还在工作吗？   ← 最隐蔽
```

**第三问指向的是「结构性排除」**：块下载百分点**只在下载推进时才产生**，停滞期一条都不产生 ⇒ 停滞**永远不可能**进入由它算出的速率。**这不是采样密度不够，加多少样本都补不上。**

同类形态：用「有日志行的时段」算占比、用「有交易的区块」算平均、用「成功的请求」算延迟 —— 都是让被测事件自己决定样本存不存在。

## 四、与既有规则的关系

- 规则 **60**（观察窗口必须长于故障周期）讲窗口要**够长**；本条讲窗口要落在**对的位置**、且**样本机制要与被测事件无关**。**长度对了位置错了，一样得出错结论。**
- 规则 **68**（"我找到了 N 处"的可信度取决于用的是枚举方法还是恰好读到的地方）—— 同属「统计量的可信度取决于它怎么被取出来」。
