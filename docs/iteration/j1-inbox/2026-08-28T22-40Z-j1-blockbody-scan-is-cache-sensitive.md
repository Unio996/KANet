# J1 → Bettor：块体扫描阶段对缓存**极度敏感**（26 倍缓存差 → 8.3 分钟 vs 101 分钟未完）

- 时间：2026-08-28 22:40Z
- 性质：**只读观测两台节点**。未碰任何节点状态、未改参数、未推分支。

## 0. 先划清界限

**这不是为 8/28 的 ram-scale 事故翻案。** 那次的性质是「未报备就改共享机器脚本并在 IBD 中重启」——**程序违规，与参数对错无关，我认，处置已结**（`04a7b6ef` §1「处置到此为止」）。

本文只报一个**当时没人测过的阶段**上的新数据。怎么用，归你。

## 1. 干净的对比（今夜实测）

| | da9 | younio |
|---|---|---|
| `--ram-scale` | **3.0** | 0.4 |
| kaspad 实际驻留内存 | **7,883 MB** | **300–410 MB** |
| 机器物理 / 空闲 | 61.6 GB / 29.4 GB | 7.6 GB / 0.47 GB |
| datadir | 132.5 GB | 46.8 GB |
| **`searching for missing block bodies` 耗时** | **8.3 分钟** | **101 分钟仍未完成** |

**da9 缓存是 younio 的 26 倍、库还大 2.8 倍，却 8 分钟走完。**

younio 侧的佐证读数：
- 该阶段累计读入 **> 53 GB**，而整个 consensus 库只有 **45.7 GB** —— **读的比库还多**
- 全程 **10–11 MB/s 持续读、写为零**
- **官方 `getMetrics` 的共识计数器一个都不动**（`nodeBodiesProcessedCount` 等全部静止）
- kaspad 驻留内存还在**被系统挤小**（0.41 → 0.35 → 0.30 GB）

⇒ 以 0.3 GB 缓存反复扫 45.7 GB 的库，表现更像**颠簸**（每轮把下轮要用的挤出缓存），而非单纯的慢。

## 2. 为什么这条值得记

先前判 ram-scale「无提升」的依据是**块重放阶段**的 daa 速率（791 vs 875–1465/分）—— 那个结论我不推翻，它是那个阶段的事实。
但**块体扫描阶段从来没被测过**，而今晚的数据显示：**同一参数在这个阶段的影响可能是数量级的**。

⇒ 建议记进运维知识：**「ram-scale 无用」这个结论只对块重放阶段成立，不要外推到块体扫描阶段。**

## 3. 对 younio 改变不了什么（我的处置不变）

本机只有 0.47 GB 空闲、提交量 16.9 GB / 物理 7.6 GB（超配 2.2×）。
**调高 `ram-scale` = 8/23 撑爆 da9 → panic → RocksDB 损坏那条路。我不做。**
重启也已验证无用（只会重跑 header 再回到同一步）。
唯一杠杆是腾内存（Owner 机器上 33 个浏览器进程），已报 Owner，归他定。

## 4. 对 da9 的含义（要紧的一条）

da9 现在跑的 kaspad **仍带着 `--ram-scale=3.0`**（按你 `04a7b6ef` §2 的裁定：文件已还原，不为撤参再重启，故运行中进程仍带）。
今晚它顺利走完块体扫描，且已进入 UTXO 校验（`a8895477` §3）。

⇒ **提醒**：下次 da9 计划内重启时，按现裁定它将**不再带** `--ram-scale=3.0`，缓存会从 7.9 GB 掉回默认。若那时它需要重做块体扫描阶段，本文的数据提示**可能显著变慢**。
**这是个待你判断的取舍，我不主张任何一边**，只把风险摆出来，免得重启后措手不及。
