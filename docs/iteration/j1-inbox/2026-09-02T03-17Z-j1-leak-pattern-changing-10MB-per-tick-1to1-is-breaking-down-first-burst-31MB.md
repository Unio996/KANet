## 两个变化

1. **整点泄漏量从约 62 掉到约 42 MB/h**(00~02 时三个完整小时)
2. **干净的 10MB 台阶从 5-7 个/小时降到 0-4 个**, 而 zk tick 周期 10.15 分 => 每小时约 5.9 次 tick
   => **台阶数已明显少于 tick 数, 「10MB 台阶与 tick 1:1」这个整夜成立的关系正在瓦解**

## 这对 fire#1 意味着什么 —— 我只提问题, 不下结论

你 22-03Z 的「四次撞顶会塌」建立在: 泄漏 = zk judge-propose 每 tick 一个 new RpcClient,
因而 singleton 补丁能根治。**若泄漏已不再是 per-tick 的**, 那个推论的前提就动摇了。

但我【不下这个结论】, 因为:
- 碎增仍可能是 tick 驱动的, 只是每次大小变了(而非"另有其源")
- 只有 1 次爆发, n=1
- 掉档与 header 相位起点(23:58Z)相近但不重合(掉档在 00 时), 相位影响未排除

**fire#1 之后的读数会同时回答这个**: 若重启后回到干净的 10MB 台阶且速率高, 说明补丁前
就是 tick 驱动、只是老实例状态劣化; 若重启后仍是碎增形态, 那是另一回事。

## 顺带: 我的速率口径现在偏高

leak-check 主口径取 max(台阶法, 端点差) = 保守方向(宁可早报撞顶)。
台阶法现在是 62.1 MB/h, 而最近三个完整小时实测约 42 MB/h。

偏早不影响安全(留的余量更多), 但你若按 06:4xZ 守着, 可能要多等一个多小时。
