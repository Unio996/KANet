## 一、结论先说

**不是我们的机器慢，是传输被往返延迟卡死。** 四项本地资源没有一项吃紧，出口带宽只用了 **0.05%**。

## 二、逐项排除（全部实测，不是推断）

```
CPU      1.14 核 / 24 核 = 总算力 4.7%              ← 闲
磁盘     PhysicalDisk 92% 空闲, 队列 0.1, NVMe SSD   ← 闲
内存     61.6 GB 总 / 28.2 GB 空闲                   ← 闲
带宽     实测下行 17.45 MB/s (140 Mbps)              ← 闲
实际收   60 秒实测 0.6 MB = 9 KB/s = 0.072 Mbps      ← 只用了 0.05%
```

**⚠ 一个会误导人的读数**：进程级计数器报「402,411 次读 / 2,717 MB / 15 秒 = 181 MB/s」，看着像磁盘打满。**但 PhysicalDisk 计数器只有 407 次/秒、92% 空闲** —— 那 26,800 次/秒绝大多数命中的是**操作系统文件缓存**，不是物理盘。**只看进程计数器会把"缓存命中"误判成"磁盘瓶颈"。**

## 三、peers 数与速度无关（我原来的假设，已被自己的数据否掉）

用我一整天 247 条采样按 peers 分组：


**四组无差异。** 原因是 IBD 只从**一个同步对端**拉数据，连着几个 peer 不影响。⇒ **补 peer 这条路是死的，不用再试。**

## 五、根因与量化

```
往返延迟 RTT = 196 ms (ping x8, 195-199 ms 极稳)
对端 136.243.93.17 = Hetzner 德国; da9 在 UTC+7 ⇒ 跨洲

反推:  9 KB/s × 0.196 s ≈ 每个往返在途 1.8 KB ≈ 3 个块
       每秒 5 个往返 × 3 块 = 15 块/秒   <- 与实测块速完全吻合
```

**⇒ 这是一个「请求—等待—收—再请求」的串行传输，在途数据量只有 ~1.8 KB。** 带宽再大、CPU 再多都用不上，因为绝大部分时间在等 196 ms 的空中飞行。

## 六、可动的与不可动的

**本地无可调项**（我查过 `kaspad --help`）：`--ram-scale=3.0` 已设、`--async-threads` 默认 24、`--rocksdb-*` 都是缓存/存储向，**没有 IBD 请求流水线深度的开关**。加内存/换盘/加 CPU **一点用都没有**。

**唯一真实的杠杆是缩短 RTT**：把同步节点放到离对端近的地方（对端在德国 Hetzner）。同机房/同区域 RTT 可降到 1–10 ms，**理论上快 20–200 倍**。具体做法（欧洲 VPS 同步后搬库 / 直接在欧洲跑节点）属于基础设施决策，**归你和 Owner，我不越界建议**。

**若不动基础设施**：按当前速度余 **2.45 天【下界·不含停滞·轮次法 26 样本/19.8 h】**，这个数是合理的，**不存在"本该更快却慢了"的缺陷**。
