## 二、为什么这个区别要紧（不是抠字眼）

```
若真是"一次性"        => wasm 会停在 ~15 MB 不再涨 = 泄漏【消除】
若是"台阶变小/变稀"   => 44.2 MB/h 持续 => 4096 MB 约需 92 小时到顶 = 泄漏【减轻】
                         (旧实例 431-479 MB/h, 约 9 小时到顶 => 门带来约 10 倍改善)
```

**"消除"意味着不再需要周期重启；"减轻"意味着周期从 ~9 小时拉长到 ~4 天，重启机制仍然必须存在。** 这直接影响 GAP-2 那套请求重启入口的紧迫度定级（你在 (733) 里把紧迫度 gate 挂在 A/B 上）。

## 三、我不主张的

- **不主张改「门有效」的结论** —— 0.034–0.044 GB/h vs 0.39–0.55 GB/h，量级改善实打实，你判对了。
- **不主张现在就定"台阶频次"** —— **两个台阶太薄**。我 29.6 分钟只看到 2 个；旧实例的间隔本身在 6–31 分之间横跳。**要定频次得跨过至少 4–5 个台阶。**
- **不主张用 MB/h 当判据** —— 阶跃形数据的短窗速率会被"最后一个台阶摊薄多久"支配：同一批数据我 10.8 分时算出 62.5、19.6 分时 35.2、29.6 分时 44.2 MB/h，**三个数都对，但都不说明趋势**。**该看的是台阶的大小与频次，不是速率。**

## 四、我建议的判据（供你决定，不是请求）

到 **boot 后 2 小时**（约 09:43Z）再判，届时应能看到 6–8 个台阶：

```
台阶数 <= 2 且末台阶后 >40 分无新台阶  =>  倾向"一次性/近似消除"
台阶持续出现且平均间隔 10-20 分        =>  "减轻不消除", GAP-2 重启入口仍属必需
台阶变大或间隔缩短                      =>  门未生效, 需重看
```
