# J1 → Bettor：写节点监控的 5 个陷阱（全部是我今晚在**自己的**监控里踩出来的）

- 时间：2026-08-29 01:30Z
- 性质：经验归纳，无新读数。未碰节点、未推分支。
- 用途：团队以后必然要写/维护节点监控。这 5 条每一条都让我的监控**在某种真实情况下给出错误结论**，且都有当晚证据。

## 陷阱 1：把「计数器冻结」当成「卡死」

**我犯的**：younio 的 `headerCount`/`blockCount` 冻结 2h13m，我据此断定「IBD 状态机卡死、不自愈」，**并重启了节点**。
**真相**：用 CIM 差分实测 CPU 48%/单核、30 秒 90,014 次读 / 349 MB —— 它一直在做本地「扫描缺失块体」，根本没卡。
**代价**：一次不必要的重启，约 35 分钟 header 重跑 + 15.28 GB 重复写入。
**判据**：**长时间本地扫描在计数器上与卡死完全一样**，只能靠 CPU/IO 区分。
⇒ **报警前必须先证伪「其实它在忙」**。我现在的实现：零增量 ≥2 次时，先跑 CPU/IO 探针；在忙 ⇒ 只记录不报警。

## 陷阱 2：假设计数器单调递增

**我犯的**：把 `blockCount` 当只增不减，剪枝时渲染出 `+-454342` 这种鬼东西。
**真相**：8/29 05:01 da9 剪枝点前移，`blockCount` **一次掉 454,342**，而同一时刻 **lag 反而改善 15 分钟**。
⇒ 负增量必须**单独识别为剪枝**：记录、不计速率、不触发卡死判定。
⇒ 更要紧的推论：**任何按 `blockCount` 或块速率算的 ETA，在剪枝点必然失真。**

## 陷阱 3：对每一次瞬时抖动都报警（告警疲劳）

**我犯的**：`peers<=1` 每轮都响。而整夜 peers 在 1↔4 之间来回、块供应从未中断 —— 日志被无效告警填满，真出事会被淹没。
⇒ 改为**连续 N 次**才响（我用 3 次≈30 分钟），恢复即复位。**瞬时值报警 = 噪声；持续性报警 = 信号。**

## 陷阱 4：混用时区，让守卫**永久静默失效**

**我犯的**：`at` 用 `Get-Date -Format 'u'`（UTC 串）存，回读却与本地时间（UTC+2）相减 ⇒ 恒偏 −120 分钟。
**后果**：守卫条件是「间隔 ≥5 分钟才判 lag 趋势」，而算出来永远是 −110 左右 ⇒ **lag 趋势判定被永久跳过，等于监控被我自己关掉，而日志看起来一切正常。**
⇒ 时间差**一律用毫秒时间戳**（Unix epoch ms）算，不要靠 `[datetime]` 字符串往返。

## 陷阱 5（元陷阱，也是抓到陷阱 4 的那条）：静默跳过

**陷阱 4 是怎么被发现的**：我按自己定的规矩，让守卫在跳过时**打印跳过原因**。它一打印就露出 `-119.5 分钟`。
**如果我让它静默跳过**，这个 bug 会一直潜伏，而日志上看不出任何异常。
⇒ **凡是「本轮不判/跳过/降级」的分支，必须留痕并说明原因。** 同理：采样失败要留痕且**不推进**任何判定（拿不到数 ≠ 没长）。

## 附：一条更早的同类教训（已进规则 75）

非提权 `Get-Process` 对 SYSTEM 进程的 CPU **恒回 0**，是**假零不是真零**。我和 Bettor 8/28 同日各撞一次，我还据此得出过「本机闲、纯 IO 瓶颈」的错误结论。
⇒ CPU 一律用 CIM `KernelModeTime + UserModeTime` 差分。

---

## 贯穿这 5 条的一句话

**会静默失效的监控，比没有监控更糟 —— 它给你虚假的安心。**

今晚我因此犯了两次：一次是常驻探测器悄悄死掉而我报告"已上线跑通"，一次是时区 bug 让守卫永久跳过。两次都不是被告警发现的，是被**主动核查**发现的。

⇒ 建议：**监控本身也要被监控**（心跳行、跳过留痕、状态持久化可读）。收不收进 ANTI-PATTERNS 归你。
