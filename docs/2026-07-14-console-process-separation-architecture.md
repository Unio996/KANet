# Console 进程分离架构设计 v1.0 —— 系统性根治(Owner 直令"系统性解决问题")

> **Status**: CURRENT (DRAFT v1.0 · Bettor 拟稿 2026-07-14 · Owner 直令 · 待 NWT 红队 → 分批实施)
> **背景**: 7/13-7/14 两天追凶七个源、修了六个,冻结依旧(仍 26 次 >30s / 最长 278s)。**打地鼠证伪。**

## 一、病根(量化证据,非推测)

| 事实 | 数字 | 后果 |
|---|---|---|
| 常驻循环全在 console 主进程 | **68 个** | 任一循环慢 = 全系统冻 |
| 同步 SQLite 调用(纯同步库,每次阻塞事件循环) | **979 处** | 任一慢查询 = 全系统冻 |
| 数据库体量 | **6.65 GB**,单表 798 万行 | 同步查询 = 纯 CPU 燃烧 |
| 31 个智能体的"大脑"(agent-mind) | **直接 import 进主进程** | LLM 处理挤占主线程 |
| 频道 API / 协调通道 | **与上述共享同一事件循环** | **系统卡死 = 我们集体失声**(今日两次通讯死锁) |

**结论:这不是"某个 bug",这是架构缺陷。在单进程单事件循环里塞进 68 个循环 + 979 个同步阻塞点,冻结是必然,不是意外。修掉一个源,另一个源的固定工作量顶上来——这解释了"恒定 4 分钟签名六轮修复纹丝不动"。**

## 二、目标架构(进程分离)

```
┌─────────────────────────────────────────────────────────┐
│ 主进程(瘦身后)= "永不阻塞层"                            │
│   · HTTP API(用户面/tg-bot/前端)                        │
│   · 频道收发(协调通道 —— 必须永远活着)                   │
│   · 健康检查 / 告警                                      │
│   · 只做轻量 DB 读(带索引、单行、有超时)                  │
│   铁律: 主进程内禁止任何 >100ms 的同步操作               │
└─────────────────────────────────────────────────────────┘
        │ IPC / 消息队列(异步,永不阻塞主进程)
        ├──────────────┬──────────────┬──────────────┐
┌───────▼──────┐ ┌─────▼────────┐ ┌───▼──────────┐ ┌─▼───────────┐
│ 结算进程      │ │ Broker 进程   │ │ Mind 进程    │ │ 做市/Demo   │
│ · pool-settler│ │ · intake      │ │ · 31 agents  │ │ · seeder    │
│ · bshard      │ │ · refund/Z20  │ │ · LLM 调用   │ │ · autobetter│
│ · voter       │ │ · state       │ │ · 记忆/上下文 │ │ · house     │
│ 卡死≠全系统死 │ │ 卡死≠全系统死 │ │ 卡死≠全系统死│ │ 可直接关闭   │
└──────────────┘ └──────────────┘ └──────────────┘ └─────────────┘
```

**核心不变量**:**主进程永不阻塞 → 用户永远能用、我们永远能通讯、任何子系统卡死都能被观测和救援。**

## 三、分批实施(每批独立可上线、可回滚)

### 批 0(今天,零风险,立即止血)—— 关掉非必需负载
主进程里有一批 **demo/测试性质**的常驻循环,公测**不需要**它们:
- `pool-auto-better`(自动下注机器人)、`pool-house-agent`(庄家 agent)、`pool-bot-autofund`
- `market-seeder`(3 个循环)、`pool-market-seeder`
- **31 个 agent 的 Mind proactive/reflection**(它们每小时全员跑一遍 LLM,是纯 demo 负载)

**动作**:给每个加 env kill-switch(已有先例:`POOL_SEEDER_ENABLED`),**默认关闭**,只在需要 demo 时开。
**预期**:主进程负载立刻下降一大截;**如果冻结随之消失,凶手就在这批里(而且我们省下了继续找它的时间)**。
**风险**:极低(关的是 demo,不是公测功能)。**这一批今天就能上。**

### 批 1(1-2 天)—— Mind/LLM 移出主进程
31 个 agent 的 `createMind` 从 `await import()`(同进程)改为 **child_process.fork**(独立进程)。
- 参考:relay 已经是 fork 的独立进程(架构里已有这个模式,直接复用)
- 主进程只保留一个薄的 mind-manager(转发消息,不跑逻辑)

### 批 2(2-3 天)—— 结算/Broker 移出主进程
`pool-market-settler` / `bshard-settle-daemon` / `broker-*` 全部 fork 为独立进程。
- 它们是**同步 SQLite 重灾区**(settler 88 处、broker-intake 33 处)
- 移出后:**它们卡死也只卡自己**,主进程照常服务用户

### 批 3(持续)—— 主进程铁律固化
- **lint 规则**:主进程代码禁止同步 SQLite(白名单:轻量单行查询)
- **看门狗**:主进程 event-loop lag > 1s 立即告警(现在是 >30s 才当回事)
- **反脆弱柱②落地**:主进程永不阻塞 = 系统永远能喊疼

## 四、为什么这是"系统性"而不是又一次打地鼠

| 打地鼠(过去两天) | 系统性(本方案) |
|---|---|
| 找到一个慢的,修一个 | **改变"一个慢的能拖死全系统"这个事实** |
| 修好 A,B 顶上来 | B 卡死只影响 B 自己 |
| 修复放出新怪兽(死 relay id → broker 复活 → 新冻结) | 复活的东西在自己进程里跑,炸不到别人 |
| 系统卡死时我们集体失声 | **主进程永不阻塞 → 永远能观测、能通讯、能救援** |

## 五、DoD
1. 批 0 后:主进程常驻循环数 **68 → <30**;冻结频率下降(数据说话)
2. 批 1 后:主进程内零 LLM/Mind 逻辑
3. 批 2 后:主进程内零同步 SQLite 重查询;**event-loop lag > 30s 归零**
4. 最终:**任何子系统卡死,用户面和协调频道零影响**(这是可测试的:kill 一个子进程,系统照常)

## 六、不做什么
- 不重写业务逻辑(只搬家,不改逻辑)
- 不引入外部消息队列(用 Node 原生 fork + IPC,项目已有 relay 先例)
- 不一次性大爆炸(分批,每批独立上线可回滚)
