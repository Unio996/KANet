## 🔴 §5-A:"R3 不受影响"论证有两个独立缺口,合起来使这句话目前不成立

原文:"账户层 xpub 公开 + 该账户下任一子私钥泄露 ⇒ 可反推账户 xprv ⇒ 该账户全部兄弟私钥。但影响面被 R1 自己夹住了:R1 要求同一 seed 的身份必属同一域 ⇒ 该放大不跨域 ⇒ 攻击者拿到的仍是他已经拿到的那台宿主上的那些钥 ⇒ R3(任一单域 < threshold)不受影响。"

### 缺口①:论证的前提正是 A2 存在的理由本身(循环)

R1 原文(`u1-key-domain-allocation-spec-v0.1.md` §2):"**同一份 mnemonic 的任何派生身份,全部属于同一个域**……**R1 需要落地时的独立检查**"。这句话本身承认 R1 不是密钥学上自动成立的性质,是一条**运维承诺**,而**A2 就是那个独立检查**(上游 spec 自己写"A2 今天验不了")。

⇒ **"该放大不跨域,因为 R1 保证同源必同域"这句话,用的正是"R1 成立"去证明"违反 R1(同一 seed 出现在两个域)时的后果可控"——而 R1 是否成立,恰恰是 A2(以及这整个 u1 项目)存在来验证的那件事。** 若 R1 真的从不被违反,A2 一开始就不需要造。**A2 要防的正是"一个不配合的运营方用同一份 mnemonic 在两个域各放一个身份、只出示互不关联的登记根"**(§0 原文自己这么写的攻击者画像)——而这恰恰就是 R1 被违反的那一刻。§5-A 用"R1 成立"当作"放大安全"的理由,等于**在检验一条规则是否被遵守的机制里,假设了这条规则被遵守**。

**这不是否定 A+C 方向,是指出这句具体的安全声明目前答不出它自己提出的问题**:如果一个运营方真的违反 R1(用同一 seed 在域 X 和域 Y 各放一个"看起来无关"的身份,正是 §0 画的那个攻击者),而域 X 的**其中一个**身份私钥因为任何原因泄露 + 账户层 xpub 是公开注册的(A2 运作的前提)⇒ 攻击者现在同时拿到域 X **和域 Y** 的私钥——**跨域了,R3(任一单域 < threshold)被直接打破**,而这正是 §5-A 说"不受影响"的那个不变量。

### 缺口②:即使 R1 严格遵守,论证也隐含假设了"整机攻破"是唯一威胁模型

（第二个并发 NWT 会话在收束前独立走到、值得折入的一点，credit 归他）即便 R1 完全没被违反(同源身份确实都在一个域内),§5-A"攻击者拿到的仍是他已经拿到的那台宿主上的那些钥"这句话默认了**私钥泄露 = 整机/整域被攻破**,这时候"反正整机都丢了,多丢几把钥没差"确实成立。**但窄通道单钥泄露(签名实现 nonce 复用、单进程侧信道、某一次密钥导出操作被截获)不需要整机权限,现实中比整机沦陷更常见、更难被发现**。在**这类**场景下,formation A 引入了一个在旧布局里不存在的新事实:**账户层 xpub 现在是必须公开给验证方的注册 artifact**(A2 机制运作的前提,不是维持"进程内部派生细节、外部不需要知道"的原状)。旧布局下,窄通道丢一把身份私钥 = 丢一把签名权,不多不少;formation A 下,窄通道丢**同一把**身份私钥 + 已公开的账户 xpub = **丢整个域的全部委员签名权**。**这是放大攻击成本下降带来的新增暴露面,不是"和以前一样"**——§5-A 现在的措辞把它写成"没有让情况变得更差",不准确。

### 两条缺口合起来对 spec 的要求

**不是要求推翻 formation A**(A+C 仍是三条形态里唯一同时满足"派生可证+同源可判"的一条,方向对),而是:

1. **§5-A 的安全声明必须改写,不能说"R3 不受影响"**,要说清楚它成立的确切前提(R1 未被违反 **且** 私钥泄露达到整机级别),并**明确承认这两条都不是 formation A 自己能保证的**——这正好呼应 §5-C 已经在做的事(把不可验的那一侧明写而不是伪装成密码学保证),§5-A 现在恰恰没有对自己做同样的诚实标注。
2. **补至少一项缓解,而不是只改措辞**(三选一或组合,留 J2/Bettor 定,不自拍):
   - **登记根分发渠道收窄**:账户层 xpub 只给需要验证的一方(验证脚本/工具直接读 DB 或专用只读接口),**不经 `dev-coord-testnet` 这类频道**——本仓已有定论频道内容 = 链上明文、不可撤回(`reference-dev-channel-is-onchain-plaintext-not-internal`),一旦账户层 xpub 因为"发个消息报个进度"这类日常操作被贴进频道,就是**永久公开、无法撤销**,而这正是 §5-A 攻击链的必要输入之一。
   - **单 seed 允许挂的身份数设上限**:放大倍数与身份数正相关,身份数越少,§5-A 那条攻击链的"值不值得"越低。
   - 若认为①②成本过高,至少要求**运行时输出同 V3 一样显式声明这条残余风险**(而不是只留文档),让读记分板的人看到"formation A 的兄弟私钥放大风险,依赖 R1 未被违反且威胁模型限定为整机级泄露"这句话,不是靠去读设计稿第 128 行才知道。

**建议新增 V6**(镜像 V3 的纪律):检查器/spec 的运行时输出必须包含"formation A 采用后,单点私钥泄露(尤其非整机级窄通道泄露)的爆炸半径 = 该 seed 下全部身份,该风险的可控性依赖 R1 合规,而 R1 合规正是 A2 本身在检验的对象"这句话的等价表述,不能只活在设计稿里。

## §6 逃逸口(`KASPA_ACCOUNT_INDEX`)处置:同意方向,补一条实现前提

J2 §6"钉死或记录并纳检"两条路都合理,不单独判优先级(Bettor 已标"取舍留设计/红队",这条我不加码)。**但有一件事 J2 §6/§8 均未提、落码时会撞到**:formation A 把委员身份的可变量从"accountIndex(硬化)"搬到了"叶子 index i(非硬化)",这**不是配置项调整,是 `wallet.mjs:39-50` 当前 `m/44'/111111'/accountIndex'/0/0`(叶子固定 `0/0`)这条派生路径本身需要加一级"叶子沿 i 展开"的代码改动**——不是"要不要堵 `KASPA_ACCOUNT_INDEX`"这一个问题,是"这套新派生逻辑要不要复用现有 `wallet.mjs`、还是给 runbook §2 步骤 2 单独一条新代码路径"这个更大的问题,新代码路径本身也需要同一套 §2(b) 式的"逃逸口"审视(例如:新代码是否也从某个可被进程环境覆盖的变量读取 `i`)。**这条只是提醒,不是本轮阻塞项**——落码阶段第一步确认清楚就行。
