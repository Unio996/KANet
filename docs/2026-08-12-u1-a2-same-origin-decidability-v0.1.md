## §0 一句话（先说结论，因为它改的是裁定的前提，不是裁定的选项）

**裁定选 ① 是对的，② 该否决也对。但那条硬要求——「登记根能派生出 relay 子 pubkey」——与 A2 要答的问题——「两个 relay 是不是同一份 mnemonic」——在本仓现行派生路径下【互斥】：能派生证明的那一层，恰恰是分不出同源的那一层；能分出同源的那一层，恰恰是派生证明不过去的那一层。**

⇒ 所以 A2 不是"选个格式然后写码"，**得先动一处派生路径，或者接受"同源只能正向证、不能反向证"**。两条我都写在 §5，带代价，**不自拍**。

## §2 决定性实验：同一份 mnemonic 的两个身份长什么样

⚠ 全程用**当场随机生成**的助记词，**未解密任何在库真实密钥**。

```bash
node scratch/_j2_a2_derivation_probe_20260812.mjs
```
```
A 同一 mnemonic · acct 0 两次  : IDENTICAL
B 同一 mnemonic · acct 0 vs 1  : DIFFER      ← 同源, 但两个地址在公开数据上看不出任何关系
C 不同 mnemonic · acct 0       : DIFFER
```

**两条直接推论**：

- **(a) 现行部署下，"两个 relay 共享一份 mnemonic" 必然表现为【同一个 address】**（因为 accountIndex 恒 0 ⇒ 同 seed 同路径 ⇒ 同私钥）。
  ⇒ **A2 在"无人动 account index"的世界里，今天就是可判的，成本为零**：`GROUP BY address HAVING COUNT(*)>1`，现读 **0 组**。
- **(b) 而这条只在 `KASPA_ACCOUNT_INDEX` 保持不被设置时成立。** 它是**进程环境变量**，不在仓里 ⇒ **一个不配合的域运营方，在自己那台宿主上 `export KASPA_ACCOUNT_INDEX=1`，就能用同一份助记词造出第二个"看起来无关"的委员身份**，而 (a) 这道检查全程绿灯。
  🔴 **而它恰恰是 u1 唯一要挡的那个人。**

## §3 🔴 裁定的硬要求与 A2 的目标，在现行路径下互斥（本稿核心）

裁定要求：**验证方能从登记根推导出 relay 子 pubkey 并比对**。问"哪一层能当这个登记根"，答案只有一个，而它答不了同源。

**实测**（本仓 wasm，不是引 BIP32 教科书）：
```bash
node scratch/_j2_a2_hardened_gap_probe_20260812.mjs
```
```
① master XPub -> deriveChild(44, HARDENED)      : 抛错 "Bip32 -> Invalid child number"
② master XPub -> deriveChild(0,  NON-hardened)  : 成功        ← 对照臂: 这把 XPub 本身可用,
                                                                ① 的失败不是"对象坏了"
③ 账户层 XPub(m/44'/111111'/acct') -> 叶子 0/0   : 成功        ← 只有这一层推得到 relay pubkey
```

于是两层各自缺一半：

| 候选登记根 | 能派生证明到 relay pubkey？ | 能判两个 relay 同源？ |
|---|---|---|
| **master xpub / seed 指纹** | ❌ 中间三级全硬化，`deriveChild(_, true)` 在 XPub 上直接抛错（①） | ✅ 相等即同源 |
| **账户层 xpub** `m/44'/111111'/acct'` | ✅ 最后两级非硬化，推得到（③） | ❌ **同一 seed 的两个账户是硬化兄弟，彼此不可关联**（②/③ 合起来说明：从 XPub 跨不过硬化那一级） |

🔴 **⇒ 不存在一个既满足裁定硬要求、又能判同源的登记根。** 硬要求原样执行 ⇒ 登记根只能是账户层 xpub ⇒ **它证明的是"这个 relay 属于这个账户"，不是"这两个 relay 同源"** ⇒ A2 没被答上，而记分板会显示 ① 已落地。

🔨 **这一格值得单独记**：硬要求本身没写错——它防的"换皮的 ②"是真风险；**错的是它默认了"存在一个既可派生证明又能判同源的根"**。这个默认在硬化账户布局下不成立，而**光看裁定文字看不出来**，得去 wasm 上撞一次。

## §5 三条可行形态（带代价，不自拍）

### 形态 A · 改派生布局：让同一 seed 的委员身份共用一个【非硬化可推】的账户层
把 u1 委员身份从"每身份一个硬化账户"改为"**一个 seed = 一个硬化账户，身份沿最后一级非硬化 index 展开**"：
```
m / 44' / 111111' / 0' / 0 / i        ← i = 该 seed 下第 i 个委员身份
```
- ✅ **两个要求同时满足**：登记根 = 账户层 xpub（可派生证明到每个 relay pubkey，③ 已实测）；**同一 seed 的身份全部挂在同一个根下 ⇒ 同源变成"根相等"，可判**。
- 💰 **成本比看上去小**：runbook §2 步骤 2 本来就是**在目标宿主本地【新生成】委员密钥** ⇒ 新钥直接按新布局生成即可，不动存量。
- ⚠ **一条必须写明的代价 —— 已由我自己实测坐实（v0.2 升级：原为 🟠 未测，现 ✅ CONFIRMED，带对照臂）**：
  账户层 xpub 公开 + 该账户下**任一**非硬化子私钥泄露 ⇒ **可反推账户 xprv ⇒ 该账户全部兄弟私钥沦陷**。
```bash
node scratch/_j2_a2_xpub_leak_probe_20260812.mjs
```
```
反推出的账户私钥 == 真账户私钥 ? 🔴 YES — 反推成立
对照臂(乱 chainCode)           ? ✅ 推不出  ← 证明上一行【确实在用登记根】, 不是算式恒真
由反推私钥再算兄弟 i=1          ? 🔴 命中   ← 单把子钥泄露 ⇒ 该账户全部兄弟沦陷
```
  🔴 **⇒ 登记表把「泄露一把子私钥」放大成「泄露该账户全部身份」。这是形态 A 引入的新代价，不是原有风险的换个说法。**
  🔵 **但放大面被两条夹住，R3 仍然成立**（这是我给的论证，**请 @NWT 独立判，别采信我这段**）：
  ① **R1** 要求同一 seed 的身份必属同一域 ⇒ 兄弟全在同一台宿主 ⇒ **放大不跨域**；
  ② **R3** 要求任一单域持钥 < threshold（今 ≤3 < 4）⇒ **即使某域全部钥沦陷，也仍然凑不齐签名** ⇒ u1 的目的本身不被这条代价推翻。
  ⇒ **结论：代价是真的，且被 R3 兜住；R3 因此从"分配规则之一"升格为"形态 A 的承重前提"** —— R3 若被运维临时打破，这条放大就直接变成"攻破一台宿主即可凑齐"。
  ⚠ **随之而来的一条运维硬规矩**：`dev-coord-testnet` 是**链上明文**（在册）⇒ **账户层 xpub 绝不可粘进频道/任何公开面**，登记根只落库。粘一次 = 永久公开。
- ⚠ 存量 10 个 oracle 仍是旧布局 ⇒ 它们之间的同源仍只能靠 §2(a) 的 address 相等判（够用，因为它们的 account index 事实上都是 0）。

### 🔴 §5-A-bis · 我上面那段「被 R3 兜住」**不够**（v0.2 自撤一半 · 第二 NWT 会话 18:50Z 抓，我复核成立）

我写"放大面被 R1/R3 夹住"时，脑子里的攻击是**整机/整域级攻破**——那种情形下"多丢几把"确实不改变什么，因为攻击者已经在那台宿主上了。
🔴 **而它不覆盖【窄通道单钥泄露】**：签名实现的 nonce 重用、单个进程内的一次内存/日志泄露、一份误传的密钥文件——**这类泄露不需要整机权限**。

- **形态 A 之前**（每个身份自己一份 seed）：窄通道泄露一把 ⇒ **只丢那一把**。
- **形态 A 之后**（一 seed 一账户、多身份挂同一个**公开的**登记根）：窄通道泄露一把 ⇒ **该账户全部身份**（§5-A 实测已坐实，含对照臂）。
- ⇒ **每次窄通道泄露的"产出"从 1 把变成 identities-per-account 把（今按 R2 = 2）⇒ 攻击者凑到任意给定把数所需的独立泄露次数【减半】。**
  今 threshold = **4-of-5**（✅ 现查代码：`pool-p2sh-v06.mjs:96` / `pool-close-builder.mjs:49` / `bshard-auto-settler.mjs:33`，非引在册）。
  ⚠ **我没验的一格，留给 @NWT**：拿到的那几把是否**恰好落在目标市场被抽中的那 5 个委员槽**里（`pool-committee-sampler.mjs` 的抽样），决定"减半"是不是直接等于"两次窄泄露即可签"。**这一格没验之前，别把它写成"两次即可"。**

🔨 **而这条最该被记住的不是结论，是它暴露的结构**：
> **在形态 A 里，「同源可判」与「一泄全丢」是【同一个属性的两面】** ——
> 一个根覆盖多个身份，**正是**它能判同源的原因，**也正是**它一泄全丢的原因。BIP32 下这两者拿不开。
> ⇒ **`identities-per-account` 这个数字，就是"A2 判定力" ↔ "泄露放大面" 的旋钮**：调到 1，放大面消失、A2 也判不出任何东西；调到 R2=2，两者都拿到一半。

⇒ 🔴 **这个旋钮我不自拍**（它是安全取舍不是工作量取舍，且我上一条推荐已被采纳=更要自己先打）。**请 @Bettor 定 `identities-per-account`，@NWT 先判上面那格抽样问题。** 在这个数字定下来之前，**形态 A 的落码我不开工**——布局是烤进密钥生成的，事后改 = 重新生成全部委员钥。

### 形态 B · 保留硬化布局，登记根 = seed 指纹，放弃"派生证明"这条硬要求
- ✅ 同源可判（指纹相等）。
- ❌ **指纹与 relay pubkey 之间没有任何可验链接** ⇒ 正是裁定要防的"换皮的 ②"。
- ⇒ **除非**指纹是在 runbook §2 步骤 2 的**生成时刻、在宿主本地由既定程序吐出并见证**（下一节）。单独用 = 不推荐。

### 形态 C · 承认边界：把 A2 的保证从"登记表"移到"生成仪式"
🔴 **一条无论选 A 还是 B 都成立的硬事实，必须写进 spec，不能留给下一个人自己撞**：

> **任何纯软件的事后检查，都【无法】证明两把独立生成的密钥【不是】同一份 seed 派生的。**
> 同源的**正向**（"这两个确实同源"）可以被证明；**反向**（"这两个确实不同源"）证明不了——
> 因为造钥的人可以私下用一份 seed 造两个身份，然后只出示两个互不关联的登记根（硬化兄弟，实测 ① 跨不过去）。

⇒ **A2 的反向保证只能来自"钥是怎么生出来的"**：runbook §2 步骤 2 的"在目标宿主本地生成"如果是**既定程序 + 见证/留证**，那么"两个域的钥不同源"这句话的可信度 = 那场仪式的可信度，**不是密码学的**。
⇒ **spec 必须把这句原样写上**，否则 A1/A2 打勾之后，读的人会以为 R3 有密码学保证，而它实际靠的是运维程序。

## §7 验收判据（预登记·看码前写死）

| # | 判据 | 怎么测 | 为什么不能省 |
|---|---|---|---|
| **V1** | 同源正向可判：同一根下的两个身份，检查器必判 SAME-ORIGIN | 构造两个同根身份（随机 seed，非真钥），跑检查器 | 这是 A2 的主功能 |
| **V2** | 派生证明真在验：把登记根改成**另一个合法的根**（不是乱码）⇒ 必红 | 弱注入臂 | 乱码根会被格式校验拦下，**它红了不证明派生比对在跑**（在册：注入物必须取自断言实读的字段集） |
| **V3** | 反向不谎报：两个**确实不同源**的身份 ⇒ 判 DIFFERENT，且检查器**显式输出"本判定不具反向保证"** | 阳性对照 + 读输出串 | §5-C 的边界必须出现在**运行时输出**里，不能只活在文档里 |
| **V4** | account-index 逃逸口：同一 seed、不同 account index 的两个身份 ⇒ 检查器**必须报"无法判定"而不是"不同源"** | 构造 acct0 / acct1 两身份（§2 实验的同一构造） | 🔴 fail-closed：把"我看不出来"输出成"它们不同源"= 把无知报成安全 |
| **V5** | 存量 32 行：跑一次全量，输出与 §1 现读一致（0 重复 address） | 全量非抽样 | 判据 B 同纪律 |

⚠ **V2 的注入物必须是"另一个合法根"**：只把根改成 `"deadbeef"` 之类，被格式校验挡下也会红 ⇒ **红了但没证明任何东西**。

## §8 残余敞口（明写，不留给下一个人撞）

1. **反向不可证**（§5-C）——A2 打勾 ≠ "不同域的钥确实不同源"。靠生成仪式。
2. **`KASPA_ACCOUNT_INDEX` 逃逸口**（§2-b）——不堵则对抗场景下 §2(a) 检查失效。
3. **2 个 privkey-only relay**（`privkey_encrypted` 非空 2）——**根本没有 mnemonic** ⇒ R1 这条规则对它们**无定义**。spec 现在没说这类身份能不能当委员。**需要 @Bettor 一句**：委员是否必须是 mnemonic 型？（若允许 privkey 型，R1 的"分配单位=一份 mnemonic"就有一类身份落在规则之外。）
4. **本稿未实测**：§5-A 的 xpub+子私钥反推账户 xprv（标准 BIP32 性质，标 🟠）；threshold 今天是否仍 4-of-5（引在册，**落地前请现查，别引我这句**——上游 spec §6 也这么标过）。
