## §0 为什么需要这份（spec 到这里就没往下写了）

spec 规定了**根是什么**（N1 账户层 xpub）、**身份怎么挂**（N2 非硬化叶）、**几个**（N3 锁 1）、**谁能当委员**（N4）。
**它没规定**：这些东西**存在哪**、**谁写进去**、以及——本稿的重点——**写进去的人凭什么证明那是他的**。

🔴 **A-1 已交付的判定库只回答"这条记录自洽吗"，不回答"这条记录是不是他有权写的"。** 两者差一次授权。

## §1 🔴 先说那个我不打算自己填的洞：**派生证明 ≠ 控制权证明**

N1/N2 的派生证明回答的是：**「这个 pubkey 确实是从这个根派生的」**。
**它没有回答**：**「提交这条登记的人，控制那个根」**。

**具体的攻击**（不是假设性的，登记表在多域互不信任的前提下运作）：
> 域 X 的运营方从登记表里**读到**域 Y 的根 `R_Y`（他有读权限——验证方要能读，见 N6"给验证方"），
> 然后用**自己的** relay_id 提交一条 `{root: R_Y, identity_index: 0, pubkey: 从 R_Y 派生出来的那个}`。
> **这条记录会完美通过 A-1 的全部校验**（派生证明成立，因为它本来就成立）。
> 后果分两种，都不好：
> - **N3 侧**：登记表里出现"同根两身份" ⇒ **A2 报构造性违规，而被指认的是域 Y**（诬告）；
> - **A2 侧**：`classifySameOrigin(X, Y)` ⇒ **SAME_ORIGIN** ⇒ 一个**伪造出来的**同源结论。

🔨 **判据（在册那条的同形）**：**一个字段只要能被"抄"，它就不是证据，是申报。**
派生证明把"申报的 pubkey"钉死到"申报的根"上，但**两个申报一起抄过来，钉死关系原样成立**。

⇒ **注册入口必须要求控制权证明**：登记时对一个**服务端出的、一次性的挑战串**用该身份私钥签名，验签通过才落库。
**这一步不在 spec 里，是我提出来要加的**——所以 **@NWT / @Bettor 裁**：
- **(a)** 认这条洞、把控制权证明加进 spec（我出实现设计）；
- **(b)** 或判定「登记表写入面本来就只有可信运维、不在威胁模型内」⇒ **那就把这句写进 spec 的作用域**，别留空。
🔴 **两条我都能做，但我不自己拍** —— 它决定 A2 的结论算不算证据。

## §2 存哪：**新表**，不是往 `u1_domain_assignment` 上挂列

| 方案 | 判 |
|---|---|
| 扩 `u1_domain_assignment` 加列 | ❌ **不采**。该表 v195 的建表注释写死「**纯记录表, 不参与签名判定**」，且 spec I2 要求它**永不进授权语句**。把身份来源证据挂上去 = 把一张"纯记录表"变成承重表，两种读法混在一个表名下（在册：一名多物）。 |
| **新表 `u1_identity_registration`** | ✅ **采**。职责单一：**身份 ↔ 登记根的绑定证据**。与"域归属"解耦，正是 spec §4 I1/I2 要的正交。 |

**拟表（待审，未落）**：
```sql
CREATE TABLE IF NOT EXISTS u1_identity_registration (
  relay_id              TEXT PRIMARY KEY,          -- 一个 relay 一条
  root_fingerprint      TEXT NOT NULL UNIQUE,      -- 🔴 见 §3: 把 N3 变成【结构约束】
  root_xpub             TEXT NOT NULL,             -- 账户层 xpub(kpub/xpub 皆可, 比较一律走指纹)
  identity_index        INTEGER NOT NULL DEFAULT 0 CHECK (identity_index = 0),
  identity_pubkey_xonly TEXT NOT NULL,
  custody               TEXT NOT NULL CHECK (custody = 'mnemonic'),   -- N4
  registered_at         TEXT NOT NULL DEFAULT (datetime('now'))
);
```
migrate 版本接 **v196**（当前最新 v195）。**改表须同步更新 `docs/DATABASE.md`**（CLAUDE.md 硬规矩）。

## §3 把 N3 从"检查"升成"结构约束"（本稿唯一的主动加固）

`UNIQUE(root_fingerprint)` + `CHECK(identity_index = 0)` ⇒ **"同根第二身份"在数据库层就写不进去**。

🔵 **为什么值得**：A-1 的检查器是**事后扫描**——它只有在**有人跑它**的时候才说话（本仓在册教训：加了 case ≠ 有人守着）。
DB 约束是**写入时**的，不依赖任何人记得跑。**两层都要**：约束挡住写入，检查器覆盖存量与跨表一致性。

⚠ **但必须写明它挡不住什么**（否则又是一次"局部性质当全局保证"）：
- 它挡的是**同一张表内**的同根重复；**挡不住**同一 seed 的**另一个硬化账户**（那是两个不同的根 ⇒ 两条合法记录）——**那一半永远是 §1-C 的仪式域**；
- 轮换（R5：换钥不搬钥）会撞 `UNIQUE` ⇒ **旧行必须先归档/删除**，这条要写进轮换流程，否则第一次轮换就被自己的约束卡住。**（这是我现在就能预见到的运维摩擦，写在这里免得落码后才发现。）**
