## 1. 已采纳的 Bettor 裁定

① V1 = 方案 A（商家发号）+ 凭据自取；私信推送与方案 B（交付地址并入 nonce）放 V1.1。
② 买家抢先 `split` 时自动交付须**三条同时满足**，任一不满足走人工：(a) 花费订单 UTXO 的交易在 `deadline` 前落链（到期前合约只允许 `split`）；(b) 给商家的输出金额精确吻合；(c) 深度 ≥ 20。⇒ 取代 v0.1 §3/§9-1 里"商家地址出现金额吻合的新 UTXO"那条弱判据。
③ 不加一次性令牌（nonce 128 位，枚举不可行）；默认允许重复取；只做限速。（方案 B 下"限速"落在读链端，见 §4.5。）
④ 私信不放激活码。
⑤ V1 放在 console 内（第②档自跑节点，数字分身也走这档）。

## 2. 事实：买家为什么够不到 console（只读实核代码与既有设计文档）

- console 绑 `HOST || '127.0.0.1'`（`kasia-console/src/index.js`；`docs/gap-A-public-exposure-allowlist.md` §1：573 条路由大半无鉴权，**禁止裸 `HOST=0.0.0.0`**）。
- console 另有一个 **tailnet 专用面**（ZK 专用、独立鉴权，见 `docs/2026-07-23-m0c-1-mechanism-a-http-capability-gateway-design.md` §2.4）——买家不在 tailnet，**不是**买家入口，也不应被借用。
- 现成"网关" = 机制 A HTTP 能力网关（同上设计）：**console 侧、本机回环**，是"本机外部 app（如 tg-bot）带信封受保护调用 relay"的入口——解决的是**授权**，不是**可达性**。
- adapter（`agent-adapter`，端口从 3010 起）= AI 大脑桥接，**本机内部**服务，同样不对公网。
- `gap-A` 的 nginx 白名单反代方案**磁盘上有设计与配置、当前未运行**——是"若要公网入口"的现成起点（方案 C）。
- relay 访问链读写：`check_utxo_landed` / `get_address_utxos`、`send_message`、`sendKaspa({to, amount, payload})`；买家侧静态页已内置 `monitor.js`（直连公共节点读 UTXO）。

⇒ 结论：**"买家 → console 的 HTTP 取货端点"在现有边界下不成立**；要么新开口，要么让交付物走一个**买家本来就能读**的地方。

## 4. 逐案：买家取货路径 · 信任边界 · 成本

### 4.B 链上加密信箱（推荐）

**路径**
1. 出单时（方案 A 商家发号）商家持有 `orderNonce`；买家持有凭据（含同一 nonce）。
2. 双方各自本地派生：`K = HKDF-SHA256(ikm = orderNonce, salt = 订单地址字节, info = "kanet-delivery-v1/key")`（AEAD 密钥）与 `m = HKDF(…, info = ".../mailbox")` → 拒绝采样得合法 Schnorr 私钥种子 ⇒ **信箱地址**（P2PK）。
3. `split` 落链后，卖家 watcher 经 `broker-action-queue` 单线出链，发一笔 **转给信箱地址的小额转账，payload = AEAD(交付物; 关联数据 = 订单地址)**（≤ 数百字节；链接/激活码足够）。
4. 买家页（静态页，已有）：凭据 → 重建订单地址（现成）→ 派生 `m`/`K` → `getUtxosByAddresses(信箱地址)`（公共节点，现成）→ 逐笔取得该 txid 的 payload → AEAD 解密成功者即交付物。
5. 状态：`delivered` 仅在信箱交易**落链确认后**写（NO TX NO STATE CHANGE，同 v0.1 §4）；`dm_txid` 字段改记 `mailbox_txid`。

**信任边界**
- 机密性 = **128 位 nonce 的保密性**。凭据泄露 ⇒ 交付物可被取（与"持有人凭证"同一模型，v0.1 §5.1 已接受）。
- 完整性：AEAD + 关联数据绑订单地址 ⇒ 任何人往信箱地址发的垃圾/伪造 payload 解不开即忽略；公共读服务**只能拒绝服务或重放旧密文，不能伪造或篡改**。
- ⚠️ **永久公开**：密文永久在链上。凭据日后泄露 ⇒ 历史交付物可被回溯解出。⇒ **不适用于需要撤销/高价值的秘密**；适用于"一次性激活码/下载链接，商家可令其失效"。这一条必须原样写进商家配置页提示。
- ⚠️ **读依赖第三方**：节点的 `getUtxosByAddresses` 只给 UTXO，**不给 payload**；取 payload 需要交易查询（公共 REST / Kasia indexer，`kasia-relay` 已在用 `api.kaspa.org` / `indexer.kasia.fyi` 两类）。**当前代码里没有"按 txid 取交易 payload"的现成函数**（`api.mjs` 只有 fee-estimate）——这是本方案最大的待验证点（§7-1）。缓解：多后端依次试；买家页允许手填 txid；自建 indexer 是后续选项。该依赖只影响**可用性与隐私（看得到谁在查哪个信箱地址）**，不影响机密/完整。
- 买家用交易所地址付款、没有任何 Kasia 钱包：**照常可取**——只需凭据与浏览器。

**成本**（估算，实现前须 simnet 实测，标 🟡）
- 每单一笔转账：网络费 ≈ 结构基线 + payload（`transaction.mjs estimateFeeReserve` 现公式 `payloadBytes×1000 + 200000` sompi 为**预留上界**；300 字节约 0.005 KAS 上界，实际下限实测应更低）。
- 信箱输出面值：受 KIP-9 存储质量约束，单个小输出不能太小（量级 ≥ 0.02–0.03 KAS，🟡 待测）；该面值**不损失**——卖家同样能派生信箱私钥，可事后回收（再付一笔网络费）；买家也可顺手扫走。净成本 ≈ 网络费 ≈ 几分之一美分量级的 KAS。
- 吞吐：无 `DAILY_SEND_LIMIT`（那是 Kasia 私信路径的 200/天/relay 限额，转账不走它）；走 `broker-action-queue` 单线，自然串行。
- 新代码量：relay 需一个**加性**入口让转账带 payload（现 `transfer` 命令无 payload 字段；`send_message` 是自转账语义不适用）；浏览器端 HKDF/AEAD 用 WebCrypto（静态页环境自带，🟡 待核）。

**新开对外端口：0。** console 仍只听回环；买家只出站访问公共节点/公共读服务。

### 4.A Kasia 私信拉取（V1.1 的推送候选，不推荐做主通道）
- 路径：买家钱包握手 → 私信凭据 → 卖家 relay 收到 → 回私信交付。
- 信任：Kasia 密钥交换端到端；读靠 Kasia indexer（第三方，同 B）。
- 成本：买家须有 Kasia 钱包并完成握手（主网 relay 入站握手自动接受**默认关**，D-027，需要运营开关或人工接受）；双向各一笔链上交易；受 `DAILY_SEND_LIMIT=200/天/relay` 限制；握手要付 `KASIA_MIN_AMOUNT`。**交易所用户/无 Kasia 钱包的买家用不了。**
- 新开端口：0。适合"已是 Kasia 用户"的推送，不适合当必达通道（与 v0.1 §5.2 一致）。

### 4.C 公网反代（仅在 B 被否决时）
- 路径：买家页 → 公网反代 → 白名单路由 → console 回环。
- 信任：把 console 前面加一道**默认拒绝**边界（`gap-A` 设计），取货路由内再校验凭据。攻击面 = 反代 + 该路由；一旦反代配置有误，573 条路由暴露。
- 成本：域名/证书/反代运行与监控、NWT 暴露面审、盘存卡新增一格；DoS 面；运营长期负担。
- **新开对外端口：≥1**（§6 单列）。与"第②档自跑节点、console 只听回环"的既定姿态相冲，故不推荐。

### 4.F Telegram bot 取货（可作 V1.1 的便利入口）
- 路径：买家把凭据发给 tg-bot；bot（出站轮询）经本机回环（机制 A 信封）调 console 的取货接口；回复交付物。
- 信任：**Telegram 看得到明文交付物与凭据**；bot 需持有取货 grant（窄 scope）。
- 成本：几乎零新开发（复用 tg-bot + 网关），但**属用户面，须 Owner 批**；买家须用 Telegram。
- 新开端口：0。**对"取货端点留在 console 内"这条是唯一不换形态的解**，可与 B 并存（B 为必达，F 为便利）。

### 4.G 出站推密文到静态托管
- 路径：卖家出站把密文写到某静态托管，买家页按订单地址哈希取。
- 信任：托管方只见密文；可用性依赖托管。
- 成本：需要外部账号与出站凭据（**新依赖、新密钥面**），与"不要把系统搞复杂"相左；链上方案 B 已经是"公共、无账号的存储"。**不推荐。**

## 5. 推荐

**V1 = 方案 B（链上加密信箱）为必达取货通道**；方案 F 与 A 作为 V1.1 便利/推送，均不依赖新端口。
理由：① 唯一同时满足"零新开对外端口 / 买家无需 Kasia 钱包 / 交易所付款可用 / 与 v0.1 的凭据模型同信任度"；② 复用面最大（relay 发 payload、静态页读链、凭据 nonce）；③ 把"公网够得到"这个问题**转化为买家本来就在做的事**（直连公共节点读链——结账页今天就这样），不改变 console 的暴露面。
代价必须说在前面：交付物密文**永久公开**、读 payload 依赖**第三方读服务**；不适合高价值/需撤销的秘密。

对 v0.1 的具体改动：§5.1 "取货端点"整段替换为 §4.B；§4 表 `dm_txid` → `mailbox_txid`；§5.2 私信推送不变（V1.1）；§9-2（取货端点重放）消失，换成本页 §4.5。

### 4.5 限速（裁定③在方案 B 下的落点）
没有 console 端点可限速；读链端的滥用只会打到公共节点/读服务。我们能控的是：买家页对同一信箱地址的轮询退避、手填 txid 兜底、不在页面里做并发枚举。**不枚举 nonce**（128 位）。

## 7. 实现前必须先做的 spike（不做就不进实现）

1. **读 payload**：公共 REST 与 Kasia indexer 是否都能"按 txid 取 payload"、返回字段、限流、对 simnet 如何替代（simnet 无公共读服务，测试需用本地可读 tx 的方式——待定）。**这是方案 B 的生死点**；若没有可靠的第三方读法，退回 F + A（或自建 indexer）。
2. 信箱输出的最小面值与实测网络费（simnet，本机 2.0.1，沿用本周的"节点拒绝文本取下限"方法）。
3. 浏览器 WebCrypto 的 HKDF/AEAD 与静态页 CSP/打包兼容（静态页 `vendor/` 已有 wasm 固定；新增依赖要进 pin 校验 `wasm-pin-check.mjs` 同类机制）。
4. relay 加性 payload 转账入口的写法（只加一个可选字段，三层注册，不进只读白名单）。

## 8. 测试清单增量（接 v0.1 §10）

单测：派生函数确定性（同 nonce+订单地址 ⇒ 同 K/信箱；换任一输入 ⇒ 全变）；AEAD 关联数据错/篡改密文/截断 ⇒ 解密失败；信箱里混入他人垃圾 payload ⇒ 忽略并仍取到真交付物；`delivered` 仅在信箱交易落链后写；抢先 `split` 三条件（deadline 前落链 / 金额精确 / 深度≥20）各自缺一 ⇒ 转人工（含边界两侧与变异）。
simnet：付款 → split → 信箱交易 → 买家页（模拟）仅凭凭据取到；换 nonce ⇒ 取不到；买家付款地址与凭据无关仍可取；watcher 中途杀掉 ⇒ 不交付、到期可退。
