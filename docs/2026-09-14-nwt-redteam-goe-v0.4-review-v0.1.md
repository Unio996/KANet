## 二、② 九步表证据逐步核——8/9 步可第三方核实，1 步(⑥)结构上只能是 Owner 自证，但这不是缺陷

逐步问"这个证据谁来核、能不能核假"：

- **①建/②验证/③停/⑤确认无拉起/⑦测第三条路径/⑧DELETE/⑨复核**：证据都是**可复现的命令输出**(DB行/PID/API响应/查询结果)，任何后续审计者(包括我下次复核)都能靠同样的命令重新验证一遍，不是"应该没问题"的断言。**这7步没有自证问题**。
- **④等90s**：证据只是两个时间戳，单独看信息量小，但这一步的**实质检查内容在⑤**（④只是等待窗口本身，不是检查点），不构成独立的自证问题。
- **⑥Owner备份确认关卡**：证据是"Owner的确认原话"——**这一步确实无法被任何 agent 独立核实**，但这不是设计缺陷，是这个机制**结构上唯一可能的形态**：备份内容本身按§2步骤3的既有纪律**不准经过任何agent的频道/ledger/scratch**（否则备份本身就先泄露了一次密钥），所以除了 Owner 亲口确认"我打开核对过、是对的"，**不存在任何不破坏"密钥不进agent视野"这条更基础纪律的验证方式**——要求一个可被第三方核实的证据在这一步等于要求密钥经过第三方，自相矛盾。**这一步的"自证"是代价，不是漏洞，我认可这是唯一可行的形态**。

**②判定：PASS，8/9 步经得起独立复现，第 9 步(⑥)的自证性质是密钥隔离纪律本身决定的必要代价，不是可以设计掉的缺陷**。

## 三、③ 确认关卡措辞是否堵住"说会存≠已核对"——PASS，原文措辞逐字核对属实

重读 §2 新增步骤 4 原文："**不是**'Owner 说了会存'就够，是'存完之后 Owner 自己打开核对过，确认那份备份是对的、能用'"——这句话**明确要求事后核对动作已经发生**（打开+核对+确认可用），不是事前承诺（会存/会记）。跟 Bettor 1126 那句"不是'说了会存'"的原话逐字对应，不是转述走样。**③判定：PASS，措辞真的区分了"承诺"与"已验证"这两件事，堵住了这条**。

## 四、④ 是否还有要求但没落的项——**两处会让第 4 条九步表实际执行不起来的机械缺陷，一处是我自己传染进来的错误**

**没有找到"我要求的东西没写"类缺项**（②的DELETE-vs置空比较已经在§2步骤7明确拒绝置空替代；③的确认关卡已经落地；④的实测硬门已经变成九步表；第三条路径已经写进条2）——**但独立重新核对文档引用的每一处坐标时，发现两处会让步骤⑦/⑧字面执行不起来的问题**：

**(a) 步骤⑦引用的 HTTP 路径错了，而且这是我自己 `fcc68351` 传下去的错**：文档写"`POST /api/settings` 传 `fixId=restart_relay_<id>`"——重新去查 `kasia-console/src/api/settings.js`，`applyFix` 真正挂的路由是 `fastify.post('/api/system/repair', ...)`（`settings.js:129`），**不是 `/api/settings`**——`/api/settings` 这个路径在全仓 `grep` 不到任何注册（我查了：`grep -rn "'/api/settings'" src` 零命中）。**这句错误是我自己 `fcc68351` 里先写的**（把"这个函数定义在 `api/settings.js` 这个文件里"跟"这个 HTTP 端点的路径叫 `/api/settings`"混成了一件事），KANet-UI v0.4 照抄了我的错误坐标。**如果真执行日照文档字面 `POST /api/settings` 发请求，会打到一个不存在的路由(404)，步骤⑦"实测第三条路径"这一步会直接失败，不是因为第三条路径不存在，是因为文档给错了触发它的地址**。修法：文档改成 `POST /api/system/repair`，body `{fixId: 'restart_relay_<relay_id>'}`（我这次重新读了 `system-repair.js` 的 `fixId.startsWith('restart_relay_')` 分支，确认这个 body 形式本身是对的，只有 URL 路径错）。

**(b) 步骤⑧的 `DELETE FROM relay_nodes WHERE id=?` 没有对应的安全执行接口**：查了 `kasia-console/src/api/relay.js` 全部 `fastify.delete(...)` 注册——只有 `/api/relay/:id/wallets/:walletId` 和 `/api/relay/:id/goals/:goalId` 两个子资源删除端点，**没有任何删除 `relay_nodes` 行本身的现成 API**。这意味着九步表步骤⑧字面上只能靠**直接对生产库跑手写 SQL**来完成——这跟"不准手插DB"这条项目既有纪律(临时脚本/直接改库历来是各种坑的根源，本会话前几轮也反复出现类似模式)是冲突的，文档目前对"这条 DELETE 具体怎么安全执行"完全没有交代(是关掉 console 后拿 sqlite3 CLI 操作？还是趁 console 活着用某个尚未写的 admin 端点？会不会跟 `better-sqlite3` 的 WAL 写锁撞车？)。**这不是"实测发现的坑"，是文档本身缺一步**——要求真执行前先把这条路径钉死（新加一个 `DELETE /api/relay/:id` 端点走既有代码审查纪律，或者明确写清楚"用哪个工具、在 console 什么状态下、谁来敲这条 SQL"），不能让九步表最关键的一步(销毁密钥)是唯一一个没写清楚"怎么做"的步骤。
