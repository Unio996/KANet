### 0.1 密钥拓扑——今天不是纯单机，但两台机器各自都未隔离
- **本机（生产 :3200 所在机，KANet-UI 直接查询）**：`kasia-console/data/console.db` `relay_nodes` 表 **32 个 relay 身份**，`is_oracle=1` 标记 **10 个**（现读，2026-08-07）。
- **J1tn 机（独立第二台，J1 现读，15:30Z 甩给本稿）**：11 个 relay，**3 个 `is_oracle=1`**（J1tn-TestOracle-1/2/3）。⚠ J1 自行更正："接位档记的'4 oracle'是错的，实测 3"。
- 🔴 **⇒ 今天已经存在两台机器，但这不构成隔离**：J1tn 那台自身仍是"1 台机持 3 身份"——3 把委员私钥共宿主 + 共同一个 `CONSOLE_ENCRYPTION_KEY` 解密 + 共一个 driver 进程可达（DECISIONS §5 已记：同机持多委员 relay 的节点，一个 driver 进程可依次取得该机全部委员签名、中间零独立检查）。**"有两台机器"≠"隔离"——真正要问的是任一台机器上，能不能凑够某个具体市场的 threshold，而不是"总共几台"。**
- ⚠ **`is_oracle` 是 per-machine 标志，不是 per-market quorum 归属**（J1/J2 2026-08-04 稿已证）——判定风险的正确单位不是"这台机器有几个 oracle 标志"，是"某个具体市场的委员会里有几把钥匙在这台机器上"（见 §0.2 判据 B）。
- **本稿 §0.2 的 63 这个数字是在【生产机】（本机）上测的**——J1tn 那台的 3 个 oracle 是否与那 63 个市场的委员会有重叠、重叠到什么程度，**本稿未核，标记 TBD，需 @J2 全网视角或再跑一次判据 B 覆盖 J1tn 机确认**。

### 0.2 63 这个数字的精确定义（判据 B，Bettor 2026-08-04 亲跑，255 个有 committee 记录的市场全量非抽样）
- **41 个市场 = 5/5**——整个委员会都在这一台机器上，threshold=4 连"少一个"的余量都没有。
- **22 个市场 = 4/x**——本机单机已可取得 ≥threshold 的签名。
- **合计 63 个市场，本机单机可取得 ≥threshold 签名**。方法：用生产谓词 `XOnlyPublicKey.fromAddress`（与 `pool.js:459` 同一匹配规则）逐市场比对 `committee_pks` 与本机 relay 地址。
- **目标（判据 B 重跑）：63 → 0**——降不到 0 视为改造未成立，这是可自证伪的指标，不能靠"改了很多"或换措辞满足。

### 0.3 两条候选路已裁定，不重新讨论
- 路-收权（P-收权，按角色收窄签名入口）**结构性达不到 63→0**——它不移动钥匙，只挡"守规矩的调用方"，绕不过入口的攻击面不受影响（2026-08-04 J2/J1 半稿已定量）。
- 路-隔离（P-隔离，本稿）是**唯一能让判据 B 归零**的路，代价主要在运维/部署层，不在代码层。

- **⇒ 隔离方案要同时回答两种失效模式**（Bettor 15:25 前、12:01 已钉死）：

  2. **liveness 面**：委员分散到多台机器后，任一台机器不可用（宕机/网络分区/运维故障）都可能让某个市场永久凑不齐 4-of-5——**隔离本身不解决，甚至可能加重**（今天单机反而"总能凑齐"，只是凑得太容易）。本稿只列这一面的成本/风险，**不替 Owner 拍具体解法**（委员副本？升级到有 timelock 的 V2？）。

## §1-8 八项交付

### ① 单一推荐基线
**推荐：拆成 4 个隔离签名域**（不称"4 个独立方"，理由见 §0 前言的三层概念钉死）。
- 依据：41 个市场是 5/5（全委员会同机），若拆成 4 台，任何单台最多持有该市场委员会的 1/5～2/5 把钥匙（视具体分配），**物理上够不到 threshold=4**。
- 4 是本稿给出的推荐值，不是唯一可行值（§2 给最低值对比）；4 台的选择理由：**故障域隔离**要求至少 threshold-1 台同时不可用才会撞上 liveness 问题。
- 🔴 **这条容错声称需要 hedge（NWT 红队 15:34Z 抓，鸽笼原理反例）**：5 把钥匙分到 4 个域，**至少有 1 个域会拿到 ⌈5/4⌉=2 把**——若恰好是那个域掉线，剩余可用签名者 = 5−2 = 3 把，**已低于 threshold=4**。**"4 域掉 1 台仍能凑够 4-of-5"不是天然保证，只在 §3 已标 TBD 的密钥分配算法把"多出的那把钥匙"分散得足够好时才成立**——本稿未给出该算法，因此这条容错声称目前只是**设计目标，不是数学保证**。
  - **备选（供 Owner 终拍时的额外权衡维度，非本稿现在选定）**：**5 个隔离签名域**（每市场每域至多 1 把钥匙）能把"任意 1 域掉线仍够 threshold"做成**数学保证**、不依赖分配算法，代价是比推荐值多 1 台机器。是否值得这多 1 台的成本换掉对分配算法的依赖，交 Owner 与 §⑧ 成本一起判断。

### ③ 最低与推荐拓扑
- **最低（技术可行下限）**：2 台，任一台持有 ≤(threshold-1) 把钥匙。对 threshold=4、5 把钥匙的市场，例如 2 台分持 2 把+3 把——单台够不到 4，判据 B 归零成立（NWT 15:34Z 核：原例"2 台各持 2 把"2+2=4≠5，算术对不上，已改）。**但 liveness 极脆弱**：2 台里 1 台不可用 = 该市场立即无法达到 threshold（除非委员本身在剩余台上凑够，视具体分配）。
- **推荐（§①）**：4 台。给出 threshold-1=3 台的容错冗余空间（任意 1 台掉线仍可能凑够，视具体密钥分配策略）。
- **本稿不拍死密钥在多台之间的具体分配算法**（哪个委员的哪把钥匙放哪台）——那是落码 spec 阶段的工作，取决于 §4.1 类型闸何时落地、以及具体委员会成员集合是否稳定。

### ④ 同宿主 / 同管理员 / 同恢复凭据各破坏什么
| 共享维度 | 破坏的性质 |
|---|---|
| **同宿主**（同一台物理/虚拟机） | 直接破坏**密钥隔离**——单点入侵/单机宕机同时影响该主机上全部签名域，判据 B 不归零 |
| **同管理员**（同一个人有多台机器的 SSH/RDP 权限） | 破坏**故障域隔离**的一半——管理员账号被钓鱼/胁迫 = 攻击者可能横向拿到多台机器的密钥，即使物理机器不同 |
| **同恢复凭据**（多台机器的备份/恢复用同一份密钥或同一处存放） | 破坏隔离的**长期有效性**——即使日常运行时钥匙分散，一旦发生"恢复"操作（见 §5），若恢复凭据集中，攻击者拿下那一份凭据就等于拿下全部，隔离在平时成立、在灾难恢复那一刻失效 |
- **三者任一被违反，隔离退化为"看起来隔离"**——这正是 timetable v2 §1 那句"部分完成的收权等于没收"的镜像：部分完成的隔离（比如物理机分开了但管理员共享、或恢复凭据集中）在被攻破那条链上等于没隔离。

### ⑤ 生成-备份-轮换-恢复-急停规程（骨架，非可执行 runbook）
- **生成**：新宿主上的签名密钥应在目标宿主本地生成（不在本机生成后再传输，传输本身是暴露窗口）。
- **备份**：**本项与冷备线（task #5）part 部分重叠但不同**——冷备线备份的是 `console.db`/`CONSOLE_ENCRYPTION_KEY`（运营方数据库侧），本项是**各签名域自己的私钥备份**，两者的托管形态可能不同（分布式密钥更适合每个域各自独立备份到各自的离线介质，不建议汇总到一处）。**这与 §4"同恢复凭据"的警告直接相关——若图省事把 4 个域的备份都存到同一处，隔离白做。**
- **轮换**：需要一套"某个宿主怀疑被攻破时如何在不停机结算的情况下换钥匙"的流程——**本稿标记为 TBD，需要与 D-012 §6-1 Oracle 权限边界契约（J1 主笔中）对齐**，因为换钥匙涉及"谁有权认定某个宿主该被踢出委员会"这个契约层问题，不是纯运维问题。
- **恢复**：见④"同恢复凭据"警告；具体恢复演练设计建议复用 task #5 冷备线已确立的方法论（quiesce 后 cp、byte-exact 校验），但作用对象不同（私钥 vs DB）。
- **急停**：需要一个"发现某宿主异常时能立刻让它退出签名资格而不影响其余 3 个域正常运作"的机制——**这正是 §4.1 持钥侧类型闸要解决的问题的一部分**，本稿不重复设计，只标注依赖。

### ⑦ 63→0 准确分母与前后向量
- **分母**：255 个有 committee 记录的市场（全量，非抽样，2026-08-04 判据 B 读数）。
- **前向量（今天）**：63/255 个市场本机单机可取得 ≥threshold 签名（41 个 5/5 + 22 个 4/x）。
- **后向量（隔离施工完成后，预期）**：0/255——用同一套判据 B 脚本重跑，任何市场的委员会 pk 集合在任一单台宿主上匹配数都 <threshold。
- **验证方法**：施工完成后，**必须用同一段代码、同一个判据脚本**重新对全部 255 个市场跑一遍（不能只抽样，2026-08-04 那次也是全量），这是本项目里少数已经存在"改造前"读数、可以做真正 before/after 对比的验收点。
