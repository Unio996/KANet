# 波 0「第二台机」骨架页 v0.1（2026-09-13 · KANet-UI · Bettor 派工，只做骨架不展开）

> **Status: OPEN（骨架·待 Owner 波 0 GO 后细化）**。权威源：ledger (998) S-2 提案 + `docs/2026-09-07-bettor-mainnet-pivot-assessment-v0.1.md` §0/§3/§5/§6。本页只整合，不新增判断；Owner 未拍波 0 GO 前不落地任何采购/装机/config 动作。

## 1. 用途（S-2 与波 0 合一，不是两台机）
一台第二台机同时承担两个角色：
- **TN12 前向节点 N2**（S-2 提案，ledger 998）——补上"全网只有一个前向 peer 且会失联"的病；
- **主网只读 pruned 节点**（评估 v0.1 §3 波 0）——转向主网的第一步，零资金、只读接入。
两者合一是评估文档 §3/§5 已定的口径（"不在同一台机上跑第二个 kaspad"指的是本机，不是禁止第二台物理机跑两个网络的节点）。

## 2. 规格（两处口径不完全一致，原样列出，未调和）
| 来源 | RAM | 磁盘 | 备注 |
|---|---|---|---|
| ledger (998) S-2 | ≥32 GB（可用 `--rocksdb-cache-size=2048` + `--ram-scale=1.0` 压到 ~10–14 GB） | ≥250 GB | 只 TN12 单节点估法 |
| 评估 v0.1 §3 表格行 | ≥32 GB | ≥300 GB | 波 0 单条目里写的"与 S-2 合一" |
| 评估 v0.1 §5 正文（本机并跑不可行段） | ≥32 GB | **≥1 TB SSD** | 明确写的是"TN12 + 主网各一台"这台机的总量，与前两行的单节点数字不是同一统计口径 |

🟡 **未调和之处（骨架阶段标出，不擅自定论）**：≥250/300 GB 是 S-2 单 TN12 节点的估法；≥1 TB 是"这台机要同时跑 TN12 N2 + 主网 pruned 节点"两个 datadir 相加后的量。哪个是最终采购口径待细化时按"两个节点各自磁盘估 + 余量"重算，不是三选一。
上行带宽：998 只给了 TN12 侧 ≥10 Mbps，主网侧尚无估。

## 4. 主网只读节点资源估（评估 v0.1 §2 第⑤条，仍是"待核"状态，未细化）
- 软件：上游 v2.0.1 官方 release（`kaspad --utxoindex`），非本机 1.1.1-toc.1 分支（其主网参数 `covenants_activation=never`，不能用于主网）。
- 硬件：评估原文写"Toccata 硬件规格上调（transient mass ×2 允许 ZK-STARK），pruned 磁盘/内存数字待 J2 按 elldeeone 报告核；本机 TN12 datadir 138 GB、kaspad WS 15–28 GB 可作下界"——**这条本身就是待办，本页不重复造数，等 J2 那份坐标**。
- 端口：可与 TN12 节点共机分开（评估 v0.1 §5：主网 16111/17110 vs TN12 16311/17210），不冲突。

## 5. 装机路径（骨架，未细化步骤，等 GO 后再出可执行 runbook）
