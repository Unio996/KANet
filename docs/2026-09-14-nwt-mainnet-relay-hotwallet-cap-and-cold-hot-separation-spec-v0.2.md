> **Status**: DRAFT-FOR-REVIEW v0.2（2026-09-14 · NWT · docs only，只写规格不落码不执行）
> 承接 `docs/2026-09-14-nwt-mainnet-relay-hotwallet-cap-and-cold-hot-separation-spec-v0.1.md`（v0.1，`749cc045`）。
> **v0.2 变更**：Codex 桥 `73f42bf3` MUST-FIX（Bettor 1138 采纳）——v0.1 的三条检查全部只在 `startRelay()` 那一刻
> 生效，是**准入上限**不是**持久硬上限**：relay 一旦启动，运行期间收到入账可以把余额推过 800/1000，私钥仍在进程
> 内存里，v0.1 完全没有覆盖这个窗口。本稿补上驻留期持续监控 + fail-closed + 超限处置 + 聚合准入的并发安全。

## 0. 一句话

**准入检查解决"一开始就不该放进来的"，驻留期检查解决"进来之后被塞大了的"——两者都要有，且都要 fail-closed，
聚合准入的并发竞态用一把进程内互斥锁堵死，不用"越查越准"的缓存技巧去逼近正确性**。

## 1. 驻留期监控——独立于健康监控，不能被 `RH_OFF` 连带关掉

**不复用 `relay-health-monitor.js` 的 tick 本身**（那个文件的存在意义是"进程死没死"，`RH_OFF=1` 关掉它是给
调试用的一个已知开关——**如果把资金上限检查也塞进同一个 tick，任何人出于跟资金无关的理由设 `RH_OFF=1`，会
连带把安全监控也关掉，这是一个不该存在的耦合**）。

**新增独立文件 `kasia-console/src/services/relay-hotwallet-monitor.js`**，结构镜像 `relay-health-monitor.js`
（同款 `setInterval`/`STARTUP_GRACE_MS`/`running`互斥标记防重入这套已验证过的既有模式，不发明新范式），但：
- **复用同一个共享 RPC 客户端**（`getSharedRpc`，跟 v0.1 §5 查余额用的是同一份，不新开连接——这条是 Bettor
  1138 原话"同一本地RPC"的字面要求，也避免重蹈 `kaspa-wasm RpcClient` 每实例泄漏内存那个已知坑）。
- **开关名不叫 `RH_OFF` 或任何看起来像它的名字**——建议 `HOTWALLET_MONITOR_OFF`，且**默认不允许被随手设**：
  这是资金安全监控，不是调试便利开关，`index.js` 里启动这个 tick 的那一行不应该用 `!== '1'` 这种轻量判断
  就放行关闭——应该要求同时设 `HOTWALLET_MONITOR_OFF=1` **且**打印一行明显的 LOUD 警告日志（"资金监控已手动
  关闭"），不能悄无声息地跟其它开关一样一行 env 就关掉不留痕迹。
- **只在设置了 v0.1 §3 的两个 cap（`RELAY_HOTWALLET_PER_RELAY_MAX_KAS`/`RELAY_HOTWALLET_TOTAL_MAX_KAS`）时才
  启动这个 tick**——没设 cap 就没有"超限"这个概念，跟 v0.1 §5 的"未设 env=不启用该项检查"是同一个原则，
  不是这次新发明的例外。

**Tick 内容**（每次 tick，遍历 `_relays` 里 `child` 存在的条目，即"当前真的活着"的那些）：
1. 对每个活着的 relay，查一次真实链上余额（同 v0.1 §5 的 helper）。
2. **单个余额超 `RELAY_HOTWALLET_PER_RELAY_MAX_KAS`** ⇒ 触发 §2 的处置。
3. **所有活着的 relay 余额加总超 `RELAY_HOTWALLET_TOTAL_MAX_KAS`** ⇒ **不是全杀**——按"最后一个把总量推过线的
   relay 负责"的原则（比较这次 tick 与上次 tick 的总量差异，找出余额新增最多的那个/那几个，从大到小依次触发
   §2 处置直到总量回到线下）；如果无法归因到具体某个relay（比如多个同时到账、差异难以精确分配），保守起见对
   **全部**当前活着的relay都触发处置——**宁可误伤停一批也不留一个真超限的活着**。
4. **余额查询失败（RPC错误/超时）**——不是"当作没变化跳过"，记一次失败计数（per-relay）；**连续 3 次**失败
   （同 `MAX_RESTART_PER_HOUR=3` 那条既有阈值的量级，不是随手拍的数字，用同一个"3次"避免因为单次RPC抖动就
   误杀，同时不允许无限期容忍查不到）⇒ 触发 §2 处置，日志明确写"余额查询持续失败，fail-closed"，不是因为
   "超限"触发，是因为"验证不了没超限"触发——**这条纪律本身就是 fail-closed 的核心：查不到=当作可能超限处理，
   不是当作没超限处理**。

## 2. 超限处置——kill 进程，不新增"隔离标记"字段，不自动转移资金

**动作**：立即 `Stop-Process`/kill 该 relay 的子进程（`relay-manager.js` 的 `_relays[id].child` 已经是既有可
调用的 kill 路径，不需要新写）——**这是唯一真正解决"私钥在内存里"这件事的动作**，其余都是记账/通知。

**为什么不需要新增一个"quarantined"标记字段**：v0.1 §5 已经把余额检查钉在 `startRelay()` 里，作为**每一次**
启动尝试（不管是谁触发的：手动/`startAll`/health-monitor/`system-repair`）**都要重新过一遍**的准入门——一个
relay 被本节杀掉之后，**只要它的余额仍然超限**，任何后续想把它拉起来的尝试都会在 `startRelay()` 那一步被同一
条既有检查挡下来，不需要额外一个"这一行被标记过"的状态。**这条只在"余额之后又降回线下"时会自动解除**（比如
Owner 手动把超限的钱转走了）——这正是期望行为：限制的是"钱在不在这个进程里"这件事本身，不是"这一行历史上
出过事"这件事，不应该让一次超限永久烙印这一行。

**不自动转移超限资金——这条明确排除在 v0.2 范围外**：把"多出来的钱自动扫到别处"做成自动化动作，本身就是
**新增一条自动化的资金移动路径**——这正是本规格从第一版就在防的那类东西（v0.1 §6："转账限额不该混进这次的
'导入前置'审查...如果Owner认为也需要给relay转账加类似上限，应该是另一条独立规格"，同样的边界现在再画一次：
**检测到超限=杀进程+响亮告警，钱原地不动，怎么处理这笔钱是 Owner 的决定，不是这个监控脚本自己拍**。自动清扫
这条如果 Owner 真的想要，必须是一次独立设计+独立红队审查，不能作为这次"修 TOCTOU 漏洞"的附带产物夹带过去。

**告警**：kill 动作发生时，除了本地日志（`console.error` 级别，不是 `warn`），**必须**同时写一条到 KANet 现有
协调频道/ledger 机制（同这个团队日常用 SendMessage/COORD-LEDGER 那条既有信道，不新造通知渠道）——理由：kill
动作本身对这个团队(Bettor/KANet-UI/Owner)是需要立刻知道的事件，不能只是安静地写进一个只有事后才会去翻的日志
文件里。

## 3. 聚合准入的并发竞态——进程内互斥锁，不是"更频繁地查"

**问题精确复述**：`startRelay()` 的聚合上限检查是"查一次当前所有活着relay的余额总和 + 候选自己的余额，跟
`RELAY_HOTWALLET_TOTAL_MAX_KAS` 比"——如果两个`startRelay()`调用（不同relay、几乎同时触发）都在"查总和"这个
异步操作完成之后才做判断，两边各自看到的"总和"都不包含对方即将新增的那部分，**各自单独判断都合法，合起来会
超限**——这是一个真实的检查-决定之间存在异步间隙(TOCTOU)导致的竞态，不是理论上的洁癖。

**修法：一把进程内的异步互斥锁，锁住"查总和→做决定→（如果决定放行）视为已占用这部分额度"这个临界区**：
```js
// relay-manager.js 模块级
let _admissionLock = Promise.resolve();
async function withAdmissionLock(fn) {
  const prev = _admissionLock;
  let release;
  _admissionLock = new Promise(r => { release = r; });
  await prev;
  try { return await fn(); } finally { release(); }
}
```
`startRelay()` 里聚合上限那一段检查（查总和+比较+决定是否放行）整段包进 `withAdmissionLock(...)`——**不是给
整个 `startRelay()` 加锁**（那样会让"起 relay"这个动作彼此排队变慢，没必要——真正需要互斥的只是"查总和+做决定"
这一小段，子进程 `fork()` 本身可以在锁外做），效果是：**任意时刻只有一个"聚合准入决定"在进行，第二个必须等
第一个决定完（放行或拒绝）才能开始查自己的总和**——这样每次决定看到的"总和"都已经把前一个刚放行的relay算
进去了，不会漏计。

**这把锁本身成本极低**（起relay不是高频操作，一天可能几次到几十次，排队等一次余额查询的网络延迟不构成实际
瓶颈），**用锁是消除竞态本身，不是把竞态概率降低**——不采用"30s缓存+保守余量"这类只是把竞态窗口缩小/把误判
概率降低的方案，因为那些方案在足够巧合的时机下仍然会犯错，锁没有这个"仍然会"。

**保留 v0.1 §5 已经写的"未设cap=不启用"这条**——没设总额cap的话，这个锁和这段检查根本不会跑，跟v0.1的既有
写法一致，不是这次新引入的例外。

## 4. 与 v0.1 的关系——不改 v0.1 已定的部分

- v0.1 §1（真实分布）/§2（冷/热分类）/§3（800/1000两个数字）/§4（冷清单）/§7（分批策略）**全部不变**。
- v0.1 §5（`startRelay()` 准入三检查）**保留，是本稿§1-3的前提**——驻留期监控解决的是"进来之后"，准入门解决
  的是"进来之前"，缺一个都不完整，两者不是二选一。
- v0.1 §6（为什么不在`sendCommandAsync`加限额）**论证同样适用于本稿**：驻留期余额监控关心的是"这把私钥值不
  值得继续活着"（存在性风险），不是"这一笔转账该不该被拦"（流量风险）——本稿没有新增任何转账拦截逻辑，
  跟 v0.1 §6 划的界线一致。

## 5. 待 Owner/Bettor 拍板的开放项（追加）

- §1 的 tick 间隔本稿没有给具体数字建议——`relay-health-monitor.js`现有30秒是"进程死活"这类需要较快响应的
  场景定的，资金余额变化的响应时效要求可能不需要这么快（也可能需要，取决于Owner对"暴露窗口"的容忍度），
  这个数字留给KANet-UI落码时参考现有30秒定一个初始值，不是本稿钉死的安全参数。
- §2 的"归因到具体relay"逻辑（tick间差异比较）在多个relay同时到账时的精确判定，本稿只给了"无法精确归因就
  保守全杀"这条兜底原则，具体比较算法留给实现时定，不是安全性质本身需要现在钉死的部分。
- §3 的锁如果发现给 relay 启动增加了不可接受的延迟（本稿判断不会，但没有实测数据），需要重新评估——本稿的
  论证是定性的，KANet-UI落码后应该跑一次多relay并发启动的真实计时。
