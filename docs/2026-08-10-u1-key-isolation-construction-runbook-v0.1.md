## §0 推荐基线（原样确认，不改）
- 拆成 **4 个隔离签名域**（域 1=现状机器留一部分，域 2/3/4=新增独立宿主）。
- 4 是推荐值非唯一可行值；容错声称需要 hedge（鸽笼原理：5 把钥匙分 4 域，至少 1 域拿 ⌈5/4⌉=2 把，该域掉线时剩 3<threshold=4）——数学保证需要 5 域，多 1 台机器成本换取不依赖密钥分配算法的保证。**这个取舍是 §3 D1。**

## §1 现在就能做的（不等 Owner 答复，零风险、不可逆动作为零）

### 1a. 域→relay-ID 映射记录格式（回退 runbook §0.1 的依赖，本稿直接把它定下来）
建施工时用的记录表，不需要等硬件到位就能建表：
```sql
CREATE TABLE IF NOT EXISTS u1_domain_assignment (
  domain        INTEGER NOT NULL,      -- 1/2/3/4(/5，若 D1 选 5 域)
  relay_id      TEXT NOT NULL,
  host_label    TEXT NOT NULL,         -- 人类可读的宿主标识，不是 IP(IP 会变)
  assigned_at   TEXT NOT NULL DEFAULT (datetime('now')),
  PRIMARY KEY (domain, relay_id)
);
```
建这张表本身零风险（新表，不改任何既有表/既有行为）。**建议施工正式开始前先建好**，第一台新宿主生成第一把密钥的那一刻起就有地方记，不要等到"回头需要回退时才发现从来没人记过这份映射"。

### 1b. J1 现有节点机的安全基线核查（域 4 候选，与"谁来运营"无关）
scoping §2 备注写"J1 节点今天定位是健康、不载生产、isSynced 的读研究节点——若要兼职当签名宿主，需先过一轮独立的安全基线核查，本稿不预设它合格"。**这项核查本身不需要等 Owner 拍"要不要用它当域 4"**——核查的是这台机器现在的安全状态（谁有访问权限/密钥托管方式/网络暴露面），是一个事实问题，不是决策问题。**建议 @J1 或 @NWT 现在就能开始**（不在本次派工范围内，本稿只标出这项不必等待）。

## §2 施工步骤（每一步排在 §3 对应决定项答完之后，标注依赖）

1. **采购/配置新宿主**（依赖 D3：物理自购 or 云托管豁免；依赖 D2：运营方人选，因为谁来经手采购是运营方决定的一部分）。
2. **在目标宿主本地生成委员密钥**（scoping §5 已定：不在本机生成后传输，传输本身是暴露窗口）——依赖 §1a 那张记录表已存在、依赖具体密钥-委员分配算法（scoping §10 项 1，落码 spec 阶段工作，不是 Owner 决策项，但需要 §4.1 持钥侧类型闸的进度配合，见 D-012 主稿 §6）。
3. **划出域 1 现有 relay 的一部分**（本机 32 个 relay 中哪些留、哪些逻辑上归入新域——这是密钥分配算法要回答的，同上依赖同一项）。
4. **验收**：施工完成后，对全部 255 个市场重跑判据 B 脚本（scoping §7 已定方法论：同一套判据脚本，全量非抽样），确认 63→0。这是施工的唯一验收标准，此前的所有步骤都是准备。

**本稿不代写步骤 1-3 的具体命令**——它们依赖 §3 的答案，答案落地前写出来的命令是编的，不是可执行的。
