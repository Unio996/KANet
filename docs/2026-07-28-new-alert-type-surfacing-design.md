# 新告警型别冒头机制 — 设计 v0.1(未审·零落码)

> **Status**: CURRENT
> 依据:Bettor 2026-07-28 裁定(暴露面盘存卡 §3 处置①)· 判据用原话:
> **「一条从没见过的告警,必须在 N 分钟内出现在有人读的地方。」**
> 🔴 本文件是设计,不是码。**而下面每个数字都是我实测的,不是估计。**

## 一、先量,再设计(这一节决定了整个形状)

```
scope=system 告警级 distinct 型别总数        : 28
首次出现落在最近 24 小时内的型别数           : 【0】
首次出现落在最近 7 天内                      : 【2】(rpc_health_check_failed · rpc_health_degraded_onset)
过去 24h 告警级事件总量                      : 4,411 条(≈184 条/小时, 前 3 型占 75.1%)
```
🔵 **⇒ 决定性的一格:新型别的到达率约【每周 2 个】,而不是每小时几个。**
⇒ 这机制**不会刷屏**,一条播报一笔链上费也完全付得起。**若这个数是每天几十,整个方案该换形状** —— 所以先量。

🔴 **两格我顺手核了,它们支撑上面这些数**:
```
① events 表【没有清理机制】(全仓仅测试文件里有 DELETE FROM events)
   ⇒ MIN(created_at) 确实是"有史以来第一次", 不是"保留窗内第一次"
② created_at 这一列【混了两种格式】: 173,184 行里有 3 行是 Unix epoch 数值不是 ISO 串
   🔴 而 SQLite 里 created_at >= datetime(...) 是【字符串比较】⇒ 那 3 行永远不会被匹配到
   ✅ 但它们全在 scope='admin', 落在本机制口径(system + 告警级)内的是【0 行】⇒ 上面的数不受影响
   🔨 而实现仍必须显式限定 ISO 格式, 否则哪天有人往 system 里写一个 epoch, 它会【静默消失】
```

## 二、机制(尽量不新造东西)

**"新型别"的定义 — 无状态,不需要新表**
```sql
SELECT event_type, MIN(created_at) AS first_seen, COUNT(*) AS n
  FROM events
 WHERE event_scope='system' AND level IN ('error','warn','critical')
   AND created_at LIKE '____-__-__%'          -- 🔴 见 §一②: 显式挡掉非 ISO, 不让它静默消失
 GROUP BY event_type
HAVING first_seen >= datetime('now', ?)        -- 窗口, 建议 7 天
```
🔵 **它没有"已见过型别表"这种状态** ⇒ 不存在"状态跑偏了怎么办""重启后要不要重建"这类问题。

**去重(避免自己变成复读机)**:每播报一个型别,写一条 `new_alert_type_announced` 的 marker 事件(payload 记该型别);下一轮排除已有 marker 的型别。**复用 events 表,零迁移。**

**冒头去哪**:协调频道(**它有读者** —— 盘存卡 §3 实测:三处读者里只有它是推送式)。

**上界**:每轮最多播报 K 条(建议 3)。**超出的不丢,记一行带分母的日志**:「本轮 N 个新型别,已播报 3,余 N-3 下轮」。
🔴 **不许出现"本轮 0 个新型别"与"本轮没跑"读数相同的情形** —— 本仓已栽过两次。

## 三、🔴 而 Bettor 那个必答题:「它没跑的时候,谁会知道」

**我不粉饰:一个独立的新 daemon,答不上这一题。**
```
它安静时的读数 = 它死了的读数 = 逐字相同(本仓已记死: 自我报告的健康机制, 沉默 == 正常 ⇒ 绿灯从无意义)
而"每周 2 个"意味着它可以【死一整周而没有任何人察觉】—— 沉默正是它的常态
```
🔨 **⇒ 所以我不建议新起一个 daemon。三个方向,我给推荐,但归你拍**:
```
✅ (甲·推荐) 把这段检查【折进一个已经在跑、且它死了会被发现的 tick】
   ⇒ 宿主死 ⇒ 宿主自己的症状先出现 ⇒ 不需要为本机制单独造一个"谁看着看门人"
   🔴 我【还没定】折进哪一个: 要挑一个"它死了真的有人会发现"的宿主,
      而按盘存卡的结论, 这个前提本身要一个一个核 —— 我不凭印象挑
(乙) 独立 daemon + 每轮心跳带分母
   🔴 而心跳写去哪? 写 events = 又一个没人读的行; 写频道 = 每轮一笔链上费
   ⇒ 除非有人真的会看那个心跳, 否则它只是把同一个问题往下推一层
(丙) 拉取式: 不推送, 改成【有人打开 /events 时】顶部显示"最近 7 天新出现的型别"
   ✅ 没有 daemon ⇒ 不存在"它死了"这件事
   🔴 而它不满足判据的前半句(「必须在 N 分钟内出现在有人读的地方」)——
      它只在有人主动去看时才有效, 而今天的问题恰恰是没人主动去看
```
🔵 **我的判断**:(甲) 是唯一同时满足"有推送"和"死了会被发现"的;而 (丙) 可以**附加**做,成本近零。
🔴 **但 (甲) 的前提是先挑出宿主,而挑宿主要逐个核"它死了谁会说" —— 这一格我还没做,不假装做过了。**

## 四、验收判据(带对照臂)

```
① 造一个【库里从没出现过的】event_type 写一条 ⇒ 必须在一个 tick 内被播报出来
   🔴 对照臂: 同时写一条【已存在型别】的事件 ⇒ 必须【不】被播报
   ⇒ 两臂都要, 否则分不开"它工作了"与"它把什么都播报出来了"
② 同一个新型别再写第二条 ⇒ 必须【不】重复播报(marker 生效)
③ 上界: 一次造 5 个新型别 ⇒ 播报 3 条 + 一行带分母的"余 2 下轮"
④ 🔴 格式臂: 写一条 created_at 为 epoch 数值的 system 告警 ⇒ 它【必须】被显式排除且记一行,
   而不是静默消失(§一② 那个坑的回归守卫)
```

## 五、我填不了 / 不打算填的格

- 🔴 **宿主选谁**(方向甲)——要逐个核"它死了谁会说",我没核。
- 🔴 **N 分钟里的 N**:判据写着"N 分钟内",而 N 该是多少取决于**最坏情况下一条新告警意味着什么**。而这一格没人定过,我不替它定。
- 🟡 **窗口取 7 天还是 24 天**:我实测 24 小时窗口今天返回 0、7 天窗口返回 2。**7 天更有信号,但一个 7 天窗口在冷启动那一刻会一次性吐 2 条** —— 可接受,但要知道会发生。
- 🟡 **`level` 的取值集**:我用 `error/warn/critical`。而库里是否还有别的 level 值我**没有穷举**,只按盘存时看到的三种写。
