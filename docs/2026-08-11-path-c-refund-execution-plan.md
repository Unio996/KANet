### 🔴 §1.2 关键澄清：退款不需要 `side_lock_daa`，"链上派生永久不可得"不等于"钱不可退"

这条是本稿存在的理由，必须先说清楚，否则整份计划的框架会被读错。

**A-3 §3 证明的是**：`side_lock_daa` 被 `canonicalBetOrder`（`pool-payout-root.mjs:66-76`）当排序键喂进 `betsRoot`，而 `betsRoot` 由每个委员**各自独立重算**——排序键缺失 ⇒ 委员算不出同一个根 ⇒ **正常的胜负结算路径**（谁赢、payout 怎么分）走不通。

**而退款是另一条路径，现读 `pool-refund-builder.mjs`（bshard `refund_draw`，J2 2026-06-15 已建）确认**：
- 退款 TX 只需要 `bettorPk`、`stake`、pool/ticket 的当前链上 state——**不读、不用、不校验 `side_lock_daa`**。
- 链上门槛（`b1e9ca14` 已实测过的 covenant weld）只有两条：`require(closed != 1)`（未被结清/取消过）+ `require(tx.time >= (deadline+7200)*1000)`（超时门，deadline 早已过，这 9 盘全部满足）。
- 🔴 **退款在链上是 permissionless**——代码注释原话："**no sig — anyone may trigger**; funds go to the ticket's bettor via `P2PK(tk.bettorPk)`"。**不需要 4-of-5 委员签名。**

**⇒ 三条推论，撑起本稿整个框架**：
1. **"链上派生永久不可得"这句判死的是胜负结算，不是退款**——退款从代码/链上门槛看，今天就能做，不受 side_lock_daa 缺失影响。
2. **本稿的执行范围是"这个市场/分片下的全部持仓行"，不是"side_lock_daa 为 NULL 的那部分行"**——上表"NULL 行本金"列只回答"A-3 那份 side_lock_daa 排查覆盖了多少"，**不是退款要处理的分母**。退款按市场/分片整盘处理，覆盖全部 `pool_bettor_sides` 行（含那些 side_lock_daa 已有值的行）——这正是 §0 红线"零排除"的技术含义：**不能因为一行的 `side_lock_daa` 是齐的就把它排除在这次退款之外**，这个市场既然整体判了路 C（链上派生不可得导致无法正常结算），就是整盘退，不是挑行退。
3. 🔴 **正因为链上无需签名即可触发，"V2 退款触发器不自动化"这条政策不是技术限制，是纯操作纪律**——技术上任何持有一个 relay 私钥的人现在就能对任一符合超时门的 bshard 市场发起退款，代码不拦。**唯一的闸是人**：本稿 §2-S5 那道"操作员显式逐盘授权"，就是整个安全模型此刻唯一起作用的那道门，必须严格执行，不能被读成形式流程。

**这条澄清本身标 `[CONFIRMED · 现读 pool-refund-builder.mjs 全文 + b1e9ca14 covenant weld 注释]`**——不是推断，是读了实际实现代码的结论。**唯一未验证的部分见 §5.1。**

## §2 通用执行框架（S1-S7，比照今晚 canary#2/9jaty 计划的规格）

**本框架适用于 9 盘中的任意一盘（kr5l4 除外，见 §4 单列）。每一步的输出都必须原文贴出，不摘要、不代读。**

### S1 · 市场状态只读确认（零写入）
- 查 `pool_markets`：`protocol_status`、`settle_txid`（须为 NULL）、`deadline`/`deadline_daa`。
- 查该市场（或该分片，若是 bshard）当前链上 pool UTXO 的 `closed` 字段（须为 `0`——若已是 `2`，说明已有人退过，停止，转异常处理，不得对同一个 pool 重复触发首笔退款）。
- 复核该市场仍在 §1.1/§1.3 最终确认名单内（防止名单在写作与执行之间又变过）。

### S2 · 持仓枚举（零写入，红线§0-1 的技术兜底）
- `SELECT * FROM pool_bettor_sides WHERE market_id = ?`（bshard 则遍历该市场全部 shard_id）——**取全部行，不加 `side_lock_daa IS NULL` 过滤**（见 §1.2 推论 2）。
- 对每一行记录：`bettor_pk`、`stake_amount`、`side_p2sh`、`side_lock_tx`、`claim_txid`（须 NULL）、`refund_attempted_at`（须 NULL）。
- 汇总：本盘应退总额 = `SUM(stake_amount)`，应退人数 = 去重后的 `bettor_pk` 数。**这两个数字是 S7 验收要对齐的基准，必须在 S5 授权申请里一并贴出。**

### S3 · 零排除核对（红线§0-1 的直接执行）
- 用 S2 枚举出的行数/人数，与 S1 该市场（或该 bshard 全部分片）的官方持仓统计（若有独立的 `pool_markets` 侧汇总字段，或 A-3/其他既有稿子里对该市场的行数陈述）交叉核对。**任何差异必须在授权申请里显式标出并说明**，不得静默吞掉。
- 明确写出："本次退款覆盖 N 人 / M KAS，零人被标记为排除。"——这句话是 §0 红线要求的可审计留痕，每次执行都必须原样出现。

### S4 · Dry-run 交易构造（零写入，零广播）
- 对 S2 枚举出的每一行，用 `buildRefundWitness()` + `buildRefundCommand()`（`pool-refund-builder.mjs`）构造 witness/command，**不发送给 relay，不广播**。
- 内置自校验会跑：`blake2b(prefix‖suffix) == ps_tmpl_hash`（模板哈希自检）+ value-conserve（`payout + pool_out == pool_value`）。**任一行自校验失败 → 停止整盘，不得跳过该行继续处理其余行**（否则等于对失败行做了静默排除，撞 §0 红线）。
- dry-run 产出的构造结果（不含私钥/签名）应作为 S5 授权申请的附件贴出。

### 🔴 S5 · 操作员签发机器可验授权 artifact（**唯一的闸，见 §1.2 推论 3——rev-2 起从"程序性"改为"机器强制"**）

> **rev-1 → rev-2 改了什么，为什么**：rev-1 把这一步写成"操作员在频道贴出批准 + 审计留痕"——Codex 红队（ebe3417e，2026-08-11）指出这是**程序性**（procedural）而非**机器强制**（machine-enforced）：只要执行路径（builder/relay）从不真正读取/校验这份"批准"，它就和"审计日志≠执行路径消费它"（今晨 CIS role_code 那条同族教训）是同一个洞——**因为 §1.2 已经证明退款在链上是 permissionless，此刻唯一挡着"谁都能触发"的就是这一步，若这一步本身不是机器强制，那么全篇的安全模型实际上是 0 道闸，不是 1 道**。这条改动不改变 V2 政策的意图（逐盘、显式、fail-closed），只是把"操作员批准"从一句人话，改写成一份 builder/relay 在触发广播前必须验证通过的结构化数据。

**授权 artifact 必须绑定以下字段**（Codex ebe3417e 原始八字段 + Codex 7f26224a 会话化修正，逐条落地）：

| # | 字段 | 内容 | 为什么必须绑死 |
|---|---|---|---|
| 1 | 精确 market/shard id | 完整 `market_id`（bshard 则精确到 shard 级，如 `…-kr5l4-s7`，不是母市场 id） | 防止一份 artifact 被挪用到"相邻"的另一盘/另一分片 |
| 2 | 退款范围（枚举或承诺 digest，**不可变**） | S2 枚举出的全部 `bettor_pk` 列表，或该列表的哈希承诺（如 blake2b(排序后的 bettor_pk 列表)） | 防止 artifact 批准了"这个市场"，却被拿去覆盖一份被悄悄增删过的持仓清单——直接兑现 §0 红线"零排除"：任何被排除的行都会让 digest 对不上；**授权会话生命周期内此范围不得追加/收窄**（见下方会话状态机） |
| 3 | 总额/输出承诺 | S2 汇总的 `SUM(stake_amount)`，或全部输出的承诺哈希 | 防止部分退款/金额被篡改后仍能通过校验 |

| 5 | policy/version | 本稿版本号（如 `path-c-refund-plan-rev4`） | 政策变更后旧 artifact 自动失效，不需要额外撤销机制 |
| 6 | 批准人身份/角色 | Owner 或 Owner 显式授权单点的可验证身份（签名/密钥标识，不是聊天显示名） | "谁批的"必须可事后审计且不可抵赖 |
| 7 | 会话 id + 状态机（**rev-3 改，见下方专节**） | 见下 | 见下 |
| 8 | 有效期 | 起止时间戳，过期后 builder/relay 拒绝该会话（不论其中还有多少笔未完成） | 防止一份陈旧的批准在很久之后被拿出来继续触发操作 |

- **签发方式**：本稿不规定具体的密钥/签名机制（落码阶段的实现细节，超出设计稿范围）——但明确要求 artifact 是**可被独立验证的结构化数据**，不是一句自然语言批准消息。频道内的"批准 j34vb"这类文字仍然有价值（人类可读的意图记录、辅助审计），**但它本身不是闸，闸是 artifact + 下面 S6 的强制校验**。
- **逐盘单独签发**：不得"一次性签发覆盖 9 盘的会话"（V2 政策原话"逐盘"，且 artifact 第 1 项绑死单一 market/shard，结构上就不允许覆盖多盘）。
- **fail-closed（签发前）**：S1-S4 任何一步读数异常/构造失败/名单存疑，一律停止签发流程，不得带着已知问题去生成 artifact。

### 🔴 §-会话状态机（rev-3 新增，Codex 7f26224a 指出的结构性冲突及修法）

**冲突是什么**：一份 artifact 授权的是"整个 market/shard"（第 2 项范围），但 S6 是**逐 bettor** 执行（kr5l4 单个分片就有 22-32 笔）。若把"唯一 nonce/op-id"设计成单次消费（rev-2 的写法）：
- 首笔退款后立刻标记该 op-id 已消费 ⇒ **该 market/shard 剩余的 bettor 全部退不了**（授权被第一笔耗尽）；
- 若不标记消费、留到最后一笔才标记 ⇒ **整个多笔窗口期内，同一份 artifact 可以被重放去触发额外的非法退款**（op-id 检查形同虚设）。

**⇒ 单次消费的 nonce 模型，结构上容不下"一次授权、多笔执行"这个真实场景——rev-2 的设计有洞，不是实现细节没写全。**

**修法（Codex 给出，本节落地）**：授权不是一次性凭证，是一个**会话**，有自己的状态机：

```
issued（签发，尚未开始执行）
  → active（S6 已开始逐笔执行，会话内已完成的 bettor 集合由机器维护）
    → completed（该会话范围内全部 bettor 都已成功退款）
    → expired（超过第 8 项有效期，无论完成与否，会话失效）
```

### 🔴🔴 会话过期后如何续做剩余范围（rev-4 改，撤回一处错误澄清）

> **rev-3 → rev-4 撤回什么，为什么**：rev-3 曾在此处写"重新走一遍 S1-S4、对当时的 DB 实况重新枚举即可，已退款者会因 DB 状态已变自然从 S2 消失"——这是我采纳 NWT 一条非 MUST-FIX 建议时加的。**Codex 红队（c2eb00d7，2026-08-11）指出这句话本身与本稿 §1.2 自己立的规矩矛盾**：§1.2 全篇的地基是 NO TX NO STATE（DB 只是索引/缓存，链上状态才是权威），而这句"续做靠 DB 自然消失"恰恰是反过来信了一次 DB 快照。**这是我自己该在加那句话时回头核对 §1.2 却没做的一步，不是 NWT 的建议本身有恶意**——她的建议解决的是"要不要另建一张跨会话去重表"这个问题（答案：不用），但具体"怎么判断谁已经退过"这半被我写成了错误的机制。撤回原句，正确版本如下。

**正确的续做逻辑：剩余集从链上确认事实派生，DB 只做已对账索引，不做权威源**：

- **S1（市场/分片状态只读确认）扩一步**：读到 `closed=2` 时，必须先判定这是不是**本池自己的授权部分退款序列造成的**——判据 = 能否找到一份**机器可验证据**，把当前 `closed=2` 状态与某个（可能已 `expired` 的）历史会话绑定（例如：该会话的范围 digest + 已确认退款交易的 txid 列表，能重算出与当前链上 pool state 一致的结果）。**能绑定 → 进入下方"新会话续做"流程；不能绑定 → 这个 `closed=2` 与本次退款处置无关，S1 照旧 fail-closed（§2-S1 原有规则不变，不因为"看起来像"退款序列就放宽）**。
- **S2 替代会话的剩余集，逐 ticket 判定，不逐行信 DB 字段**：对该市场/分片枚举出的每一个 `bettor_pk`（原授权范围内），必须**逐笔查链上事实**（该 bettor 的 `PoolSide` ticket 当前是否已花费、若已花费其花费交易是否正是一笔已确认的 `bshard_refund_cancelled` 输出到该 bettor 地址）来分类，**不能只读 `refund_attempted_at` 或 `claim_txid` 这类 DB 字段就当数**——DB 字段可能因为"已广播但确认前崩溃"、"DB 写入失败但链上已确认"这类中间态而与链不同步，§1.2 的纪律要求任何这类不一致都以链上现读为准。
- **新会话范围 = 原授权范围 − 链上确认已完成项，零追加**：替代会话的范围 digest 必须**精确等于**原始范围减去链上已确认完成的那些 bettor，不多不少。**若要把范围扩大到原授权之外的 bettor（比如发现 S2 当初漏枚举了一行），那是一次新的、独立的授权事件**（走完整的 S1-S5 重新签发），**不允许把它包装成"对旧会话的续做"**——续做只能收窄范围，不能借续做的名义扩大它。

**补充测试用例（Codex c2eb00d7，并入 §-S5/S6 落码前置的验收门列表）**：
- 会话在 N 笔确认后过期，重入时必须精确识别出"已完成 N 笔"而非重新枚举出全部
- `closed=2` 重入，但该状态**不能**关联到任何已知会话（无关的 closed=2）→ 仍 fail-closed，不得被当成"续做"放行
- 广播已发出、链上尚未确认、DB 还没来得及更新时崩溃 → 重启后必须能识别"这一笔在途"而不是当作"未开始"重复触发
- DB 记录 `refund_attempted_at` 有值，但链上该 ticket 从未被消费（DB 说做了、链没做）→ 判定为未完成，不得因为 DB 有记录就跳过
- 链上该 ticket 已被消费为一笔退款，但 DB 字段是陈旧的未更新状态（链做了、DB 没跟上）→ 判定为已完成，不得重复触发
- 替代会话的范围 digest 必须精确等于"原范围 − 链上已确认完成项"，一个不多一个不少
- 已完成的 bettor 不得出现在新会话里被重新"授权"（即使只是形式上再走一遍也不行——见上条零追加原则的另一面）
- 不允许新 bettor 被追加进续做的范围（范围只能收窄，扩大必须是独立授权事件）

- **不可变范围 digest**（第 2 项）在会话创建时锁定，`active` 期间**不允许追加/收窄**——若发现范围枚举本身有误（比如 S2 漏了一行），正确做法是作废整个会话、回到 S1-S4 重新走一遍，签发一份新会话，**不允许对活跃会话打补丁**。
- **机器维护的已完成子集**（或等价形式：为每个 bettor 派生一个子 op-id，形如 `session_id + bettor_pk` 的确定性哈希，每个子 op-id 各自单次消费）——两种实现路径均可，本稿不指定，落码阶段选一种；**要求是**：给定同一个 bettor，同一个会话内不能被重复退款（防重放），但会话内的其余 bettor 不受影响（不会因为一笔已完成就锁死整个会话）。
- **重启必须重建会话状态**：若执行在 bettor N 与 N+1 之间崩溃/重启，恢复后必须能够**精确续做剩余范围**——已完成的不重做（防重放），未完成的不遗漏（防静默排除，直接呼应 §0 红线），且**不允许在重启后扩大范围**（不能借着"重新读一次 S2"混入原本不在这份授权 digest 里的新行）。
- **链上 spent-once 票不能替代这一层**（Codex 明示）：`PoolSide` ticket 本身是链上一次性消费不假，但那只保证"同一笔 stake 不会被退两次"这个链上事实，**不保证"KANet 这一层有没有在没有效授权的情况下发起了这笔广播"**——授权会话的状态机是 KANet 侧的闸，链上票据是另一层独立的保护，两者不互相替代。

### 🔴 S6 · 执行层验证 + 逐笔广播（仅在 S5 会话 `active` 后）

- **前置强制**：builder/relay 在够到广播路径**之前**，必须验证 S5 会话——校验其绑定字段（market/shard id、bettor 枚举 digest、总额、批准人身份、有效期）与当前即将构造的交易**逐项匹配**，并核对该 bettor 在会话的"已完成子集"里尚未出现过。**任一项不匹配 → 拒绝构造，不得静默跳过或退化成"缺会话也放行"**——这条是本节存在的全部意义，若执行层在拿不到有效会话时仍能完成广播，等于 S5 从未存在。
- 验证通过后，逐笔（逐个 `bettor_pk`）发起 `bshard_refund_cancelled` 命令，落 relay IPC。
- **首笔退款会把 `closed` 从 0 翻到 2**（F2 latch，`pool-refund-builder.mjs:16`）——这一动作对该 pool 是**不可逆的一次性状态转换**，翻转后同一个 pool 上的其余退款走的是"pool 已 closed=2"路径，须确认后续每一笔都能在这个新状态下继续构造（`currentPoolState` 每笔都要用最新链上态重取，不能沿用 S4 dry-run 时的旧快照）。
- 建议节奏：**逐笔发起、逐笔等待落链确认后再发下一笔**，不批量并发广播（这条是本稿建议，不是已有代码强制；理由：pool_continuation 是同一个 UTXO 链式消费，并发广播会互相打架，产生竞态失败，不是安全风险，是效率/可靠性考量）。

### 🟠 S5/S6 的落码前置（本稿明确标注，不代实现拍板）
- 本节只定义会话**必须绑定什么**、状态机**必须怎么转移**、执行层**必须在何时验证**——具体的密钥/签名机制、状态存储位置（哪张表）、如何在 relay 与 builder 之间传递会话状态，是落码阶段的工作，本稿不预写。
- **验收门（Bettor 08:23Z + Codex 7f26224a 逐条给出，落码合并前必须逐条有可执行用例，不是只测阳性路径）**：
  1. 缺会话 artifact → 拒绝
  2. 批准人身份不合法 → 拒绝
  3. market/shard id 与会话不符 → 拒绝
  4. bettor-set digest 被篡改（范围与签发时不符）→ 拒绝
  5. 总额/输出承诺被篡改 → 拒绝
  6. 会话已过期 → 拒绝
  7. 对已完成子集里的 bettor 重复触发（同一会话内重放）→ 拒绝
  8. 对已 `completed`/`expired` 的整个会话重放（试图用一份旧会话触发新的一批 draw）→ 拒绝
  9. **崩溃恢复语义**：在 bettor N 与 N+1 之间人为中断，重启后必须精确续做剩余范围——已完成的不重做（第 7 条的另一面）、未完成的不遗漏（§0 红线）、且不允许范围扩张
  10. 阳性路径：合法会话 + 合法逐笔请求 → 全部放行，`active`→`completed` 状态正确转移

  这与今天 CIS role_code 那条"注释级警告没有运行时闸"的教训是同一个形状——本节把它在设计阶段就钉死，不留到落码时才发现。

### S7 · 验收（每笔 + 整盘两级）
- **每笔**：`check_utxo_landed`（复用今晚反复验证过的方法论：NO TX NO STATE，链上有 UTXO 落地才算数，不是"relay 返回了 txid"就算完成）确认 payout 输出真实到账 `bettorAddress`。
- **整盘**：S6 全部完成后，回到 S2 的枚举结果，逐行核对 `claim_txid`/退款 txid 是否补齐、总额是否与 S2 汇总的应退总额一致。**任何一行缺失 → 整盘不算完成，不得关闭这次执行**。
- 最终交付一份"本盘退款完成报告"，格式=原始枚举表 + 每行对应的落链 txid，供 NWT 审计（红线核对项：零排除是否真的做到）。

## §4 `kr5l4` 单列（体量最大、结构最复杂，不并入通用模板）

### §4.1 结构：bshard 22 分片，不是单一市场

现查确认：`kr5l4` 是母市场 + 22 个子分片（`kr5l4-s0` 至 `kr5l4-s21`），每个分片 `protocol_status = shard_internal`，各自独立持有 pool UTXO（各自的 `pool_p2sh`/`closed` 状态）。母市场本身 `protocol_status = verifying`，`settle_txid = null`。

**⇒ §2 的 S1-S7 框架必须对 22 个分片各自独立跑一遍**，不是对 kr5l4 跑一次。每个分片是独立的链上 covenant 实例，`closed` 翻转、退款触发都是分片级别的动作，不存在"母市场一键退款"这回事（除非未来专门设计一个批处理包装层，本稿不预设有这个包装层存在）。

现查 22 个分片汇总：793 行中的 694 行属于 kr5l4（每分片 22-32 人不等），应退总额 25,075 KAS（含已有 side_lock_daa 值的 105 行——按 §1.2 推论 2，这些行同样要退，不因为 side_lock_daa 有值就被排除）。**22 个分片全部 `claim_txid`/`refund_attempted_at` 为 NULL——干净状态，同 §1.4。**

### 🔴 §4.2 kr5l4 特有的前置：先分清"疑丢"与"不可得"（A-3 §1-quater）

A-3 rev-2 §1-quater 已经把这条钉死：kr5l4 在册还挂着一桩 25 天悬案——"leaf 疑丢"（钱/叶子在不在，链上状态的存在性问题）与本稿要处理的"派生不可得"（值取不取得到，我们这侧的读取能力问题）是**两个不同的定性**，今天只有后者被 Owner 终裁"永久不可得"，**前者尚未定案**（A-3 §7 证据层级表标 `🟠 [未定案]`）。

**⇒ 这条前置直接影响退款是否安全**：若"疑丢"最终被坐实为"叶子在链上层面确实丢失/无法定位到具体 UTXO"，那意味着某些分片的 pool UTXO 本身可能对不上账（不是 side_lock_daa 缺失那么简单），**退款前必须先对 22 个分片逐一确认 pool UTXO 链上确实存在、金额与 §2-S2 枚举的 `SUM(stake_amount)` 一致**（这本来就是 §2-S1 的动作，kr5l4 只是格外强调：这一步对 kr5l4 不是形式检查，是真正可能拦下问题的一步，因为"疑丢"悬案还没结案）。

**⇒ 具体处置建议（不代 Owner/Bettor 拍，摆出选项）**：
- **选项一**：kr5l4 22 个分片，执行 §2 框架前先补跑一次 A-3 §1-quater 建议的判别动作——"取当时(25天前开案时)的剪裁点读数与 kr5l4 deadline_daa(60,722,281) 比"，坐实"疑丢"是否就是这堵墙的另一种表现形式（若是，则"疑丢"这个标签本身可以合并进本次路 C 处置，不需要单独等一个悬案结案）。
- **选项二**：不等悬案结案，直接对 22 个分片逐一做 §4.2 那条"链上 UTXO 存在性+金额核对"，只要这一步通过就视为"这个分片没有疑丢问题，可以按标准框架退"——分片级别独立判断，不要求 22 个分片一起等悬案结论。**本稿倾向选项二**（更快、更细粒度，不因为一个悬案挡住其余没问题的分片），但最终选择留给 Bettor/Owner。

### §4.3 执行顺序建议

22 个分片体量不均（`totalStake` 从 82,000 KAS 到 125,000 KAS 不等——注：此处单位是分片内**全部**持仓含非 NULL 行，不是"NULL 行本金"那个更小的子集）。建议**从最小分片开始**（现查 `kr5l4-s21`，22 人/82,000 sompi-scale，是 22 个分片里唯一人数不满 32 的一个，体量也最小），验证 §2 框架在 bshard 分片这个具体结构上跑通，再推广到其余 21 个分片——同 §3 的"先验证框架再推广"逻辑，只是这次是在 kr5l4 内部先跑一个分片当"kr5l4 自己的首例"。
