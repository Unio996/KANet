## ② 报价 JSON（新增押金条款字段，O3）

在 v0.3 报价 JSON 基础上，`require_channel_deposit: true` 时新增一组**必填**的押金条款字段（V1 全部固定值，写进报价是为了"承诺"而不是"可配置"——即使 V1 只有一种取值，也要求报价显式声明，为未来版本放开可配置性预留位置，不需要那时候改报价 schema 本身）：

```json
{
  "...": "...(其余字段同 v0.3)",
  "require_channel_deposit": true,
  "min_deposit_sompi": "100000000",
  "deposit_terms": {
    "schema_v": 1,
    "redeemable_by": "depositor_only",
    "redeemable_after_ms": 0,
    "forfeitable": false,
    "forfeit_conditions": null,
    "arbiter": null
  }
}
```

- `redeemable_by`: V1 固定 `"depositor_only"`（只有押金人本人能取回，§7.2 `checkSig` 机制的直接体现）。
- `redeemable_after_ms`: V1 固定 `0`（随时可退，无锁定期——本版无罚没机制，没有"锁定期"存在的理由）。
- `forfeitable`: V1 固定 `false`（**押金不可没收**——写死在报价里，任何声称"可以没收我的押金"的商家配置在 V1 都是无效配置，SDK 应拒绝任何 `forfeitable:true` 的报价，不是静默忽略）。
- `forfeit_conditions`/`arbiter`: V1 固定 `null`（没收条件与裁决方——V1 没有没收机制，这两个字段存在只是为了让 schema 在未来版本引入没收机制时不需要破坏性变更，V1 阶段任何非 `null` 值都应被拒绝）。

**为什么现在就写这些字段而不是等 V2 才加**：Owner 原话"须在渠道加入前写入报价"——即使 V1 的取值全部固定，把这些字段**现在**就放进报价 schema、并在签名覆盖范围内，意味着渠道在决定押金、决定要不要加入这条归因链之前，看到的报价**已经明确承诺了这些条款不会被商家事后追加没收条件**——这是承诺的时间点问题，不是功能问题。

## ③.1 归因链接格式——去重与上限规则重写（N2/N3 修复）

链接格式不变（`ch=<addr1>[,<addr2>[,...最多5个]]`），**去重与上限两条规则重写如下**：

### 上限规则（N3 修复：卡在原始位置数，不是去重后数量）

**判断对象是 `ch` 参数按逗号分割后的原始位置数量（包含重复）**，不是去重之后剩下几个不同地址。原始位置数 >5 直接结构性拒绝，明确报错，**这一步在做任何去重判断之前就完成**——`ch=A,B,C,D,A,F`（6 个原始位置）在这一步就被拒绝，不会进入"去重后剩 5 个不同地址（A/B/C/D/F），F 该放进哪个槽位"这个无解的讨论。

**这条改动的理由（NWT 找出的真实攻击）**：如果上限判断改成"去重后数量"，`ch=A,B,C,D,A,F` 会因为"去重后只有 5 个不同地址"被判定合法通过，但第 6 个原始位置的 F 到底该占第 3 位（A 空出来的位置，被"压缩"进去）还是被静默丢弃——两种读法都能自圆其说地符合"上限规则"字面，但**都有问题**：压缩会让"位置=槽位编号"这条前提失效（后面详述的签名链验证依赖位置严格对应槽位）；静默丢弃则给了任何一个转发环节一个**免费、无成本**的手段——只要在自己转发那一环插一次重复地址（哪怕是自己已经出现过的地址），就能把排在自己后面的所有真实渠道**无声挤出局**（那些渠道自己没做错任何事，链接本身"合法"，却拿不到任何佣金，也没有任何报错提示）。改成卡原始位置数之后，这类链接在检查长度那一步就整体失效，F 想要归因就必须出现在前 5 个位置以内，不存在"挤别人"这个操作空间。

### 去重规则（N2 修复：比较规范化字节，不是原始字符串）

**去重判定必须在地址解析成规范字节之后做**：每个 `ch` 参数里的地址先各自反解出 scriptPubKey（§6.2 已有机制，`addressFromScriptPublicKey` 反解 + 拒绝非标准模板），**用完整的 `version++script` 字节做逐字节比较**来判定"是否同一个地址"——不能比较地址的 bech32 文本表示。理由：bech32 编码本身**大小写不敏感**（标准允许混合大小写，只是规范形式是全小写），如果去重判断做的是原始字符串逐字比较，同一个地址换几个字母大小写就能在两个字符串"不相等"的前提下通过去重检查，零成本占两个槽位、拿两份佣金——这会直接废掉"去重规则本身是一道免费防线"这句话（§6.4）。

**同一把私钥、不同地址模板，是否算同一渠道——写死为"不算"**：一把 pubkey 理论上可以同时对应一个 P2PK 地址和一个 P2PK-ECDSA 地址（两种不同的脚本模板，字节完全不同），本设计**不做"底层是不是同一把钥匙"这种跨模板归并**——去重的判据严格是"完整 scriptPubKey 字节是否逐字节相同"，不是"背后的签名密钥是否相同"。理由：(a) P2SH 地址背后没有单一 pubkey 可比较，任何"同一把钥匙"的判定规则对 P2SH 都不成立，规则不能只对部分地址类型生效；(b) 即使限定只在 P2PK/P2PK-ECDSA 之间比较，两种模板在链上确实是**两个不同的、可独立花费的对象**（不是同一个 UTXO 的两种表示法），把它们当"同一渠道"合并，反而制造了一种新的歧义（如果两个不同模板的地址都出现在链里，到底该按哪个模板的份额支付、算不算重复）。**结论：去重只做"字节完全相同"这一种最简单、无歧义的判断，不做任何跨模板/跨密钥的身份统一推断。**

### 工作示例（写死，不留解读空间）

| 输入 `ch` 参数 | 原始位置数 | 处理 |
|---|---|---|
| `A,B,C` | 3 | 合法，`channel_1=A, channel_2=B, channel_3=C` |
| `A,B,C,D,A,F` | 6 | **直接拒绝**（原始位置数 6 > 5），不产生任何槽位分配 |
| `A,B,a`（`a` 是 `A` 的大小写变体，反解出同一 scriptPubKey） | 3 | 合法（长度未超限），但去重命中：`channel_1=A, channel_2=B, channel_3=(空，视为未填)` |
| `A,B,A,C` | 4 | 合法，`channel_1=A, channel_2=B, channel_3=(空), channel_4=C`（v0.3 原有示例，位置不压缩，本版确认不变） |

## ③.4 渠道逐级签名链（O1，新增全节）

### 3.4.1 目标与整体机制

商家签报价（已有机制）；**每个渠道加入链条时，对"前序链条的规范化摘要 + 自己的位置 + 自己的地址 + 自己的签名身份公钥"签一次名**，形成一条哈希链式签名结构。结账页/SDK 验证整条签名链后才锁定最终归因；**订单 covenant 的 ctor 只烤入这条链最终的规范化摘要（`channel_chain_commitment: byte[32]`），作为纯审计字段，不参与任何 `require()`**——链上仍然"不感知归因"（D-034 §8 原话不变），签名链的验证工作完全在链下（结账页/SDK/任何审计者），只是现在有了一个可以逐环核验的密码学证据链，不只是"整条链的地址集合决定 ctor"这一层（v0.1-v0.3 已有），还多了"这条集合确实是渠道各自同意加入的、没有被中途篡改"这一层。

### 3.4.2 签名规范

```
DOMAIN = "KANET-COMMISSION-CHAIN-V1"                       // 域分隔, 防跨协议签名重用
quote_hash = blake2b(canonical_quote_bytes)                 // 复用既有 canonical 序列化, 不新造
chain_digest_0 = blake2b(DOMAIN || quote_hash || network)   // 根摘要, 任何人拿报价就能算, 不需要问任何人

// 渠道 k（k = 1..5，严格按加入顺序 = 槽位编号）加入时：
entry_k = { position: k, address_spk: <scriptPubKey字节>, signing_pubkey: <32字节> }
message_k = chain_digest_{k-1} || byte(k) || address_spk_k || signing_pubkey_k
sig_k = SchnorrSign(signing_privkey_k, message_k)            // 65 字节, 同本仓既有签名字节长度约定
chain_digest_k = blake2b(message_k)                          // 滚动前进, 供下一环使用
```

`channel_chain_commitment` = 最终 `chain_digest_K`（K = 实际链长，0-5）。

**渠道签名身份 pubkey 与收款地址的关系（Owner 明确要求写清）**：每个链条条目携带**两个独立字段**——`address_spk`（钱付到哪，来自 §6.2 允许的任意标准地址类型：P2PK / P2PK-ECDSA / P2SH）与 `signing_pubkey`（用哪把钥匙证明"我同意加入这条链"，**始终必须是一个可签名的 32 字节 pubkey**）。两者的关系：
- 收款地址是 P2PK/P2PK-ECDSA 时，`signing_pubkey` **可以**（不强制）复用同一把钥匙——最简单的情形，渠道一把钥匙两用。
- 收款地址是 P2SH（比如渠道想让佣金直接进自己的另一个 covenant）时，`signing_pubkey` **必须**是一把独立的、专门用来证明链条身份的钥匙——P2SH 背后没有单一 pubkey，这种情况下"身份"（谁能证明自己是这个链条位置的合法拥有者）与"收款目的地"（钱付到哪个脚本）是两件独立的事，本设计**不假装它们是一回事**，直接用两个字段分开表达，不引入"从 P2SH 反推身份"这种没有通用解法的机制。

### 3.4.3 验证算法

```
function verifyChain(quote, entries /* [{position, address_spk, signing_pubkey, sig}], 长度 0-5 */):
  d = blake2b(DOMAIN || quote_hash(quote) || network)
  for k in 1..entries.length:
    e = entries[k-1]
    require(e.position == k)                                   // 位置必须严格递增且从 1 开始, 不允许跳号/乱序
    msg = d || byte(k) || e.address_spk || e.signing_pubkey
    require(checkSig(e.sig, e.signing_pubkey, msg))             // 验证这一环签名
    d = blake2b(msg)
  return d   // = channel_chain_commitment, 供比对 ctor 里烤的值
```

### 3.4.4 攻击抵抗（逐条对应 Owner 点名的五种篡改）

| 攻击 | 机制为何能识破 |
|---|---|
| **X 替换 A**（把 A 的条目换成 X，不经 A 同意） | `sig_A` 是用 A 的 `signing_pubkey` 对"…|| A 的地址 || A 的签名 pubkey"签的名——换成 X 意味着要为一条**内容不同**的消息（含 X 的地址/pubkey）伪造一个能通过 `checkSig(_, A的pubkey, _)` 校验的签名，这在不知道 A 私钥的前提下做不到；如果攻击者反而用 X 自己的私钥重新签——那不是"替换 A"，是"X 用自己的身份在这个位置真实加入"，属于正常操作范畴，不是攻击。 |
| **删 A**（呈现 root→B→C，隐去中间的 A） | B 的真实签名是对 `chain_digest_1(=blake2b(...含A...))||pos=2||...` 签的；删掉 A 后验证者从 `chain_digest_0` 直接推到"B 在位置 2"，重算出的消息跟 B 当初签的消息**不同**（少了 A 的内容），`checkSig` 校验失败。 |
| **插入**（root→A→X→B，B 本该紧跟 A） | X 插入后 B 实际处在位置 3 不是 2；B 当初对"位置 2"签的名对不上验证者用"位置 3 + 含 X 的新摘要"重算出的消息——校验失败，除非 B 为新位置重新签一次（那已经不是"插入攻击"，是链条真实按这个新顺序重构，B 主动配合）。**在链尾追加**不属于这一类——那是正常的逐级转发，不是插入。 |
| **重放他人签名**（把某个签名从别的报价/网络场景搬到这里） | `chain_digest_0` 本身就绑死了 `DOMAIN + quote_hash + network`——不同报价或不同网络算出的根摘要完全不同，之后每一环的消息都建立在这个根摘要上，跨场景的签名在新场景下重算消息必然对不上。 |
| **截断尾部**（真实链是 root→A→B→C→D，构造订单时只用 root→A→B） | **这个验证不出"篡改"——因为它本来就不是篡改**：一条有效链的任意前缀本身就是一条完全自洽、可独立验证的有效链（每一环的签名只依赖它之前的内容，不依赖之后是否还有更多环）。C/D 因此拿不到这笔订单的归因，但这不是密码学意义上的伪造，是"这笔订单最终选择了哪条（有效的）链"这个业务层面的问题——**与 Owner 原话"绕开原链接、从商家重新起一条"是同一政策范畴**：任何时候，构造具体订单的一方选择用一条更短的、真实的前缀链，跟直接找商家另起一条全新的（零渠道）链，本质上是同一类"没有恶意方能从中获利"的行为——折算份额回流指定方（§6.4），不会被截断者私吞，只是被截断的渠道那一单没有拿到归因。**协议层面无法、也不应该试图阻止这件事**——阻止"用更短的有效前缀"等价于要求"必须证明不存在更长的链"，这是要求证明一个否定命题，结构上做不到。 |

### 3.4.5 链接长度（真实计算，不是估算）

- 主网地址（bech32，`kaspa:` 前缀）实测长度：**67 字符**。
- 65 字节 Schnorr 签名（本仓既有签名字节长度约定，64 字节签名 + 1 字节 sighash 类型）用 base64url 编码：**87 字符**（比 hex 编码的 130 字符省 33%，推荐用 base64url，全部字符 URL 安全不需要再转义）。
- `signing_pubkey`（32 字节）base64url 编码：约 43 字符（若与收款地址不同、需要单独携带时才计入；收款地址是 P2PK/P2PK-ECDSA 且复用同一把钥匙时,这个字段可以省略,验证时从收款地址反解即可，进一步压缩链接长度）。
- **单条链条目**（地址 + 签名，不含单独 pubkey 的最省情形）：`67 + 1(分隔) + 87 ≈ 155` 字符。
- **5 条全部占满**：`155 × 5 + 4(条目间分隔) ≈ 779` 字符，加上 `q=<quote引用>` 与基础 URL（建议报价用短哈希/id 引用而不是把整份 JSON 塞进链接，链接只携带"指向报价的指针"，报价本体单独托管/附带传输——同 §4 结账页"不需要我们的服务器"原则一致，报价可以由商家自己的静态托管、渠道自己缓存，链接本身不需要背整份 JSON），**总长度稳定在 900-1000 字符量级**。

**对比常见实际限制**：现代浏览器 URL 长度限制普遍在 2000-8000+ 字符（早年 IE 的 2083 字符限制已基本不构成实际约束）；YouTube 视频简介栏上限约 5000 字符；邮件 HTML 超链接的 `href` 属性长度不受可读性影响（可见文字可以是"点击领取"四个字，真实链接藏在 `href` 里）；QR 码在中等版本号（约 15-20 级）+ 低容错等级下即可容纳 900-1000 字母数字字符，标准智能手机摄像头可正常扫描。**结论：5 层签名链的链接长度在所有常见分发渠道下都有充分余量，不构成实践障碍**——这是真实计算出的数字，不是"应该够用"的猜测。

### 6.1b 付款前完整交易预检——三维 mass 报告（O2，新增）

分档表只是**报价签名时刻**（`validateQuoteMassFeasibility`）用的准入判据。Owner 要求另外补一道**付款前**（用户已经知道订单地址、准备构造/广播 `split()` 之前）的完整交易预检——对整笔即将广播的交易（商家输出、broker 输出、各渠道输出、找零、手续费、脚本字节、输入）做一次真实 `estimateMassUpperBound` 调用，**分三个维度分别报告**（不只报一个"mass"数字）：

| 维度 | 硬上限 | 来源 |
|---|---|---|
| `compute` | 500,000 | `consensus/core/src/config/params.rs` `prior_block_mass_limits.compute` |
| `storage` | 500,000 | 同上 `prior_block_mass_limits.storage`（与 compute 共享同一数值，但是两个独立维度，各自单独达到上限都会被拒） |
| `transient` | 1,000,000 | 同上 `new_transient_mass_limit`（这个维度上限是另外两个的两倍，本设计目前所有真实测量场景里从未接近这个上限） |

**6 渠道场景的具体维度分解**（真实测量,回答 Owner"标明超的是哪一维"）：

```
6渠道(各0.1KAS)+找零: compute=10,486（远低于 500,000）| storage=685,715（超过 500,000 硬上限）| transient=3,304（远低于 1,000,000）
```

**结论：本设计目前测过的全部场景，唯一会被突破的维度是 `storage`（存储质量）——`compute` 与 `transient` 在所有已测场景里都留有巨大余量（两个数量级以上）**。这不是巧合：`compute` 主要由交易字节长度与脚本复杂度决定（本设计的合约逻辑简单、没有循环里的重逻辑），`transient` 只是字节长度的一个线性放大（系数 4，`constants.rs`），两者都不会因为"某个输出金额很小"而升高——只有 `storage` 的公式里有 `C/amount` 这种"金额越小、贡献越大"的结构，这正是本设计从 v0.1 一路踩到 v0.3 的所有 mass 坑的共同根源。**付款前预检报告应该把三个维度都打印出来（哪怕两个维度永远不会亮红灯），让实现者和审计者一眼看清"是哪个维度、为什么"，不是只报一个笼统的"mass 超限"。**

### 6.1c 五级是最大深度，不是目标（O4，新增）

配置页/SDK 生成报价时，如果商家配置了 N 个渠道槽位（N≤5），且渠道预算占总价的比例是 `channel_budget_bps`，**应该反算出这份报价能支持的最小订单额，并在配置页明确提示**：

```
min_order_sompi = N × dosage(N) / (channel_budget_bps / 10000)
```

**具体例子**（Owner 原话给的数字）：5 个渠道，每个最低 0.15 KAS（v0.3 无 broker 分档表数字，简单情形示范），渠道预算合计占总价 10%：
```
5 渠道最低总额 = 5 × 0.15 KAS = 0.75 KAS
渠道预算占比 10% ⇒ 订单总额至少 = 0.75 / 0.10 = 7.5 KAS
```

也就是说：一份"渠道预算占比 10%、允许最多 5 层转发"的报价，**只适合客单价 ≥7.5 KAS 的商品**——客单价更低的商品，5 层转发在这份报价下根本凑不出满足运营下限的份额（渠道分到的钱会被 `validateQuoteMassFeasibility` 判定太小而拒签，或者商家得把渠道预算占比调更高才行）。**配置页应该在商家填完价格、渠道预算占比、最大层数三个数字后，实时算出并提示这条约束**（"以当前配置，最多支持 N 层同时归因；如需 5 层，订单额建议不低于 X KAS"），**引导商家自己根据实际客单价选择合理的层数上限，不是默认所有报价都开 5 层**——5 是协议允许的结构上限，不是每份报价都该用满的目标（D-034 §8 原话）。小额订单自然应该只用一两级，SDK 的默认建议值应该反映这一点，而不是无条件默认开满 5 层。
