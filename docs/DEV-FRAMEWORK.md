## 铁律（无例外）

**任何 agent，未经「报备 → 审核 → 批准 → 测试」，无权改动任何代码。先报，后动手。绝不先斩后奏。**

## 强制流程（每次改动都走）

1. **① 报备（改之前）**：频道报清 —— 改哪些文件、为什么、影响面、方案。**先报计划，不是写完代码再补报。**（既有资产核查在先，见 CLAUDE.md 接位 SOP 第5条。）
2. **② 审核**：
   - **Bettor 审所有**：设计合理性 / 影响面 / 风险 / 是否符合 Owner 主线 / 是否重复造轮子（查现有资产）。
   - **reviewer（按 COORD-LEDGER 域表，通常 NWT 或域内 reviewer）逐项核实**：不是听方案文字，是**读实际代码/编译产物/字节偏移**——GREEN 或列 finding。money-path/covenant 代码必须字节级验收（**byte-exact diff 是唯一判据，功能测试过 ≠ 过关**）。
   - **必须 Owner 批的**：用户面（tg-bot/*.mjs、*.eta、messages.mjs、i18n.mjs、任何用户看得到的文案版面）+ 钱路/covenant/结算 + 重大功能/新机制。
   - 小/内部改动：Bettor 审即可（但仍先报）。
3. **③ 批准**：Bettor（协调域）签字 GO，才允许 commit/落码/广播。
4. **④ 实现**：批准后才写代码。
5. **⑤ 测试**：自测 + 单测/回归（改 broker/agent 必跑 `test-framework`）。落码后贴证据（diff + 实测输出，如 byte-exact diff / clock-check 结果 / testnet dry-run），reviewer 复核证据后才算收尾。
6. **⑥ co-verify**：NWT/Bettor 独立验（钱路/显示尤其必须，链上取证 predict-then-verify）。
7. **⑦ 部署**：验过才部署。**用户面部署前 Owner 过最终样图/渲染对比。**

## 机制（不靠自觉·靠卡点）

- **Bettor = 强制审核闸**：没走报备→审核的改动，Bettor revert + 记录。审核是 Bettor 的头号本职，不是钱路盯紧了 UI 就可以放。
- **lint 标记**：`scripts/lint-kanet.mjs` 加规则 —— commit 碰用户面/钱路文件（tg-bot/*、*.eta、messages.mjs、i18n.mjs、pool-*.sil、*settle*、*claim*）就亮「需审核」灯，绕过无处藏。
- **写进接位 SOP**：新会话/接位 agent 必读本文档 + CLAUDE.md 引用。

## 违反 = 退回

先斩后奏、绕过审核、写完代码才报备 = 改动 revert，透明记录。测试网也不例外。

## 技术不确定性直接问 Bettor（2026-07-07 J1tn 提·D-006·Bettor 批准全队生效）

**遇到需要验证的技术不确定性时（旧消息是否已经陈饭/某个假设对不对/某条 blocker 是否还开放），直接问 Bettor，不要自己长链条静态回溯调查再拍。**

- **为什么**：J1tn 2026-07-07 接位时，对一条自己都不确定是否已发出的旧消息("escape_trigger blocker")，花大量周期通读 COORD-LEDGER 自行判断"是否陈饭"——事后 Bettor 一句话查清真相（消息压根没广播成功，撞在 Phase0 停栈窗口）。协调者手上有全频道可查记录 + 广播成功与否的第一手判断依据，agent 自己脑补大概率绕远路。（同日第二例：J1tn 误判本文档"从未创建"——文件躺在主机未跟踪，他节点静态查不到。）
- **怎么应用**：事实性确认问题（"这个是不是已解决的旧问题"、"我理解的现状对不对"、"这条 blocker 还在吗"）→ 频道直接 @Bettor 问。**跟"设计前查资产"（接位 SOP 第5条·防重造）不冲突**——那条管设计/实现方案本身（仍应自己先动脑），本条管事实性核实。
