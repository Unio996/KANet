## 真对抗结论

### 发现①(MUST-FIX, 卡 S1 落码前必须先定, 直接承接 #7 发现): §3 边界1"测试流量必须可辨识"本身是同一类弱边界, 且 S1 会直接拿它去撞 #7 那条真实存在的洞

§3 第一条硬边界原文: "所有模拟用户消息带既有探针标记约定(如 7/12 探针的显式前缀), 工单/事件可过滤...Owner 收到的升级转发若来自模拟流量, 前缀必须显式声明"。

问题: 这条边界的执行机制是**消息内容里加一段约定俗成的前缀文本**——跟我在 #7(`docs/2026-07-17-NWT-redteam-escalation-payload-downstream-sanitization.md`)里刚打穿的那条防线是**同一类结构**: 纯文本约定, 不是 DB 级硬标记(如 `is_simulated` 列)或结构性隔离(专用测试身份段)。本项目今天刚复发过两次"约定靠自觉守不住必须上机制"(终端自驱 SOP 那两次+#7 的免责前缀), 这里第三次用同一种脆弱模式, 而且这次风险更具体:

- §2 item1 明确写了 S1 要拿 `malicious`/`liar` persona 去跑 `cases/support/` 首批, **目标之一就是 "owner-bot 转发含硬前缀"**——即 S1 设计本身就会让 adversarial 内容真实流过 owner-bot 的 Direction C poller, 落到 `dev-coord-testnet`, 用 Owner 本人 `trust_level=owner` relay 身份广播(#7 已坐实这条链路机制)。
- 如果"测试流量前缀"只是消息内容里的一段字符串(跟"Owner 免责前缀"同一个信任层级), 而不是在 DB 写入时就打的硬标记, 那么: (a) `malicious`/`liar` persona 的探针内容如果本身就是在模拟"伪造系统标记"这类攻击(#3 边界要求的就是社工/资金话术负例), 它和"给这条消息打上'我是测试流量'标签"这两件事**互相干扰**——一条精心构造来测试"能不能伪装系统前缀"的 payload, 跟"我方给它盖的'这是测试'戳"混在同一个信任层, 谁先谁后、能不能互相覆盖, 框架稿完全没界定; (b) 万一 marker 因为测试代码疏漏没带上(同类历史事故: relay id 硬编码漏 1/10 文件教训族), soak 产出的 adversarial 内容会**以 Owner 真实身份广播出去**, 而不只是"污染统计"这么轻——是我在 #7 里描述的攻击场景在**没有真实攻击者的情况下被自己的测试框架意外实现一次**。

**建议**(不落码, 排 S1 前置): S1 落地前必须先回答两个问题, 而不是默认"加个前缀就够":
1. 测试流量的"可辨识性"能不能提到 **DB 写入层**(比如 persona 用一批保留的测试专用 relay/pubkey, 天然可按地址过滤, 不依赖消息文本), 而不是只在文本内容层加前缀?
2. `malicious`/`liar` persona 若产出会触发 `classifyEscalation` 升级的内容, 在 S1 首跑前是否需要先给 owner-bot Direction C poller 加一道"来自已知测试 persona 地址的升级, 走隔离预演频道/dry-run 不真发 dev-coord-testnet"的口子——这不等于否定 §3 的"真闸测真"精神(测试要打真实闸没错), 但"打真实闸"和"广播到 Owner 真实身份的生产协调频道"应该是两件可以分开控制的事, 现在框架稿把它们绑成了一件。

### 发现②(时效性提醒, 非文档缺陷): §1"7/12 探针套(...七条社工话术)"这句话此刻(07:3xZ)已经跟最新地面事实有偏差
