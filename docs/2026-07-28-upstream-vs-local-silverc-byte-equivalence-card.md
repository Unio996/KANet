## 一、问题一句话

**外部程序用【上游 silverc】编出的字节,与我们这棵树编出的,是不是同一串?**

```
字节不同 ⇒ blake2b 不同 ⇒ P2SH 地址不同 ⇒ 🔴 完全另一个地址, 不是"差一点"
```

🔴 **而它坏起来的样子是这样(J2,结算域)**:外部程序按配方编出合约、往**他算出的地址**打钱,而我们在**我们算出的地址**上等 —— **两边都"按代码正确工作"**,钱在一个我们看不见的地方。
🔴 **最坏的一格**:它**不报**"字节不一致",它报 **【查不到】** —— 与「他还没打钱」「索引没跟上」「地址填错了」**读数完全相同**。

## 三、🔴 选参考行的判据(三条同时成立,不许省)

> **这一节是本卡最容易被跳过、而跳过代价最大的一节。**

```
① created_at ≥ 2026-07-06 21:14:56(本地补丁的 author date)—— 必须是【补丁之后】写入的
② 该行 p2sh(shard_redeem_hex) == 库里存的 shard_p2sh
   🔴 对【这一行本身】核, 不许引用"这一类行都对得上"的结论
③ 该地址在链上实实存在(有 UTXO 或有已花费痕迹)
```

🔴 **为什么 ①**:补丁之前写入的行,是**带 bug 的那一版**编出来的。拿它当参考 ⇒ 比出"字节不同"的原因是**我们那一版有 bug**,而**不是**两边实现不同。
⇒ 🔴 **而这两种"不同"在读数上完全相同:都是"字节对不上"。**

🔴 **风险量化(J2 实测)**:`market_shards` 有 `shard_redeem_hex` 的 **1341 行**中,**1000 行在补丁之前** ⇒ **随手挑一行,约 75% 概率挑到坏的那种。**

> **它是最坏的参考行,而它看起来是最好的那个。**(NWT)

## 四bis、🔴 三格结算域后果(J2 补,2026-07-28 —— 它们改变本卡的**成本估计**,不改变结论)

### ① 🔴「语义等价」在这件事上**不构成安慰** —— 而它是最容易被读出的那个安慰
```
J1 的数: #178 之后 script_len 一致缩小 3–6%(10/10 全变小)
🔵 而一个很自然的读法是:「更短 = 更优的发射路径 = 语义一样 ⇒ 那没事」
🔴 而对 covenant 而言【语义无关, 字节才是地址】——
   ⇒ 所以这不是"可能有影响, 待评估": 对【地址】而言, 影响是【确定且全面】的
```

### ② 🔴 迁移**永远只能对新盘** —— 而这是迁移的主要成本(今天之前没人提过)
```
链上已有的 covenant, 其地址 = 【当初那串字节的 blake2b】⇒ 已 baked, 不可改
⇒ 换编译器对【已在链上的盘】不产生任何影响, 也【救不了】它们
   (jepu1 那 188 KAS 正是"产物不可变"的活证)
⇒ ⇒ 🔴 于是迁移之后会有【两族 covenant 并存】,
     而 settler / 委员 / voter 侧必须【同时认得两族】, 或者划一条硬边界
🔴 ⇒ 迁移的主要成本在这里, 不在构建难度
```

### ③ 🔨 于是步2 的产出要重新定价:它答的是【差异的结构】,不是【差异存不存在】
```
🔵 而库里那些 redeem_hex 让它更便宜: 不需要"两边各编一次",
   只要上游那一版对同一份源编一次, 与库里那串比
🔴 而要看的是【差异分布】:
   · 差异散布在【整份字节】⇒ 机制被整体替换 ⇒ 迁移成本高
   · 差异集中在【少数几段】⇒ 可能只是某几个 opcode 的编码变了 ⇒ 成本差很远
⇒ 🔴 而这两种在"字节不同"这个读数下【同样是"不同"】—— 又是本卡末节那一族
```

## 五、结论要分两种形态记,别合成一句

```
✅ 【字节相同】⇒ 外部程序生成的 covenant 与我们同址 ⇒ 那条主线在这一层通了
🔴 【字节不同】⇒ 那不是"有个 bug 要修", 是【两边在生成不同的东西】
   ⇒ 而那时才轮到问"我们要不要向上游对齐" —— 而【那】才是迁移问题(D-005 那类独立决策)
```
🔵 **⇒ 于是迁移从"现在要不要迁"变成"要不要迁取决于这个测量的结果"。顺序对了。**
