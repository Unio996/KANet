## 一句话结论

> **接入 KANet 的理由是:你有一笔价值在绑定完成前处于风险,而没有任何单一裁决域能原子地保护它。**
>
> **你没有这个问题,就不需要我们 —— 而且接了我们,你的信任假设会变多,不是变少。**

后半句不是谦辞,是这轮最硬的发现之一,理由见第四节。

---

## 一、靶子:那个插件实际在做什么

读了仓库,不是望文生义:

商家提供一个 `kpub` → 插件按 BIP-44 每单派生一个新地址 → **轮询公开 Kaspa REST API** 查该地址的 UTXO 集 → 金额到账即标记已付。允许分多笔支付、允许多付。**没有退款,没有争议处理。**

⇒ **它用近乎零基础设施解决了它的全部问题。** 一个卖货收 KAS 的商家只需要一句话的答案:钱到没到我地址。一个 REST API 就能回答。

**这是这轮的正确起点:先假设它不该接入我们,再看这个假设能不能被推翻。**

## 二、判别式(本轮的核心产出)

### 被推翻的旧判别式

Bettor 初判:**「有没有对手方 ∧ 义务是不是晚于付款才兑现」**。
NWT 用两个反例打破,Bettor 当场撤回:

- **A 型 —— 同时发生,却仍然需要我们**:跨链 / 跨信任域的原子交换。我付 KAS、对手在另一条链付 USDT,两条腿都是此刻就存在的资产,**没有任何"义务在后"**。而"链本身就够"在这里是假的:**单独一条链无法把两条链的两条腿原子绑定。**
- **B 型 —— 晚于付款兑现,却根本不需要我们**:按周期预付、可随时停付的订阅/流付。有对手方、义务也在后,**但时间差内没有任何一笔锁定资金处于风险。**

### 取而代之的判别式

> **绑定完成之前,有没有一笔价值处于风险?**
> **以及,有没有一个单一裁决域能原子地保护它?**
>
> **时序与对手方只是它的相关物,不是它本身。**

**它为什么更好(有现成证据):** 它**同时**解释了数字商品那个案子 —— 买家付了钱、还没拿到密钥,那一刻价值在险;而哈希锁提供了单一裁决域内的原子性。旧判别式只能勉强够到它的一半(靠"义务在后"进来,而真正的理由是"钱在险")。

## 三、用新判别式重切 Owner 分的两类

### 类① —— 与 Kaspa 相关的程序

**纯收款插件不是客户。** 钱到即终局,无价值在险。

**客户是这三种形态:**
1. **跨链 / 跨信任域交割**(A 型)—— 这是我们唯一一个别人替代不了的位置
2. **密钥换钱必须原子的数字商品**(授权码 / 下载 / 会员密钥)
3. **付款与交付有时间差,且时间差内有锁定资金的**

### 类② —— 与 Kaspa 完全无关的应用

🔴 **Bettor 初判是「没有能扛住反驳的接入理由」,本轮更正:有,而且就是 A 型。**

一个完全不碰 Kaspa 的应用,**在它需要跨到另一个信任域去交割时**,需要的正是一个中立裁决域。
**它不需要喜欢 Kaspa,它需要一个双方都不控制的地方。**

### 关于 oracle / broker / exchange

用新判别式看,**它们不是三个产品,是同一件事的三个实例**。
而**每一个的价值都取决于同一件事:裁决是不是原子的、是不是不需要任何人签字。**

## 四、🔴 我们目前卖不出去的真实原因

**不是没人需要裁决,是我们的裁决要人签字。**

| 事实 | 强度 |
|---|---|
| 三份 escrow 合约**全部靠签名放钱,零自执行条件** | ✅ 已实核,**带阴性对照**(哈希条件在本库别处用了两百多次)⇒ **是选择,不是能力限制** |
| 跨链交割**不是原子的**(顺序执行 + 争议兜底) | ✅ 依据仓库既有设计与实核注记 |
| oracle **没有出货** | ✅ 服务文件存在,但"对外可用"这一格**未验**,本文不拿它当筹码 |

⇒ **所以外部程序今天接进来,拿到的不是「链会替你执行」,是「你得信那个签字的人」。**
而那个插件现有的模型是「钱到地址、不可逆、不用信任何人」。
⇒ **我们把它的信任假设变多了。这是"为什么不接入我们"目前最硬的一条理由。**

**而好消息在同一句话里:这不是研究问题。** 原语齐备且已在别处大量使用,缺的是**从来没有一份合约往那个方向写过。**

## 五、站得住的、以及攻过但没打穿的

**✅ 站得住(两人独立确认)**
- **我们不是更好的「钱到没到」预言机**。它轮询一个公开 API,我们问一个节点,同一个架构。
  🔴 而自攻之后这条更强:**这个问题的正解是「商家自己跑一个节点」** —— 那把我们直接删掉。拿我们去换,只是换一个要信的人。

**✅ 攻过、没打穿(照实交付)**
- **实物商品仍然需要 oracle**。物流单号、签收、第三方证明 —— 每一条都要有人把链下事实搬上链。找不到任何绕过的形态。

**🔵 打穿了、但有边界**
- **哈希锁可做零 oracle 的条件交付**:商家把商品密钥的哈希烤进 covenant,买家付款进去,**商家必须揭示原像才能取钱 —— 而揭示那一刻买家同时拿到密钥**;商家不揭示则过期后买家自动可退(时间条件,链上可判)。全程零 oracle,零签字人。
  🔴 **边界(Bettor 补):oracle 只是挪位,没有消失。** 链能验"揭示的东西哈希对得上",验不了"揭示的东西是不是当初承诺的那个" —— 商家完全可以烤一串垃圾的哈希。
  ⇒ **适用面 = 买家能独立、当场、廉价验真的商品**(授权码可以;"课程访问权"这类不行)。

## 六、被推翻和被撤回的(留档,因为它们比结论更有用)

| 原判断 | 结局 |
|---|---|
| 「无退款争议疼的是买家,而装插件的是商家 ⇒ 商家不 care」 | 🔴 **垮(全称命题)**。商家 care 的是**转化率**,而买家保护是转化杠杆。数字商品段更是**塌**:裸收款插件**结构上做不到**"密钥与钱同时易手" |
| 「这个洞只在少数品类成立」 | 🔴 **撤回**。撑它的证据(现成托管插件没主导 WooCommerce)**同时兼容两个相反原因**——买家保护没人要 / 整个加密电商本身微不足道(占比差两个数量级)⇒ **无分辨力**。改为:**规模未知,而我们是基础设施队,测不出它** |
| 「有没有对手方 ∧ 义务是否在后」判别式 | 🔴 **破,已撤**(见第二节) |
| 「类②没有能扛住反驳的接入理由」 | 🔴 **更正:有,就是 A 型** |

**另需记入的外部事实:托管这个位置已经有在位者**(若干非托管托管 + 买家保护的 WooCommerce 插件已经存在并在售),**而我们所在的链电商存量更少。** 我们要进的不是空地。
