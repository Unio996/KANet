## §1 结论先写：**建议 NOT-BEFORE 走 DAA-score lockTime（深度原生），不走墙钟**

理由三条，都可独立核：

1. **finality 本来就以深度计量。** 走 DAA 即**无需换算**——
   而**换算正是 fail-open 的所在**（见 §3 数字）。
2. **本链的出块速率是【运营变量】，不是协议常量**（§2 实证）。
3. **可建性已有先例，不是新能力**：`OracleStake_v1.sil:46` → `require(tx.time >= lockUntilDaa)`，
   变量名直书 `lockUntilDaa`，**DAA 模式 lockTime 已在生产合约里跑着**。

---

## §2 依据（实测，非推断）

**(a) DAA 增速 == 出块速率**（`getBlockDagInfo` 两次快照，60s 窗）：
DAA 前进 **30** / 出块 **30** ⇒ 比值 **1.00**。⇒ **不存在量纲混淆**。

**(b) 而实测速率 ≈ 0.5 BPS，与 `p2sh.mjs:1474` 注释的「~2.5s @ 8BPS」差约 16×。**
同日另测得 **0.48/s 与 0.96/s**（2× 摆动）⇒ **速率本身不稳定**。

**(c) 🔴 速率为什么不稳 —— 根因是运营配置，不是协议**：
本机 `stratum-bridge` 启动参数含
`--internal-cpu-miner --internal-cpu-miner-threads 1`
⇒ **TN12 的出块由我们自己【一个 CPU 线程】驱动**。
且本仓有先例：矿工停 ⇒ **整链 halt**（见 memory `reference-tn12-node-mining-outage-recovery`）。

⇒ **任何"每秒多少块"的常量在这里都不是协议保证，而是【当前有谁在挖】的函数。**

🟡 **明列我没查的**：`8 BPS` 很可能是 TN12 的**设计目标值**（注释写时未必错）；
我**没有**查 TN12 的 `BlockrateParams` 真值——本机 `/d/rusty-kaspa` 与 `/d/rusty-kaspa-tn10-build`
都无法给出（前者 `params.rs:643-645` 只认 `Some(10)`，遇 suffix 12 直接 panic；后者只有 release 产物无源码）。
**⇒ 我不拿"8 BPS 是错的"当结论；我的结论只依赖"实测值 ≠ 假设值，且实测值由运营决定"。**

## §3 若坚持走墙钟，fail-open 的数字有多大

| 假设 | 20 深度 ≈ |
|---|---|
| 注释的 8 BPS | **2.5 秒** |
| 实测 0.96/s | ~21 秒 |
| 实测 0.48/s | ~42 秒 |

⇒ 照 8 BPS 把 `F_reveal` 烤成 ~2.5s，**covenant 会在真实 finality 到达前约 37 秒放行 reactive claim**
——**那 37 秒正是 C4-FINALITY 要挡的攻击窗**。

🔴 **而这一格的测试极易全绿**：正常流程没人会卡在那 37 秒里，**只有攻击者会**。

🔴 **更坏的一种（墙钟独有）**：链 halt 后恢复 ⇒ 墙钟早已走过 ⇒
**恢复瞬间 claim 窗立刻打开，而深度一格没涨** ⇒ **fail-open**。
走 DAA 则深度照常累积，**halt 期间两侧都不动 = fail-closed**。

## §4 保守取值（**若** Bettor 裁走墙钟，则本节生效）

- **取值必须按【实测最慢速率】而非平均** —— **慢的那一侧才是 fail-open 的一侧**；
- 速率下界须有**出处 + 观测窗口 + 观测者**，并注明它是**运营量**（会随挖矿配置变）；
- 🔴 **且必须配一条运行时护栏**：出块速率跌破该下界时**停止发起新的 fair-exchange**，
  否则烤进去的常量会在链变慢的那天**静默失效**。
- 换算公式与常量**只允许存在一处**（同 `REORG_SAFE_MIN_DEPTH` 收敛成单一具名常量的先例，
  `pool-shard-register.mjs:83-88`；四处并行维护同一个数字是 Owner 点破过的反模式）。

## §5 单位分叉：两条路的诚实对比

| | **DAA-score lockTime**（建议） | **墙钟 ms lockTime** |
|---|---|---|
| 与 finality 同单位 | ✅ 直接 | 🔴 需换算（fail-open 所在） |
| 受出块速率波动影响 | ✅ 不受 | 🔴 直接受 |
| 链 halt→恢复 | ✅ fail-closed | 🔴 **fail-open** |
| 仓内先例 | ✅ `OracleStake_v1.sil:46` | ✅ `CloseZkV2.sil:67`/`PoolRoot.sil:56` |
| 5e11 地板 | 自动落 DAA 模式（DAA ≈ 7.9e7 ≪ 5e11） | 须 ≥5e11，且**手写 `*1000` 换算是已知坑** |
| 跨腿 | 各腿用**各自链原生单位**（与 §17.3「跨链态不进 covenant 判定」一致） | 同 |

🔴 **两条路都不能混用同一个 lockTime 字段** —— 模式由数值量级自动选，
混写 = **静默换语义**（`PoolRoot.sil:56` 的 `deadline * 1000` 就是手写换算，漏一次即换模式）。

---

## §5-bis 🔴 作用域：**三处 lockTime 必须【同一单位】，不是只改 NOT-BEFORE**

（NWT 2026-08-20 红队指出本草案初稿的缺口，收）

J1 identify 的三处：**reactive NOT-BEFORE** / **reveal 上界**（现改成 refund 下界构造）/ **refund cutoff**。

🔴 **它们之间是【不等式关系】**，例如 `T_react_refund > T_react_min + claim_land_worst + margin`。
⇒ **若只把 NOT-BEFORE 改成 DAA、refund cutoff 仍留墙钟，这个不等式就是在拿【DAA 分数】和【毫秒】比大小。**

**那不是"精度差一点"，是【比较本身没有意义】** —— 而它不会报错：
两个都是整数，比较照常返回 true/false，**只是答案与任何物理事实无关**。

🔨 判据：**同一条安全不等式里出现的所有量，必须同单位。**
⇒ **本草案的建议 = 三处【全部】走 DAA-score，不是只改一处。**
   若 Bettor 裁走墙钟，则同理 —— **三处全部墙钟**，不许混。

## §5-ter 🟡 可移植性留档（NWT 提，当前不影响 TN12 判断）

§5 那句「DAA ≈ 7.9e7 ≪ 5e11 ⇒ 自动落 DAA 模式」**依赖 TN12 当前的慢速率**：
按 ~0.5/s 算，DAA 要涨到 5e11 约需 **3 万年** ⇒ 本网络生命周期内不可能撞线。

🔴 **但这不是普适不变量**：若本设计日后被复用到出块快得多的网络，
DAA score 可能在网络生命周期内**真的逼近 5e11**，届时「自动落 DAA 模式」这个前提会失效，
而失效方式是**静默换模式**（数值一旦跨过 5e11，同一个字段改按 ms epoch 解释）。

⇒ 复用前必须重新核这一条；**本草案的结论只对 TN12 当前参数成立**。
