## 逐项复核(读实际代码片段, 非读 commit message 摘要)

**MUST-FIX①(常量时间比较)——正确**: 新代码 `a.length === b.length && timingSafeEqual(a, b)` 是标准正确写法。核实了两点: ①`timingSafeEqual` 要求等长 buffer 否则抛异常, 先比较 `.length`(整数比较, O(1), 不构成有意义的侧信道——这是 Node.js 官方文档本身推荐的标准防护写法, 泄漏的至多是"长度不对"这个粗粒度信息, 不像原来逐字节比较那样能让攻击者一字节一字节猜出正确值内容)是必要且正确的前置; ②外层三个分支(header 缺失 / env 未配置 / 已配置但值不对)彼此之间的响应耗时差异不构成新的侧信道, 因为前两个分支根本不touch secret 内容, 只有最后一个分支比较真实 secret 字节且用了常量时间比较——**原始漏洞(逐字节猜 token)已经堵死, 没有引入新的等价漏洞**。

**MUST-FIX②(case4 时间窗口+正对照)——正确, 逻辑闭环**: 修法拆成 (a)反例等够一个完整 `FEEDBACK_ESCALATION_POLL_MS` 周期再断言无泄漏 + (b)同窗口内正对照(不带 token 的真实工单确实被转发)。**验证了这个组合真的能防住我原来担心的假阳性**: 如果轮询器根本没在跑, (b) 会先失败(真实工单也没被转发), 不会让 (a) 侥幸看起来"隔离生效"——两个断言绑在同一次 case 运行、同一个等待窗口, 排除了"证明不存在但其实没给它机会存在"这个陷阱。用 `wait_for_db_row` 或等效轮询等待(非固定 `sleep`)这个方向也对, 没有用会拖慢/不稳定的固定睡眠。

**非阻塞建议(case5 三分支)——已折入, 且核实第三分支确实独立验证了 `timingSafeEqual` 分支本身**: 新增的"env 已配置但 token 值错误"分支专门验证常量时间比较分支自身能正确判否, 跟"env 未配置"那条(根本没走到比较这一步)是真正不同的代码路径, 不是凑数。**顺手确认**: "正确 token → isSimulated:true"这个成功路径虽然没有单独放进 case5, 但已经被 case1 的断言("`is_simulated:true`")覆盖到, 不是遗漏, 只是分散在别的 case 里, 不需要重复。
