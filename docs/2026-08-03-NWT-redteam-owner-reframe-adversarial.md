## finding② 🔴🔴 批注 A 与批注 B 放在一起看,会互相拆台——A 对 Prediction 的背书,被 B 自己点名的机制在同一批市场里推翻

这是本轮我认为最重的一条,因为它不是"框架漏了什么",是**Bettor 自己给的两条批注,合起来读会自相矛盾**,而分开读时各自都成立、都没错。

**批注 A 说什么**:"Prediction 线成立"(ZK settle 真落链,D-001 + claim merkle-binding)。

**批注 B 说什么**:"没有人拥有自由裁量权"是目标不是现状——"现役 committee 盲签 + driver-enforce 居多,VOTER 默认 OFF"。

**问题在哪**:批注 A 给"Prediction 线"整体背书为"条件放钱已成立",而批注 B 点名的"committee 盲签"**就发生在 Prediction 的结算路径上**——不是另一条产品线,是同一批 v0.5/v0.6 市场(3-oracle/5-committee 多签结算)。**本轮 J1 和 J2 刚刚各自独立找到的证据,坐实了这个矛盾不是我推测出来的:**

- J1(`#c9pzp8` 同轮,逐字读码):oracle 密钥**亲自签放钱 TX**(`sign_input_for_settle`,`kasia-relay/src/relay.mjs:711`)——"报告"和"放钱"在委员结算路径上是同一个动作,不是"报告→covenant 自动放"。
- J2(同轮):`handlePoolOracleTxSignReq` 签名前**不重跑 decideConsensus、不比对自己之前投的票、不核 evidence**——"谁把 tx_obj 喂过来就签谁的"。已有的 byzantine self-check 模式(PB-S8)存在,但 scope 在 bshard 路径,`pool-market-settler.js` 的 v0.6/v0.7 committee 流程**结构上跳过它**(`isBshard` 判断即 skip,两条路互不相交)——"牙已经造好了,但没装在这条枪上"(在册 memory `reference-trustless-teeth-built-but-not-armed` 的又一实例)。

⇒ **两人这次找到的洞,精确落在批注 A 用来背书"Prediction 线成立"的同一个结算路径上。** 若这批 v0.5/v0.6 committee-sig 市场在当前活跃 Prediction 市场里占多数(D-001 原文自己写"rolling 保持 live 公测运行... 但不再追加投入"——即 committee-sig 路径不是历史遗留,是**当前仍在承载真人钱的主力路径**,ZK-native v0.7 是目标架构但尚未成为多数),那么批注 A 那句"Prediction 线成立"对**当前实际承载资金的大多数市场**是不准确的——它对的是 v0.7 ZK-native 那一个已验证的样本(pb73v/单片 LANDED),不是对"Prediction"这整条产品线。

**要求**:批注 A 需要显式加一句作用域限定,类似:"'条件放钱已成立'目前只对 v0.7 ZK-native 子集成立;v0.5/v0.6 committee-sig 子集(现仍是活跃市场主力)不满足这个断言,适用的是批注 B 的现状描述,不是批注 A 的背书。" 不这样切,D-012 草案会把 B 揭示的问题读成"次要瑕疵",而实际上它覆盖的正是 A 拿来立论的那同一批市场里,金额占比更大的那部分。

## finding③ Exchange 的"Oracle Skill"对应物,不是"比 Prediction 弱",是对真实分歧场景**结构性不存在**——加深而非否定批注 A 那半

批注 A 已经指出 Exchange 三份 escrow 签名占多数、hash 占极少数、跨链非原子。我这条不重复那个数,查的是**争议真正发生时,谁来裁**——这是"Oracle Skill"在 Exchange 里对应的功能位。

逐字读 `kasia-console/src/api/exchange.js:747-796`(`POST /api/exchange/resolve`):
```
2026-04-14 语义: concede-only —— 调用方只能"认输", 不能"宣判对方输"。
maker 调 resolve ⇒ 自动设 taker_wins(maker 认输)
taker 调 resolve ⇒ 自动设 maker_wins(taker 认输)
```
⇒ **这个端点没有裁决能力,只有自愿投降能力。** 如果 maker 和 taker 都不认输(真实分歧,双方各执一词),Exchange **没有任何代码路径能推进到终态**——不是走得慢、不是走了个弱化版的规则,是这条路完全没有铺。对照 Prediction 好歹有 committee 多签(哪怕批注 B 指出它盲签),Exchange 连"谁来投票"这个角色都不存在。

**修正我原本的猜测(诚实标注)**:我一开始以为这里是"管理员手动仲裁",读码后发现不是——**连人工仲裁都没有**,只有双方自愿让步。这比"人工仲裁"更弱,是我原判断的更正,不是补充。

**判定**:批注 A "Exchange 线今天不成立"这句需要加深一层——不只是"条件放钱的机制不够硬",是**争议解决这个角色在 Exchange 里目前是空集**,连 Owner 说的"Oracle Skill 把结果转成可验证条件"这件事在 Exchange 里都没有对应的运行代码,不是"从 Prediction 抽出来复用"就能直接套的空当——抽出来之后 Exchange 那边还没有东西可以插。这个和第 5 点"先冻结 Skill 接口边界,再验证第三个异质应用复用"的顺序建议是一致的,但需要显式写清楚:Exchange 不是"待接入 Oracle Skill 的客户",是"目前连裁决角色都不存在的空位"。

## finding④(次要,不要求处理,记录供参考)Market Seeder 是框架四角色之外的第五种存在形态

第 4 点列的经济角色:Broker / Maker / Oracle Adapter / Verifier / 界面。`market-seeder.js`(既有功能,DEVELOPER-GUIDE 记录)自动做市:同时挂 buy-side 和 sell-side 挂单,需求由自己生成(不是"外部人来找"),流动性也由自己提供——**这个实体同时扮演了"发起需求的人"和"提供价值的人"两个角色,而且没有对手方是外部参与者**。它不是 Broker(没有外部需求要组织),不是纯 Maker(没有外部对手方),更谈不上 Verifier。

**这不是攻击第 4 点的立论**——"外部程序该问什么角色"这句本身没问题,Seeder 是**内部**自动化,不在"外部接入"的讨论范围内。**记录的原因**是:如果 D-012 最终把"四角色"当成对系统内所有经济活动的穷尽分类(而不仅是对外部接入者的分类),Seeder 会是第一个反例。建议 D-012 明确"四角色"的范围是"外部参与者的可选角色",不隐含"系统内一切经济行为都能归进这四类"。

B 的原话("没有人拥有自由裁量权"是目标非现状,委员盲签 + driver-enforce 居多,VOTER 默认 OFF)本身已经用了"居多"这种带余地的措辞,不是全称断言,不容易被单个反例打穿。本轮 J1/J2 的新证据(finding② 引用的两条)只是**加固**了 B,没有削弱它——B 不需要改。唯一要做的是finding②那条:B 揭示的问题需要显式连回 A 覆盖的同一批市场,不能让两条批注分开读、互不打架地都通过。

## 总裁定

**不是"reframe 整体打不穿",三条具体、可核实的修正,建议进 D-012**:

1. **finding①**:第 3 点"Broker 不保管资金"需拆成目标/现状两句,现状句注明当前唯一存量 Broker 实例是托管钱包。
2. **finding②(最重)**:批注 A 对"Prediction 线成立"的背书需要显式限定到 v0.7 ZK-native 子集;v0.5/v0.6 committee-sig 子集(仍是当前活跃市场主力)应改用批注 B 的现状框架描述,不享受 A 的背书——这是 Bettor 自己两条批注之间需要显式连起来的地方,不连起来 D-012 会读出比实际情况更乐观的整体印象。
3. **finding③**:批注 A 对 Exchange 的"不成立"需要加深——争议裁决角色目前结构性空缺(不是弱,是没有),这直接影响"先冻结 Oracle Skill 接口再复用"这个下一步动作的起点估计(Exchange 侧不是"接现成接口",是从零开始需要一个裁决角色)。
4. **finding④**:记录 Seeder 反例,建议"四角色"范围限定为"外部接入者可选角色",不隐含系统内穷尽分类。

批注 B 本身经受住了这轮对抗,不需要改。
