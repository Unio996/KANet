## 根因 (实证)

UTXO 4fdb24b8:0 同时被 3 笔 tx 抢 input:
1. **9a1009f6** (08:12:45.633 retail-dex "请发付款 tx hash") — **赢, 进 mempool**
2. **37a60e61** (08:12:45.639 broker accept_v1 broadcast) — **输, REJECTED**
3. **d3d99af0** (08:12:45.642 broker fail-DM "accept 上链失败") — **输, REJECTED**

→ Martin 0 收到 (broker 1+2 都 失败)
→ broker 状态 _quotes 已 delete (line 112), 但 _pendingAccepts 没 set (因为 tx 是 null)
→ Martin 看不到付款指引

## 为什么 retail-dex (#1) 在 broker handler (#2) 之前赢

J2 推测: conversations.js fork 顺序: handleBuyIntent → handleSellIntent → retail-dex. handleBuyIntent 应该 match "YES" + return 非 null + 早 return. 但它**确实 match 了** (有 broadcastAccept attempt + 失败 fallback DM). 那 retail-dex 怎么也跑了?

可能 1: Trader-B relay 重复处理同一 message (catch-up + live). 第一次跑 handleBuyIntent broadcastAccept fail return "accept 上链失败" (d3d99af0), 第二次重跑 _quotes 已 delete → fall-through retail-dex → "请发付款 tx hash" (9a1009f6).

可能 2: 不同 user message 同时处理. retail-dex 9a1009f6 服务**别的 user** (在 retail-dex state="confirming/awaiting_payment"), broker 37a60e61+d3d99af0 服务 Martin. 两路并发. wallet UTXO selector 都挑了 4fdb24b8:0 (最大 change 后).

## 修法 (不今晚改, 列方案)

a. relay transaction.mjs `_sendLock` 持续到 broadcast confirm (现 likely 只 lock to mempool insert, 同 mempool tx 还能撞 — 待 J2 grep 确认)
b. handleBuyIntent 失败 retry (UTXO 短暂占用, 250ms-500ms 后再试)
c. 把 broker-buy-handler.broadcastAccept + fail-DM 都加到 retry 队列 (同 b)
d. broker DM/broadcast 之前 sleep 300ms 让 retail-dex 那笔先 confirm 离 mempool
e. 强制 broker 操作 serialize (排队), 不让并发 sendCommandAsync

我倾向 (b) 简单 retry — 失败次数低, retry 1-2 次就好. UTXO 双花是 mempool 限速性, 60s 后自然清.
