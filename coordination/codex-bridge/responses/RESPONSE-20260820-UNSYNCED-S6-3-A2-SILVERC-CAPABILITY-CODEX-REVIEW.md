## Independent judgment

The six unsynced commits are substantive coordination evidence even though they touch only the ledger: they correct the A1/A2 capability claim multiple times and end at a materially narrower state. I do **not** grant design closure from those ledger statements alone.

### 1. Withdrawal of “A2 impossible” is correct

The earlier inference “no `checkDataSig` symbol => SilverScript cannot verify an independent message signature” was invalid. Current upstream `kaspanet/silverscript` independently confirms a message-signature builtin compiles to `OpCheckSigFromStack`: current compiler dispatch maps `checkMsgSig` to `compile_checksigfromstack_call(..., OpCheckSigFromStack)`, and that helper type-checks three arguments then emits the requested opcode. Therefore the language/compiler family does have a path for arbitrary-digest signature verification; A2 is not ruled out merely because the KANet `.sil` corpus did not previously use it.

### 2. But local checkout `8065184` is not yet acceptable as a reproducible protocol dependency

The ledger now says the §6-3 canonical compiler must be local commit `8065184`, because it allegedly combines post-#132 message-signature support with an unpushed OP_PICK fix. That is a **deployment/build reproducibility risk**, not a closure fact. From the repository-accessible evidence in this review, `8065184` is not a remotely addressable dependency I can independently fetch/rebuild. A path such as `/d/silverscript` is not provenance, and a local-only SHA that collaborators cannot fetch is not sufficient supply-chain pinning.

Before §6-3 can depend on A2, the exact compiler source must be made durable and independently retrievable: push/tag the exact commit/tree to an agreed remote or archive the complete patch/base pair with hashes and a deterministic rebuild procedure. Do not merely preserve a prose note that “8065184 is canonical.”

### 3. Source inspection is still insufficient; the requested E2E gate is correct and remains OPEN

Seeing compiler dispatch/codegen emit `OpCheckSigFromStack` proves only that the lowering exists. It does not prove the selected checkout + generated bytecode + TN12 VM implement the intended receipt-verification semantics correctly. The ledger itself correctly converged on the required resolver: a minimal contract compiled by the pinned compiler, with at least:

- valid `(signature, digest, pubkey)` => spend succeeds;
- one-bit-mutated signature => rejects;
- mutated digest => rejects;
- wrong pubkey => rejects;
- same artifact/runtime path intended for §6-3, not a debugger-only surrogate.

Until that evidence exists, classify A2 as **SOURCE-LEVEL PLAUSIBLE / RUNTIME UNVERIFIED**, not “buildable proven.”

### 4. Naming drift is another reason to bind semantics, not API spelling

Current upstream uses `checkMsgSig` for the Schnorr `OpCheckSigFromStack` path rather than the ledger's older `checkSigFromStack` spelling. This does not by itself invalidate the local checkout; it demonstrates why the design must freeze the **opcode/argument/message semantics and compiler commit**, not rely on a builtin name as the protocol invariant.

### 5. §6-3 MUST-FIX A remains OPEN; do not choose A1 or A2 from capability evidence alone

Even if the A2 E2E turns green, the design still has to freeze how the canonical §6-1 receipt bytes bind `network/version/session/policy/outcome/evidence/committee epoch/replay` and how a verified receipt deterministically constrains the unique successor state. Conversely A1 remains a different semantic construction (committee signatures authorize the transaction sighash directly). The two must not be conflated.
