Verified facts:

- `compilePayoutShardRedeem` compiles V1 `PayoutShard.sil` with the pinned legacy compiler and a 22-parameter constructor.
- `compilePayoutShardV2Redeem` compiles V2 `PayoutShardV2.sil` with the pinned ZK compiler and a 27-parameter constructor that includes `closeZkTmplAnchor` and four additional ZK-state fields.
- Both `ensurePayoutShard` and `ensurePayoutShardV2` persist redeem/address/constructor fields into the same `payout_shards` shape, but that table has no immutable V1/V2 family discriminator. Existing-row fast paths return the row without coherence validation.
- For 8pson, omitted `zk_native` defaulted genesis creation to V2; the later manual flip to `zk_native=false` routed the daemon recompile through V1. The observed 2614-byte G0/G1 structural difference is therefore expected cross-family divergence, not state serialization, compiler binary drift, or cache behavior.
- The daemon-expected zero-UTXO address was the V1-recompiled address, while consolidate followed the landed V2 redeem through state splice. The chain and daemon were each internally deterministic but followed different family authorities.

Assessment:

- Final classification: **B-plus, with a general architectural blast radius**. The hand-built market and post-genesis flag mutation triggered the incident; the underlying defect is that a mutable market field is treated as the sole family authority for immutable covenant bytes.
- This is not a universal address-derivation defect affecting all untouched bshard markets. It is a universal *coherence vulnerability*: any row can enter the same failure shape after flag mutation, backfill, migration, or partial repair.
- J1tn's proposed fourth explanation is stronger than the earlier three candidates and is consistent with the code and byte evidence. A normal-flow control remains useful as a regression baseline, but it is no longer required to identify the 8pson root cause.
- The landed input redeem plus deterministic state splice is the only safe runtime continuation authority. Recompilation from mutable DB metadata must not independently choose the next spend address.

Objections or risks:

- Adding only a family column is insufficient if it is populated by reading the mutable market flag after mint. It must be written from the actual compile path and bound to a redeem hash/compiler pin/template identifier at genesis.
- Making `zk_native` immutable only at the API layer is insufficient; direct SQL, migrations and repair tools also need a fail-closed invariant or audited override path.
- Structural family detection should be a validation aid, not the primary authority. Where possible, persist explicit `covenant_family`, `template_id`, `compiler_pin`, and `genesis_redeem_hash` from the mint receipt.
- No recovery or refund transaction for 8pson is authorized by this response.

Recommended next action:

1. Move DISC-002 to `proposed_decision` after J2 records the V2 self-recompile closure: decode or recover the original `closeZkTmplAnchor`, then prove `G0 == compilePayoutShardV2Redeem(...)` byte-for-byte.
2. Design the coherence gate as one small fail-closed batch:

   - reject post-mint family mutation except through an explicit audited recovery workflow;
   - validate declared family ↔ structural probe ↔ stored G0 hash ↔ family-specific recompile before consolidate/settle;

3. Add regression tests for both historical inverse cases: V2 market accidentally minted V1 (cswib shape) and V2 mint later re-routed as V1 (8pson shape).
