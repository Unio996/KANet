## ① 第一实例:目标用户画像 · 现有替代方案 · 最痛步骤 · 触发频率

**目标(卡的原话)**:确实需要开放结算,但**不愿自建链上钱路 / 不愿托管用户资金**的 Broker / app。

### 画像 A —— 已经在撮合、但结算走线下的小型 Broker
- 现在怎么做:撮合在自己系统里,**钱走线下或第三方支付**;争议靠人工截图对账
- 最痛的那一步:**争议发生时拿不出双方都认的凭据** —— 各执一词,只能按关系亲疏判
- 触发频率:每笔有争议的订单;而**痛感的峰值在"一个月一两次、但每次很贵"**,不是高频

### 画像 B —— 想加结算、但一看到"托管用户资金"就停下的 app
- 现在怎么做:功能做到"下单"为止,**结算那一步一直没上**
- 最痛的那一步:**托管即承担责任** —— 密钥保管、合规、被盗的赔付,任何一条都超出团队能力
- 触发频率:每次产品会上提一次,每次都被同一个理由挡回去 ⇒ **痛感是持续的,而行动频率是零**
  🔴 ⇒ **这类最危险**:他们会热情地聊,而永远不动手。**访谈必须问出"上一次你为这件事实际做了什么",不能只问"你想不想要"。**

### 画像 C —— 需要可验证裁决的中立第三方 / Oracle 型角色
- 现在怎么做:出具结论,**而结论的执行靠对方自觉**
- 最痛的那一步:**裁决与执行之间断开** —— 判了不一定被执行,且没有痕迹
- 触发频率:每次裁决

### 现有替代方案与切换成本(卡要求记录)
| 替代方案 | 他们为什么现在用它 | 切换成本 |
|---|---|---|
| 线下 / 第三方支付 | 零集成、马上能用 | 低 —— 所以**"能用"不是我们的卖点,"可验证"才是** |
| 自建钱包 + 自托管私钥 | 完全可控 | 🔴 高且是**责任成本**,不是工程成本;这正是他们不做的原因 |
| 现成 L1/L2 SDK | 生态成熟 | 中;而它**不解决"托管用户资金"这一条** |
| 干脆不做结算 | 零风险 | 零 —— 🔴 **这是我们最强的竞争对手** |

## ② 五角色端到端 journey

**Requester(发起需求)**:有需求 → 找到能做的人 → 谈定条件 → **付钱/锁钱** → 收到交付 → 确认或申诉
🔴 断点在「锁钱」与「申诉」:**他要相信钱在自己不履约时拿得回来,在对方不履约时也拿得回来。**

**Provider(履约)**:看到需求 → 接单 → 履约 → **证明我履约了** → 收钱
🔴 断点在「证明」:他手里的证据,**Requester 不一定认**。

**Broker(撮合 —— 首批目标)**:把两边接上 → 定规则 → **不碰钱地让结算发生** → 出问题时有据可依 → 抽成
🔴 断点在「不碰钱」:今天他要么碰钱(承担托管责任),要么不管结算(那他的撮合就只值一次介绍费)。
🔵 **⇒ 这一格就是 KANet 的位置。整条 journey 里,只有这一格是"现有方案都不好"的。**

**Oracle(裁决)**:被请来判 → 取事实 → 出结论 → **结论被执行**
🔴 断点在最后一步(见画像 C)。

**开发者(接入)**:听说 → 看文档 → **能不能十分钟内看到一次成功的往返** → 接自己的场景 → 上线
🔴 断点在第三步。**而这一格我们今天做不到:外部程序还接不进来(onboarding 仍要求 `bot_token`)。**
⚠️ **⇒ 这不是访谈能解决的,是 UX1 与模块化主干的活。** 写在这里是为了让它别被漏成"用户不感兴趣"。

## ④ 20–30 分钟问题访谈提纲

🔴 **卡的硬约束:禁止用产品宣讲代替问题发现。** 因此本提纲**前 20 分钟不许出现 KANet 三个字**。

**开场(2 分钟)**:说明这次是了解他们怎么做事,不是介绍产品;问可否记录。

**A. 现状与最近一次(8 分钟)——全部问过去,不问将来**
1. 你们现在的结算/交付确认是怎么走的?带我过一遍最近的一笔。
2. **最近一次出问题是什么时候?当时发生了什么?**
3. 那次你们花了多久?谁去处理的?
4. 这类事多久发生一次?

**B. 已经付出的代价(6 分钟)——问行为,不问意愿**
5. 为这件事你们**已经做过什么**?(做过的东西比想做的东西可信一百倍)
6. 试过什么方案?为什么没继续?
7. 现在这套,你们每月大概花多少时间/多少钱在上面?

**C. 边界与不愿意(6 分钟)**
8. 如果要你们**托管用户的钱**,你们会怎么想?
9. 有没有什么是"再好也不会用"的?
10. 接一个新东西,谁来做?他手上现在排着什么?

**D. 收尾(3 分钟)**
11. 我们在做一个东西(**此处才第一次提,一句话,用 Owner 订死的口径,不加一个字**)。你听完的第一反应是什么?**包括"没听懂"和"没兴趣",那两个对我们更有用。**
12. 如果有个只读的版本,你愿意看一眼吗?**(不追问、不劝说 —— 犹豫本身就是数据)**

🔴 **禁止事项**:不许在 A/B/C 里提我们的方案;不许把"我们能解决这个"作为追问的引子;不许把受访者的礼貌当作需求。

## ⑥ 「不愿尝试」的原因分类(访谈中必须归到其中一类,不许记成"再看看")

1. **无需求** —— 这个问题在他们那里不痛
2. **信任不足** —— 痛,但不信我们能解决 / 不信这个阶段的东西
3. **流程不合** —— 想要,但插不进他们现有的流程
4. **集成成本** —— 想要,但没人手做
5. **经济性不足** —— 值,但不够值
6. 🔴 **看不懂** —— 我加的第六类。前五类都假设他理解了我们在说什么;**而"没听懂"要能被记下来,否则它会被误记成 1 或 2。**

🔨 **判据**:每次拒绝必须落到一类;落不进去 ⇒ 说明分类不够,回来改分类,**不许记成"待跟进"**。
