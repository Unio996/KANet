# 控制面 / 协议面 分界线 v0.1 —— 默认拒绝 + 一份极短白名单

> Bettor 07:09 派工 → 07:10 自纠形状（NWT 纠反）。
> **最终形状：白名单列【协议面】，其余一律 deny —— 包括没人分类过的、以后新加的。**
> 判据：`docs/KANet-Positioning.md:78`「不运营任何业务。不撮合交易，不托管资金，不设定价格，**不审核参与者**」

## 🔴 为什么必须是白名单，而不是"列出要装钥匙的那些"

```
逐路由 opt-in ⇒ 忘了列 ⇒ 【它敞着】
默认拒绝      ⇒ 忘了列 ⇒ 【它拒】
```
🔴 **而这不是理论偏好，是本仓的规模决定的**：

```
【实跑】kasia-console/src 下 fastify.get/post/put/delete/patch/all/route 注册行 = 620 行 / 43 个文件
⚠️ 而"行数"不等于"路由数": capability.js 是【循环注册】(:213 for…of CAPABILITY_ROUTES)
   ⇒ 它只贡献 1 行。本次实读该常量 = 1 条路由, 于是这里恰好相等 ——
   🔴 但这个计数方法【在一般情况下会少数】, 任何以后新增的循环注册都会被它漏掉。
```
🔴 **⇒ 620 条逐一分类, 本身就不可能被证明完整。而白名单可以 —— 因为规则是「不在单子上 ⇒ 拒」。**

## 🔵 这份单子的失效方向是安全的那一侧

```
🔴 若我漏了一条【本该是协议面】的 ⇒ 它被拒 ⇒ 有人来抱怨 ⇒ 我们补上
🔵 若我错放一条【本该是控制面】的 ⇒ 它敞着 ⇒ 没有人会来告诉我们
⇒ 所以这份单子【宁可太短】。而它现在只有一条 —— 那不是我没找全, 是外部程序今天确实只能用这一条。
```
✅ **⇒ 而这一条性质要说准**：白名单的完整性**不需要**我把 620 条都看对，只需要**放进去的每一条都对**。
这是默认拒绝相对逐路由 opt-in 的全部价值所在。

---

## 🔴 三条给下一步（NWT 出改法时的硬输入）

```
① deny 必须在【入口】, 不是在每个 handler 里 —— 逐 handler 加检查 = opt-in 换了个写法
② deny 的默认值不许来自"路由没匹配到" —— 未注册的路径本来就 404, 而【已注册但没分类的】才是危险的那批
③ 白名单要按【完整路径 + 方法】匹配, 不许前缀匹配
   🔴 理由: /api/public/… 与 /public/… 只差一个前缀, 而后者是 HTML 页面。
      前缀匹配会把一整族顺手放行, 而那正是"忘了"的另一种形态。
```
