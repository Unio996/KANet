供编程智能体实施参考。所有决策已由架构师确认。
v1.1：合并6项技术修正 + UI认知校准。

## 背景

现有两个页面继续运行，不碰：
- `/trading` — KAS/USDT 专用，42 笔历史交易
- `/market` — KAS/USDT OTC，现有链上协议

新建：
- `/exchange` — 协议级自由市场，从这里开始长

---

## 决策一：页面形态

选方案 C（对话流）+ 轻量分组。

**不用订单簿，不按买卖分。** 市场是一条广播流，每条广播平等——不管是"我有 A 换 B"还是"我要 A 出 B"，结构相同，展示在同一条流里。

轻量分组方式：按派生的 `market_key` 聚合（见决策五），可以切换"全部流"或按资产对过滤。

### UI 认知校准（与代码同等重要）

用户打开 `/exchange` 脑子里默认是"交易所"。首屏必须压住这个预期差。

首屏必须出现的文案：
```
这是你当前节点观测到的市场广播流
不是全网完整订单簿
你的视野取决于本节点自启动以来的索引覆盖
当前节点观测起点：区块 #8,432,100
```

这不是免责声明，是对协议本质的诚实表达。

## 决策二：数据模型

### 核心原则

**供给和需求结构完全对称，只有一种广播结构。**

"我有 100 KAS 换 USDT" 和 "我要 100 KAS 出 USDT" 是同一种消息，挂单方站的角度不同而已。不需要 `type: offer | request` 字段区分。

### Offer 数据结构

```json
{
  "id": "<broadcast_tx_id>",         // 锚定链上来源，全局唯一，跨节点一致
                                     // 若一笔TX含多条广播：broadcast_tx_id + message_index

  "give_asset": "KAS",               // 我愿意给出的资产（自由字符串）
  "give_amount": "100",              // 字符串存储，避免精度问题
  "give_chain": "kaspa",             // 资产所在链，链上资产必填

  "want_asset": "USDT",              // 我想要的资产（自由字符串）
  "want_amount": "4.1",              // 字符串存储
  "want_chain": "bnb",               // 期望对方用哪条链支付

  "maker": "kaspa:qptg465...",       // 挂单方地址
  "broadcast_block": 8432100,        // 广播时的块高
  "broadcast_at": "ISO8601",         // 从链上块时间推导，供流式UI展示"多久前"
  "expires_at": "ISO8601",           // 过期时间

  "verification": "cross_chain_tx",  // 验证类型
  "verification_meta": {             // 验证参数，当前不需要可留空 {}
    "chain": "bnb",
    "token": "USDT",
    "contract": "0x55d398326f99059fF775485246999027B3197955"
  },

  "protocol_status": "open",         // 协议状态（见决策三）
  "is_fully_observed": true,         // 本节点是否观测到完整生命周期

  "market_key": "KAS|USDT",         // 派生字段，UI分组用（见决策五）
  "observed_by_node": "node_id"      // 本节点标识，为多节点同步预留
}
```

### 资产字段：自由字符串

`give_asset` 和 `want_asset` 是**自由字符串，不是枚举**。

协议是格式，不是规则。协议不对标的做判断：
- `"KAS"` ✓
- `"BTC"` ✓
- `"代码审计服务，10小时"` ✓
- `"Polymarket YES shares, event #xyz"` ✓

系统不认识的资产 → `verification: "manual"`，双方手动确认。

### Amount 存字符串

`give_amount` 和 `want_amount` 统一用字符串存储，展示层再解析。

原因：KAS 是 sompi 精度，跨链资产精度各异，服务类没有标准单位。JS number 在跨精度场景是定时炸弹。

## 决策三：状态字段设计

节点有视野边界，不追历史，不补断档。某些节点只观测到报价生命周期的片段。状态字段必须诚实反映这个现实。

### protocol_status（协议状态）

节点根据观测到的协议消息推断：

```
open        — 广播中，无人接单
matched     — 已有人接单
completed   — 交割确认完成
cancelled   — 挂单方取消
expired     — 超过 expires_at
timed_out   — 协议超时
```

### is_fully_observed（观测完整性）

```
true   — 本节点从广播到终态全程观测
false  — 本节点只看到生命周期的一部分
```

不做复杂的 `observation_confidence` 分级，布尔值够用，不过度设计。

---

## 决策四：验证器注册表

验证方式从硬编码改为可扩展注册表。每个报价自带 `verification` 字段，状态机根据此字段选验证器。`verification_meta` 传入验证器作为参数。

```
验证器注册表：

"cross_chain_tx"  → cross-chain-verify.mjs（现有，BNB/ETH/SOL/TRON USDT）
"kaspa_tx"        → kaspa TX 确认（现有）
"btc_tx"          → BTC TX 确认（待建）
"manual"          → 双方手动确认（服务类交易、无链资产）
"oracle"          → 第三方预言机（未来）
```

新增资产 = 新增验证器实现，核心状态机代码不变。

---

## 决策五：分组键（派生视图，非协议字段）

链上广播只有 `give_asset` 和 `want_asset`，分组是 UI/索引层的派生行为。

**分组键不进入协议，不影响广播格式。**

本地索引派生规则：
```javascript
// 规范化：字母排序保证 KAS|USDT 和 USDT|KAS 归同一组
market_key = [give_asset, want_asset].sort().join('|')

// 示例：
// give=KAS, want=USDT  → "KAS|USDT"
// give=BTC, want=KAS   → "BTC|KAS"
// give=代码审计, want=KAS → "KAS|代码审计"（排序后）
// give=任意, want=任意  → "CUSTOM|CUSTOM"（兜底）
```

UI 按 `market_key` 分组，用户也可以切换查看全部广播流。

## 决策六：节点索引机制

### 核心哲学

**参与即索引，缺席即空白。**

每个 KANet 节点自己扫链、建本地索引。没有中心索引服务器，节点间数据不一致是设计，不是 bug。

### 具体行为

- Scout 启动时记录当前块高，从此刻开始扫
- 只索引自节点启动后观测到的广播
- 节点重启 → 从重启那块继续，中间断档不补、不追
- 每个节点的视野是独立的，用 `observed_by_node` 标记

```
node_started_at_block: 8,432,100
index_coverage: 8,432,100 → 当前块
```

### Scout 写 DB 的字段设计原则

按"将来能共享给别人"设计，不只是"跟我相关"。

未来节点之间可以同步索引片段（类似 DHT），不需要重新扫链。这个字段设计现在改代价小，以后改代价大。

## 实施顺序

```
步骤 1  DB: exchange_offers 表（按 v1.1 字段建）
步骤 2  Scout: 识别 kanet_exchange_v1 协议消息，写索引
           - id = broadcast_tx_id（或 + message_index）
           - broadcast_at 从块时间推导
           - market_key 派生写入
           - is_fully_observed 初始为 false，终态更新为 true
步骤 3  Console API: GET /api/exchange/offers
           - 支持 market_key 过滤
           - 支持 protocol_status 过滤
           - 返回节点观测起点块高（供UI展示）
步骤 4  UI: /exchange 页面
           - 首屏：节点视野说明（见决策一）
           - 广播流 + market_key 分组切换
           - 每条广播展示 broadcast_at 相对时间
步骤 5  UI: 发起报价表单
           - give/want 自由字符串输入
           - verification 类型选择（影响后续流程提示）
           - verification_meta 按类型动态展示参数
步骤 6  状态机：接单 → verification 路由 → 交割确认
           - 根据 verification 字段选验证器
           - 传入 verification_meta 作为参数
           - 终态写回 protocol_status + is_fully_observed
```

步骤 1-3 是后端地基，步骤 4-5 是可见入口，步骤 6 是完整闭环。

---

## 不做的事（边界）

- 不碰 `/trading` 和 `/market` 现有代码
- 不建中心化索引服务
- 不做链下撮合算法（点对点，广播后自然撮合）
- 不强制资产白名单
- 历史数据不回填（节点上线前的广播不追）
- `market_key` 不写入链上协议消息（仅本地派生）
